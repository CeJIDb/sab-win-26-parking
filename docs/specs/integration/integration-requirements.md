# Требования к интеграции

Документ фиксирует требования класса `INT-*` для обмена с внешними и смежными системами, а также сохраняет рабочий маппинг данных для онлайн-оплаты.
Он служит каноничной точкой входа для интеграционных требований в разделе `docs/specs/`.

## Оглавление

## Пользовательские требования к интеграции

### `INT-001` `АдаптерСКУД.Событие.ПроверкаДоступа`

Модуль Проверка Доступа должен принимать от модуля Адаптер СКУД СобытиеСКУД со следующими атрибутами:

- типСобытия
- ГРЗ
- датаВремяСобытия
- кппИд
- полосаИд

### `INT-003` `АдаптерСКУД.СобытиеСКУД.ПроверкаДоступа`

Модуль ПроверкаДоступа должен получать от модуля АдаптерСКУД объект СобытиеСКУД (нормализованное представление события смежной СКУД) со следующими атрибутами:

- типСобытия
- ГРЗ
- датаВремяСобытия
- кппИд
- полосаИд

При временной недоступности API основного процесса АдаптерСКУД должен обеспечивать отложенную доставку тех же атрибутов после восстановления связи, сохраняя порядок событий, достаточный для корректной обработки въезда/выезда.

### `INT-002` `ПроверкаДоступа.ПравоДоступа.АдаптерСКУД`

Модуль ПроверкаДоступа должен передавать модулю АдаптерСКУД значение результата проверки права доступа (допуск на КПП) со следующими атрибутами:

- кппИд
- полосаИд
- решениеДопуска: разрешено или запрещено
- корреляцияЗапроса (идентификатор, связывающий ответ с принятым событием, если используется)

### `INT-002` `АдаптерСКУД.КомандаШлагбаума.СКУД`

Модуль АдаптерСКУД должен передавать в смежную систему СКУД команду управления шлагбаумом со следующими атрибутами:

- кппИд
- полосаИд
- команда = «открыть шлагбаум»

### `INT-004` `Платеж.ЗапросОплаты.ПлатежныйПровайдер`

Модуль Платеж должен передавать в ПлатежныйПровайдер запрос на проведение онлайн-оплаты (карты, СБП — по возможностям провайдера) со следующими атрибутами:

- сумма
- валюта
- способОплаты
- внутреннийИдПлатежа
- назначениеПлатежа
- срокОплаты (при необходимости)
- реквизиты, необходимые провайдеру для идемпотентности и сверки (в т.ч. значение, сопоставимое с идПровайдера после ответа)

### `INT-004` `ПлатежныйПровайдер.СтатусОплаты.Платеж`

Модуль Платеж должен получать от ПлатежныйПровайдер данные о результате и статусе операции оплаты со следующими атрибутами (минимум):

- идентификатор операции у провайдера (сопоставимый с идПровайдера)
- статусОперации (достаточный для перевода записи Платеж в одно из значений фиксированного набора статусов)
- времяЗавершения у провайдера (если применимо)

### `INT-004` `Платеж.ЗапросОтменыОплаты.ПлатежныйПровайдер`

Модуль Платеж должен передавать в ПлатежныйПровайдер запрос отмены незавершенной операции с атрибутами, достаточными для идентификации операции у провайдера (в т.ч. идПровайдера), когда Платеж находится в промежуточном статусе.

### `INT-004` `Платеж.ЗапросВозврата.ПлатежныйПровайдер`

Модуль Платеж должен передавать в ПлатежныйПровайдер запрос возврата по успешно проведенной операции с атрибутами: сумма возврата, валюта, ссылка на исходную операцию у провайдера, внутренний идентификатор платежа-возврата.

### `INT-004` `Платеж.ЗапросАктуальногоСтатуса.ПлатежныйПровайдер`

Модуль Платеж должен по расписанию или по событию запрашивать у ПлатежныйПровайдер актуальный статус операции по идПровайдера и получать ответ с атрибутами, достаточными для обновления статус и времяЗавершения записи Платеж.

### `INT-005` `Платеж.ЗапросОплаты.ПлатежныйТерминал`

Модуль Платеж должен передавать на ПлатежныйТерминал объекта (КПП, выезд) запрос на прием оплаты со следующими атрибутами:

- сумма
- валюта
- внутреннийИдПлатежа
- назначениеПлатежа
- идентификатор терминала или точки оплаты (если требуется провайдером терминалов)

### `INT-005` `ПлатежныйТерминал.РезультатОплаты.Платеж`

Модуль Платеж должен получать от ПлатежныйТерминал результат операции со следующими атрибутами (минимум):

- идентификатор операции у терминала/эквайера
- статусОперации
- времяЗавершения (если применимо)

### `INT-006` `Платеж.ЗапросФискализации.ОФД`

Модуль Платеж должен передавать в ОФД запрос на регистрацию фискального чека с реквизитами, достаточными по законодательству и политике выбранного ОФД/ФН, включая:

- идПлатежа и сумму, согласованную с успешным платежом
- состав позиций и налоговые признаки в формате провайдера
- идентификатор чека во внутренней системе для корреляции ответа

### `INT-006` `ОФД.РезультатФискализации.Платеж`

Модуль Платеж должен получать от ОФД результат фискализации со следующими атрибутами (минимум):

- номерФискальный (при успехе)
- статусФискализации (значение из фиксированного набора)
- датаВремяЧека (при необходимости уточнения)
- сведения об ошибке (при неуспехе), достаточные для повторной отправки и учета

### `INT-007` `ОФД.ДанныеЧекаДляПредставления.Платеж`

Модуль Платеж (через связанную запись Чек) должен располагать после фискализации набором атрибутов, достаточным для отображения клиенту и выдачи по сценарию получения чека, на основании данных, полученных от ОФД, в том числе:

- номерФискальный
- датаВремяЧека
- статусФискализации
- сумма
- идПлатежа

### `INT-008` `Аутентификация.ЗапросАвторизации.IdP`

Модуль Аутентификация должен передавать во внешний IdP (Яндекс ID, VK ID) параметры потока OAuth2/OIDC для регистрации/входа клиента ФЛ, включая идентификатор клиента, перенаправления, запрашиваемые области (scopes), защиту от CSRF (state, nonce) - в соответствии с профилем провайдера.

### `INT-008` `IdP.КодАвторизации.Аутентификация`

Модуль Аутентификация должен получать от IdP ответ авторизации с кодом (или иным элементом потока), достаточным для обмена на токены.

### `INT-008` `Аутентификация.ЗапросТокенов.IdP`

Модуль Аутентификация должен передавать в IdP запрос на обмен кода авторизации на токены (grant_type, code, redirect_uri и иные обязательные поля провайдера).

### `INT-008` `IdP.НаборТокенов.Аутентификация`

Модуль Аутентификация должен получать от IdP набор токенов (в т.ч. access_token, id_token по профилю OIDC), достаточный для установления сеанса пользователя в платформе.

### `INT-009` `IdP.АтрибутыПрофиля.Аутентификация`

Модуль Аутентификация должен получать от IdP минимально необходимый набор атрибутов профиля (утверждения claims или UserInfo), достаточный для идентификации пользователя и ведения личного кабинета в соответствии с политикой согласий и ПДн (например: стабильный идентификатор субъекта, контакт для уведомлений - по согласованному с заказчиком минимуму).

### `INT-010` `АгентУведомлений.ЗапросДоставки.СервисУведомлений`

Модуль АгентУведомлений должен передавать во внешний СервисУведомлений запрос на доставку сообщения со следующими атрибутами:

- канал (SMS или e-mail)
- адресПолучателя (номер или e-mail)
- тема (для e-mail, при необходимости)
- текст или идентификаторШаблона
- типСобытияИсточник (для журналирования и поддержки)
- ключИдемпотентности

### `INT-011` `АгентУведомлений.ПолитикаПовтора.СервисУведомлений`

Модуль АгентУведомлений при сбоях доставки должен обеспечивать повторные попытки отправки с тем же ключИдемпотентности, чтобы внешний СервисУведомлений или логика платформы предотвращали дублирование критичных сообщений клиенту при семантике at-least-once.

### `INT-012` `Договор.ИсходящийДокументЭДО.ЭДО`

Модуль Договор должен передавать в ЭДО пакет по договорной документации юридического лица только для маршрута `EDO_CLIENT_THEN_OWNER` (UC-8.2) со следующими атрибутами (минимум):

- типДокумента / вид обмена
- содержимое или безопасная ссылка на документ
- внутреннийИдДоговора
- идПопыткиПодписания
- версияДокумента
- реквизиты контрагента, необходимые ЭДО
- маршрутПодписания (последовательно: клиент, затем Владелец)
- ключИдемпотентности

Повторная отправка одной попытки должна использовать тот же ключИдемпотентности. Новая версия документа или повторное оформление должны создавать новую попытку подписания и новый ключ; внутреннийИдДоговора не является ключом идемпотентности. Требование не применяется к UC-8.8: подписанный оригинал регистрируется Управляющим без ЭДО.

### `INT-012` `ЭДО.СтатусДокумента.Договор`

Модуль Договор должен получать от ЭДО нормализованные сведения о ходе подписания и отклонении документа со следующими атрибутами (минимум):

- кодПровайдераЭДО
- идДокументаЭДО
- идСобытияЭДО
- типСобытияЭДО
- моментСобытия
- метаданныеСобытия, необходимые для проверки ЭП и отображения в ЛК клиента ЮЛ

идСобытияЭДО должен быть стабильным при повторной доставке. Если провайдер не передает стабильный идентификатор, EDO Adapter должен сформировать детерминированный нормализованный идентификатор из неизменяемых атрибутов события.

Входящее событие должно сопоставляться с попыткой подписания по паре кодПровайдераЭДО + идДокументаЭДО и изменять только текущую попытку договора после проверки допустимого перехода. Дубликат, событие неизвестной пары и событие старой попытки должны фиксироваться в contract_inbox_events без повторного перехода текущей попытки или изменения жизненного цикла договора.

Архивирование документа у провайдера ЭДО не изменяет signing_status, lifecycle_status или contracts.archived_at. contracts.archived_at означает внутреннее архивирование договора и заполняется платформой только после терминального состояния жизненного цикла.

### `INT-013` `Площадка.ДанныеИндикации.ИнформационноеТабло`

Модуль Площадка должен передавать на ИнформационноеТабло (дисплей въезда, выезда, навигации) объект ДанныеИндикации со следующими атрибутами (набор уточняется конфигурацией площадки):

- идУстройстваТабло
- сектор / зона (при необходимости)
- показательЗанятости или направление
- оперативныйТекст или кодСообщения для отображения

### `INT-014` `Договор.ИсходящийДокументСМаршрутом.ЭДО`

Модуль Договор должен передавать в ЭДО исходящий документ договора с маршрутом согласования (Клиент → Владелец) со следующими атрибутами:

- типДокумента
- содержимое или безопасная ссылка на документ
- внутреннийИдДоговора
- идПопыткиПодписания
- версияДокумента
- реквизитыКонтрагента
- маршрутПодписания (упорядоченный список сторон с указанием последовательности подписания)
- ключИдемпотентности

Повторная отправка одной попытки должна использовать тот же ключИдемпотентности и не порождать дубликатов в ЭДО. Новая версия документа или повторное оформление должны создавать новую попытку и новый ключИдемпотентности.

### `INT-014` `ЭДО.ПодтверждениеПриема.Договор`

Модуль Договор должен получать от ЭДО синхронный ответ на отправку документа со следующими атрибутами:

- кодПровайдераЭДО
- идДокументаЭДО
- статусПриема
- моментПриема

При успешном статусе приема Модуль Договор должен сохранить неизменяемую пару кодПровайдераЭДО + идДокументаЭДО в текущей попытке и перевести ее в `AWAITING_CLIENT_SIGNATURE`. Неуспешный статус приема не должен переводить попытку в ожидание подписи.

### `INT-014` `ЭДО.СобытиеПодписиКлиента.Договор`

Модуль Договор должен получать от ЭДО асинхронное событие подписания документа клиентом со следующими атрибутами:

- кодПровайдераЭДО
- идДокументаЭДО
- идСобытияЭДО
- моментПодписи
- идентификаторПодписанта

После сопоставления с текущей попыткой и проверки ЭП Модуль Договор должен выполнить переход `AWAITING_CLIENT_SIGNATURE` → `AWAITING_OWNER_SIGNATURE` и заполнить client_signed_at. Для маршрута `EDO_CLIENT_THEN_OWNER` подпись клиента не должна переводить попытку напрямую в `SIGNED`.

### `INT-014` `ЭДО.ФинальныйДокумент.Договор`

Модуль Договор должен получать от ЭДО асинхронное событие с финальным документом, подписанным обеими сторонами (клиент и Владелец), со следующими атрибутами:

- кодПровайдераЭДО
- идДокументаЭДО
- идСобытияЭДО
- содержимое или безопасная ссылка на подписанный документ
- моментПодписиКлиента
- моментПодписиВладельца
- проверенныеМетаданныеЭП

После проверки обеих ЭП и принадлежности документа текущей попытке Модуль Договор должен перевести попытку в `SIGNED`, заполнить client_signed_at при пропущенном промежуточном событии, owner_signed_at, document_file_ref и completed_at, а затем инициировать `EvaluateContractActivation`. Получение финального документа не должно записывать `ACTIVE` напрямую.

### `INT-014` `ЭДО.СобытиеОтказа.Договор`

Модуль Договор должен получать от ЭДО асинхронное событие отказа от подписания (клиент или Владелец отклонил документ) со следующими атрибутами:

- кодПровайдераЭДО
- идДокументаЭДО
- идСобытияЭДО
- сторонаОтказа (клиент или Владелец)
- моментОтказа
- причинаОтказа (если доступна в ЭДО)

После сопоставления с текущей попыткой отказ клиента должен переводить ее в `REJECTED_BY_CLIENT`, а отказ Владельца — в `REJECTED_BY_OWNER`. Сторона, момент и причина отказа должны сохраняться в истории переходов попытки.

### `INT-014` `ЭДО.СобытиеПросрочки.Договор`

Модуль Договор должен получать от ЭДО асинхронное событие об истечении срока подписания на одной из сторон маршрута со следующими атрибутами:

- кодПровайдераЭДО
- идДокументаЭДО
- идСобытияЭДО
- сторонаПросрочки (клиент или Владелец)
- моментПросрочки

Срок ожидания подписи составляет 7 календарных дней на каждый этап маршрута (последовательно: клиент, затем Владелец). Авторитетное решение об истечении срока принимает планировщик Contract Service по signature_deadline_at и допустимому переходу текущей попытки. Событие ЭДО может быть входным сигналом, но не должно обходить эту проверку. По подтвержденному таймауту попытка переходит в `SIGNING_EXPIRED`; lifecycle `EXPIRED` и финансовые состояния не изменяются.

Транспорт асинхронных событий (подпись клиента, финальный документ, отказ, просрочка) основан на webhook как первичном канале доставки. При недоступности платформы или отсутствии подтверждения доставки в течение настраиваемого интервала Договор должен обеспечивать polling fallback по идДокументаЭДО. Webhook и polling должны формировать одно и то же нормализованное событие со стабильным идСобытияЭДО; если провайдер его не предоставляет, EDO Adapter формирует детерминированный идентификатор.

Каждое входящее событие должно сначала фиксироваться в contract_inbox_events с дедупликацией по кодПровайдераЭДО + идСобытияЭДО, затем сопоставляться с попыткой по кодПровайдераЭДО + идДокументаЭДО. Дубликат не создает повторный переход; неизвестная пара и старая попытка не меняют текущую попытку или договор; событие для терминальной попытки фиксируется как конфликт. При нарушении порядка финальный документ с двумя проверенными ЭП может восстановить пропущенный переход подписи клиента. Фиксация обработанного inbox-события, изменение signing_status и запись истории выполняются в одной транзакции с проверкой version текущей попытки.

### `INT-015` `Договор.СобытиеОтправкиНаПодпись.АгентУведомлений`

АгентУведомлений должен передавать в СервисУведомлений уведомление об отправке договора на подпись клиенту после успешного подтверждения приема документа ЭДО и перехода текущей попытки в `AWAITING_CLIENT_SIGNATURE` со следующими атрибутами:

- типСобытияИсточник = «ДоговорОтправленНаПодпись»
- идДоговора
- идПопыткиПодписания
- идКлиента
- идДоменногоСобытия
- параметрыШаблона (название оператора ЭДО, ссылка на кабинет если применимо)
- ключИдемпотентности

### `INT-015` `Договор.СобытиеЗаключения.АгентУведомлений`

АгентУведомлений должен передавать в СервисУведомлений уведомление об успешном заключении договора только после фактического перехода lifecycle_status в `ACTIVE`, если текущая попытка имеет signing_status = `SIGNED`. Переход попытки в `SIGNED` только инициирует `EvaluateContractActivation` и сам по себе не запускает это уведомление. Уведомление рассылается двум получателям:

- Клиенту ЮЛ со следующими атрибутами:
  - типСобытияИсточник = «ДоговорЗаключен»
  - идДоговора
  - идПопыткиПодписания
  - идКлиента
  - идДоменногоСобытия
  - параметрыШаблона (номерДоговора, датаНачала, датаОкончания)
  - ключИдемпотентности

- Управляющему со следующими атрибутами:
  - типСобытияИсточник = «ДоговорЗаключен»
  - идДоговора
  - идПопыткиПодписания
  - идКлиента
  - идУправляющего
  - идДоменногоСобытия
  - параметрыШаблона (номерДоговора, датаНачала, датаОкончания)
  - ключИдемпотентности

### `INT-015` `Договор.СобытиеОтклонения.АгентУведомлений`

АгентУведомлений должен передавать в СервисУведомлений уведомление об отклонении договора клиентом или Владельцем со следующими атрибутами:

- типСобытияИсточник = «ДоговорОтклонен»
- идДоговора
- идПопыткиПодписания
- идКлиента
- идДоменногоСобытия
- сторонаОтказа (клиент или Владелец)
- статусПопытки (`REJECTED_BY_CLIENT` или `REJECTED_BY_OWNER`)
- моментОтказа
- причинаОтказа (если доступна)
- ключИдемпотентности

### `INT-015` `Договор.СобытиеПросрочки.АгентУведомлений`

АгентУведомлений должен передавать в СервисУведомлений уведомление об истечении срока подписания договора со следующими атрибутами:

- типСобытияИсточник = «ИстекСрокПодписанияДоговора»
- идДоговора
- идПопыткиПодписания
- идКлиента
- идДоменногоСобытия
- сторонаПросрочки (клиент или Владелец)
- моментПросрочки
- ключИдемпотентности

Для всех уведомлений INT-015 ключИдемпотентности должен однозначно определяться доменным событием, получателем и каналом доставки. Повторная доставка одного уведомления использует тот же ключ; новая попытка подписания порождает новые доменные события и ключи.

### `INT-016` `Аналитика.ОперационныеДанные.СервисАналитики`

Модуль Аналитика должен по расписанию передавать во внешний сервис аналитики агрегированный набор операционных данных паркинга со следующими атрибутами:

- периодОтчета (дата начала / дата окончания)
- выручкаЗаПериод (сумма, валюта)
- выручкаПоСегментам (список: сегментКлиента, сумма)
- среднийДоходНаМесто (сумма, валюта)
- коэффициентЗагрузки (число; доля занятых мест к общей емкости за период)
- количествоСессий (целое число; число завершенных парковочных сессий за период)
- количествоНовыхКлиентов (целое число)
- доляОнлайнОпераций (число; отношение онлайн-операций к общему числу за период)
- ключИдемпотентности (идентификатор, исключающий повторную запись одного снимка)

Передача данных не должна содержать персональных данных клиентов (ФИО, телефон, e-mail) — только агрегированные показатели. Исходные транзакционные записи остаются внутри системы.

### `INT-017` `СервисАналитики.ПодтверждениеПриема.Аналитика`

Модуль Аналитика должен получать от Сервиса аналитики синхронное подтверждение успешного приема данных со следующими атрибутами:

- ключИдемпотентности («эхо»-ключ из запроса)
- статусПриема (значение из фиксированного набора: «принято», «ошибка»)
- кодОшибки (при статусе «ошибка»; необходим для диагностики и повторной отправки запроса)

При получении статуса «ошибка» модуль Аналитика должен зафиксировать попытку во внутреннем журнале и выполнить повторную отправку не более трех раз с экспоненциальной задержкой.

### `INT-018` `Площадка.КарточкаОбъекта.ГеоСервис`

Модуль Площадка должен при изменении публичных атрибутов объекта парковки передавать в Гео-сервис обновленную карточку объекта со следующими атрибутами:

- названиеОбъекта
- адрес (текстовый адрес и координаты: широта, долгота)
- режимРаботы (расписание по дням недели)
- общаяЕмкость (целое число; общее число мест)
- доступныеМеста (целое число; текущее количество свободных мест; обновляется при каждом изменении состояния площадки)
- ценаОт (минимальная ставка из активных тарифов, валюта)
- контактныйТелефон
- идентификаторОбъектаВГеоСервисе (внешний ключ, полученный при первичной регистрации)

Первичная регистрация объекта в Гео-сервисе выполняется вручную администратором. Интеграция поддерживает только обновление уже зарегистрированной карточки. Обновление доступных мест допускается с задержкой не более 5 минут.

### `INT-019` `ГеоСервис.РезультатОбновления.Площадка`

Модуль Площадка должен получать от Гео-сервиса ответ на запрос обновления карточки со следующими атрибутами:

- идентификаторОбъектаВГеоСервисе
- статусОбновления (значение из фиксированного набора: применено, ошибка)
- сообщениеОбОшибке (при статусе «ошибка»; текст, достаточный для диагностики)

При получении статуса «ошибка» событие фиксируется в журнале системы. Повторная отправка не выполняется автоматически; актуализация произойдет при следующем плановом обновлении или изменении состояния площадки.

### `INT-020` `Бронирование.ИнициацияПлатежа.Платеж`

Модуль Бронирование должен передавать модулю Платеж команду на создание платежной записи в момент, когда бронирование переходит в статус «ожидает оплаты», со следующими атрибутами:

- бронированиеИд (идентификатор создавшего запрос бронирования)
- клиентИд (идентификатор плательщика)
- сессияИд (идентификатор связанной парковочной сессии, если активна)
- сумма (итоговая сумма к оплате, рассчитанная по примененному тарифу)
- валюта (код ISO 4217)
- назначениеПлатежа (значение из Enum: парковка, абонемент)
- способОплаты (значение из Enum: онлайн-лк, автосписание)
- срокОплаты (дата-время, до которых платеж должен быть совершен)
- ключИдемпотентности (исключает дублирование платежной записи при повторном вызове)

Модуль Платеж не пересчитывает сумму самостоятельно — она передается как зафиксированный результат тарификации из модуля Бронирование. Атрибут сессияИд обязателен при постоплате (статус бронирования «активно»); при предоплате (статус «ожидает оплаты» до начала сессии) допускается null.

### `INT-020` `Платеж.РезультатИнициации.Бронирование`

Модуль Платеж должен возвращать модулю Бронирование синхронный ответ на команду инициации платежа со следующими атрибутами:

- платежИд (идентификатор созданной записи Платеж)
- статусПлатежа (значение из Enum: инициализирован, ошибка)
- кодОшибки (при статусе «ошибка»; достаточен для логирования и диагностики)

При получении статуса «ошибка» модуль Бронирование не переводит бронирование в следующий статус и фиксирует сбой в журнале событий.

### `INT-021` `Аутентификация.ДанныеПрофиляSSO.КлиентскийПрофиль`

Модуль Аутентификация после успешного завершения потока OAuth2/OIDC должен передавать модулю КлиентскийПрофиль данные для создания новой учетной записи клиента или обновления существующей со следующими атрибутами:

- ssoПровайдер (значение из Enum: VK ID, Яндекс ID)
- ssoИдентификатор (стабильный идентификатор субъекта у провайдера)
- имя (из профиля провайдера, при наличии)
- фамилия (из профиля провайдера, при наличии)
- телефон (из профиля провайдера, при наличии; формат: 7XXXXXXXXXX)
- email (из профиля провайдера, при наличии)
- сценарий (значение из Enum: первичнаяРегистрация, повторныйВход)
- ключИдемпотентности (исключает создание дублирующей записи Клиент при параллельных вызовах)

При сценарии «первичнаяРегистрация» модуль КлиентскийПрофиль создает запись Клиент с типом «физическое лицо» и устанавливает статус «активен». Поля имя, фамилия, телефон, email заполняются из данных от провайдера только в той мере, в которой провайдер их предоставил; обязательность полей по схеме сущности Клиент проверяется модулем КлиентскийПрофиль самостоятельно. При сценарии «повторныйВход» создание записи не производится — возвращается существующий клиентИд.

### `INT-021` `КлиентскийПрофиль.РезультатСинхронизации.Аутентификация`

Модуль КлиентскийПрофиль должен возвращать модулю Аутентификация синхронный ответ со следующими атрибутами:

- клиентИд (идентификатор созданной или найденной записи Клиент)
- статусКлиента (значение из Enum: активен, приостановлен, заблокирован)
- сценарийВыполнен (значение из Enum: создан, найден)
- статусОперации (значение из фиксированного набора: успех, ошибка)
- кодОшибки (при статусе «ошибка»; достаточен для диагностики)

Модуль Аутентификация использует статусКлиента для принятия решения о допуске в сессию: клиенты со статусом «заблокирован» не получают доступа вне зависимости от результата верификации у провайдера.
