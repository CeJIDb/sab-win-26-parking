## Назначение

Раздел собирает артефакты этапа интеграций — материалы, которые описывают взаимодействие проектируемой платформы с внешними системами и технологические контракты обмена.

## Что хранить в разделе

Подходящие документы для этого каталога:

- интеграционные сценарии использования;
- UML Sequence Diagram;
- DFD и конвейеры сообщений;
- регламенты взаимодействия систем;
- подходы к JSON, XML, RESTful, SOAP;
- журналирование, ретраи и обработка ошибок;
- решения по Kafka, RabbitMQ и другим каналам обмена.

## Текущие материалы

- [Регламент взаимодействия ИС](is-interaction-regulation.md) — сводит в одну таблицу направления межсистемного обмена для блоков СКУД и онлайн-оплаты.
- [UML Sequence Diagram — UC-10.2 Онлайн-оплата краткосрочной аренды](sequence-uc-10-2-pay-online-short-term-rental.md) — показывает последовательность онлайн-оплаты, фискализации и уведомления клиента с ключевыми ветками ошибок.
- [UML Sequence Diagram — UC-12.1 Автоматическая идентификация на въезде](sequence-uc-12-1-pass-auto-identification-entry.md) — цепочка проверок от фиксации ГРЗ до решения `ALLOW/DENY` с reject-ветками и асинхронным уведомлением через дисплей.
- [UML Sequence Diagram — UC-8.2 Создать договор с ЮЛ через ЭДО](sequence-uc-8-2-create-contract.md) — основной поток создания договора + 6 расширений (`3а`, `7а`, `10а`, `10б`, `12а`, `12б`); синхронная передача документа в ЭДО, асинхронные webhook-события подписи / отказа / просрочки, паузы SLA 7 календарных дней между этапами маршрута Клиент → Владелец. Связан с `INT-014`, `INT-015`.
- [UML Sequence Diagram — UC-10.6 Получить чек](sequence-uc-10-6-receipt.md) — основной поток получения фискального чека клиентом ФЛ через PWA/Web + 5 веток ошибок (`401`, `404`, `403`, `409 RECEIPT_PENDING`, `502 OFD недоступен`) и ветка повторной фискализации при статусе `ERROR`. Связан с `INT-006`, `INT-007`.
- [Маппинг обмена данными с ЮKassa](yookassa-data-mapping.md) — фиксирует соответствие между внутренней моделью `payment.*` и объектами API ЮKassa.
- [JSON-пример ответа — UC-10.2-1](payload-uc-10-2-payment.md) — каноничные примеры полезной нагрузки ответа по оплате парковочной сессии.
- [JSON-схема ответа — UC-10.2-1](schema-uc-10-2-payment.md) — формальная JSON Schema ответа по оплате парковочной сессии.
- [JSON-пример ответа — UC-10.6](payload-uc-10-6-receipt.md) — каноничный пример ответа по получению платежного чека с вложенными данными платежа.
- [JSON-схема ответа — UC-10.6](schema-uc-10-6-receipt.md) — формальная JSON Schema ответа по получению платежного чека.
- [XML-пример ответа — UC-10.6](payload-uc-10-6-receipt-xml.md) — каноничный XML-пример полезной нагрузки `receipt` (SOAP-аналог JSON-варианта) с вложенными данными платежа.
- [XSD-схема ответа — UC-10.6](schema-uc-10-6-receipt-xml.md) — формальная XSD-схема receipt-структуры в пространстве имен `http://parking.example.com/schemas/receipt`.
- [WSDL-контракт SOAP-сервиса — UC-10.6](wsdl-uc-10-6-receipt.md) — полный SOAP-контракт `ReceiptService.GetReceipt` (SOAP 1.1, `document/literal`): WSDL с импортом receipt-XSD, конверты запроса и ответа, XSD-схема запроса, fault `ReceiptFault` с перечислением кодов ошибок. Связан с `INT-006`, `INT-007`.
- [OpenAPI-контракт REST-метода — UC-10.6](openapi-uc-10-6-receipt.md) — полный REST-контракт `GET /payments/{paymentId}/receipt` в нотации OpenAPI 3.0.3: путь, параметры, security (Bearer JWT), ответы `200/401/403/404/502` и общие схемы данных. Связан с требованиями `INT-006` и `INT-007`.
- [OpenAPI-контракт REST-метода — UC-12.1](openapi-uc-12-1-access-check.md) — полный REST-контракт `POST /access/check` в нотации OpenAPI 3.0.3: тело запроса от LPR-камеры, security (`X-API-Key`), ответ `200` с трехзначным решением `accessDecision` (`GRANTED` / `DENIED` / `MANUAL_REVIEW`) и ошибки `400/401/503`. Связан с требованиями `INT-001`, `INT-002`, `INT-013`.
- [DFD конвейера сообщений Kafka — онлайн-бронирование (учебный TO-BE)](message-flow-kafka-online-booking.md) — Mermaid K-L1 (обзор с одним блоком Kafka) и K-L2 (три топика синими) для сквозной цепочки «бронь → оплата → подтверждение → уведомление». Outbox-таблицы и CDC-процесс показаны явно. Связан с [ADR-007](../adr/adr-007-kafka-event-bus-online-booking.md).
- [Требования к Kafka — конвейер онлайн-бронирования (учебный TO-BE)](kafka-requirements.md) — две таблицы по формату телемед-референса: технические параметры топиков и семантика доставки для `Topic_BookingCreated`, `Topic_PaymentCompleted`, `Topic_BookingConfirmed`. Producer'ом во всех строках выступает CDC поверх outbox исходного модуля.
- [DFD конвейера сообщений RabbitMQ — рассылка уведомлений (учебный TO-BE)](message-flow-rabbitmq-notification.md) — Mermaid R-L1 (RMQ одним блоком) и R-L2 (Direct exchange `notification.direct` с тремя routing keys + Fanout DLX `notification.dlx` с DLQ). Балансировочная таблица «Kafka-событие → команда RMQ → канал → доставка». Связан с [ADR-008](../adr/adr-008-rabbitmq-notification-dispatch.md).
- [Требования к RabbitMQ — конвейер рассылки уведомлений (учебный TO-BE)](rabbitmq-requirements.md) — таблица обменников и очередей (4 строки: 3 для `notification.direct` × {sms, email, push} + 1 для `notification.dlx` → `notification.dlq`) и раздел «Параметры детально» с расшифровкой `durable`, `x-dead-letter-exchange`, `x-message-ttl`, `x-max-length` и обоснованием отсутствия `x-max-priority`.
- [Реестр ошибок «Оплата»](payment-errors-registry.md) — каталог из 25 типовых ошибок интеграции с платежным провайдером (PAY-001..PAY-025) с типом, контекстом, рекомендациями, критичностью и уровнем автоматизации; покрывает конфигурацию, webhook, идемпотентность, валидацию суммы / валюты, возвраты и устойчивость канала (TLS, rate limit, circuit breaker). Связан с `INT-004`, `INT-005`, `INT-006`.
- [Реестр ошибок «SSO»](sso-errors-registry.md) — каталог из 22 типовых ошибок интеграции с IdP по OAuth2 / OIDC (SSO-001..SSO-022) с типом, контекстом, рекомендациями, критичностью и уровнем автоматизации; покрывает конфигурацию клиента, CSRF-защиту (`state`, `nonce`), валидацию `id_token` (`iss`, `aud`, `exp`), обмен `code` на `token`, получение `userinfo` и устойчивость канала. Связан с `INT-008`, `INT-009`.
