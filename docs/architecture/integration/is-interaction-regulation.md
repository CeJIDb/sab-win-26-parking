# Регламент взаимодействия ИС

Документ фиксирует регламент межсистемного взаимодействия цифровой платформы парковки: кто кому что передает, с какой периодичностью и по какому поводу.

Регламент сводит в одну таблицу направления обмена, состав передаваемых данных и событийную модель. Он используется как опорная таблица для интеграционных сценариев, UML Sequence и контрактов обмена.

## Назначение

Регламент нужен, чтобы:

- зафиксировать перечень межсистемных обменов в одном месте;
- согласовать направление обмена, состав передаваемых данных и триггер передачи;
- дать общую рамку для дальнейшей детализации в UML Sequence, маппингах и API-контрактах.

Регламент описывает направления обмена на уровне «кто кому что передает и по какому событию». Конкретные схемы сообщений и полная семантика полей задаются в контрактах обмена и маппингах (см. раздел [Связанные документы](#связанные-документы)).

## Границы регламента

Включено:

- взаимодействие СКУД, адаптера СКУД и сервиса контроля доступа;
- взаимодействие ЛК клиента, платформы парковки, платежного сервиса, адаптера платежей и внешнего платежного провайдера в сценарии онлайн-оплаты парковочной сессии;
- взаимодействие платежного сервиса с ОФД в сценарии фискализации чека;
- взаимодействие сервиса уведомлений и адаптера уведомлений с внешним сервисом доставки сообщений;
- взаимодействие модуля Договор с внешним ЭДО (СБИС / Диадок) и сервиса уведомлений с внешним сервисом доставки сообщений в сценарии заключения договора с юридическим лицом через ЭДО.

Не включено:

- протоколы физических устройств на объекте (шлагбаумы, терминалы);
- UI-детали редиректа и экраны оплаты у провайдера;
- UC-8.8: Управляющий регистрирует подписанный обеими сторонами оригинал без ЭДО, поэтому маршрут не использует EDO Adapter, contract_inbox_events, кодПровайдераЭДО или идДокументаЭДО.

## Условные обозначения

- **Полный объем / изменения** — передается целиком или только дельта относительно предыдущего состояния.
- **Периодичность обмена / событие** — что именно запускает передачу.
- **Протокол взаимодействия** — транспорт и формат обмена (уточняется в контрактах API).
- **Полезная нагрузка** — пример или схема сообщения (уточняется в соответствующих артефактах JSON/XML).

### Корреляция, порядок и идемпотентность

- Повторная исходящая отправка одной попытки использует тот же `ключИдемпотентности`; `внутреннийИдДоговора` не является ключом идемпотентности.
- Webhook и polling должны формировать одно нормализованное событие. `идСобытияЭДО` стабилен при повторной доставке; если провайдер его не передает, EDO Adapter формирует детерминированный normalized event id из неизменяемых атрибутов события.
- Входящее событие сначала фиксируется в `contract_inbox_events` с дедупликацией по `кодПровайдераЭДО + идСобытияЭДО`, затем сопоставляется с попыткой по `кодПровайдераЭДО + идДокументаЭДО`.
- Дубликат не создает повторный переход. Неизвестная пара и событие старой попытки сохраняются для разбора, но не меняют текущую попытку или договор. Событие для терминальной попытки фиксируется как конфликт.
- При нарушении порядка финальный документ с двумя проверенными ЭП может восстановить пропущенное событие подписи клиента и заполнить обе даты подписания.
- Изменение `signing_status`, запись истории и фиксация обработанного inbox-события выполняются в одной транзакции с проверкой `version` попытки.
- `contracts.archived_at` означает только внутреннее архивирование договора после терминального lifecycle. Архивирование документа у провайдера ЭДО не меняет `signing_status`, `lifecycle_status` или `contracts.archived_at`.
- Для уведомлений `ключИдемпотентности` однозначно определяется доменным событием, получателем и каналом. Новая попытка подписания порождает новые доменные события и ключи.

Источник требований — [INT-012](../../specs/integration/integration-requirements.md) и [INT-014](../../specs/integration/integration-requirements.md) (Договор ↔ ЭДО), [INT-015](../../specs/integration/integration-requirements.md) (Договор → Сервис уведомлений).

## Открытые вопросы

- Конкретный протокол контроллера КПП / СКУД (TCP / RS485 / проприетарный API) — выбирается под оборудование площадки.
- Состав реквизитов идемпотентности и сверки для провайдера платежей — уточняется в контракте интеграции с конкретным провайдером.
- Конкретный ОФД-провайдер (прямой API или через агрегатор) и итоговый профиль ОФД для состава позиций / налоговых признаков.
- Конкретный внешний сервис доставки уведомлений (SMS-шлюз, email-провайдер, собственный сервис) и схема идентификации шаблонов.
- Протокол взаимодействия и полезная нагрузка для Блока 3 (документооборот через ЭДО) — заполняются после согласования контракта с конкретным ЭДО-провайдером (СБИС / Диадок).
