# JSON-схема запроса — UC-8.2 Создание договора с ЮЛ

Документ фиксирует формальную JSON Schema запроса на создание договора долгосрочной аренды с юридическим лицом в сценарии [UC-8.2](../../artifacts/use-case/uc-8-2-create-contract-legal-entity.md) — тело внутреннего REST-метода `POST /api/contracts`.

Схема соответствует спецификации JSON Schema draft 2020-12 и описывает параметры аренды, которые клиент ЮЛ указывает в форме «Создать договор» личного кабинета.

## Назначение

Документ нужен, чтобы:

- задать формальный контракт запроса для шагов 1–4 основного потока UC-8.2;
- служить опорой для автоматической валидации запросов в тестах и в рантайме;
- зафиксировать обязательность полей и ограничения на идентификаторы и списки.

## Контекст применения

Запрос отправляется из ЛК клиента ЮЛ (PWA) через API Gateway в `Сервис Договоров` (P14) после подтверждения условий договора (шаг 3 UC-8.2). По итогам обработки система создает `[договор]` со статусом `черновик` (шаг 4) и запускает документооборот через ЭДО.

Состав тела запроса намеренно минимален:

- идентификатор клиента в запросе не передается — `клиентИд` берется из авторизованной сессии (шаг 4 UC-8.2);
- реквизиты ЮЛ не передаются — подставляются из профиля клиента при формировании документа (шаг 5);
- шаблон договора не передается — система использует опубликованный шаблон долгосрочной аренды для ЮЛ (предусловие UC-8.2).

Каноничный пример полезной нагрузки приведен в артефакте [JSON-пример запроса — UC-8.2](payload-uc-8-2-create-contract.md). HTTP-обвязка метода (security, коды ответов) и контракт ответа будут зафиксированы в OpenAPI-спецификации — Фаза 8 [мастер-плана UC-8.2](../../../plans/2026-05-02-uc-8-2-edo-integration.md); этот документ остается формальной JSON Schema тела запроса.

## JSON Schema

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://example.com/schemas/contract-creation-request.json",
  "title": "ContractCreationRequest",
  "description": "Схема запроса на создание договора долгосрочной аренды с ЮЛ. Передает параметры аренды из формы «Создать договор» в ЛК клиента.",
  "type": "object",
  "required": ["startDate", "endDate", "tariffId", "vehicleIds", "parkingPlaceIds"],
  "properties": {
    "startDate": {
      "type": "string",
      "format": "date",
      "description": "Дата начала действия договора (ISO 8601, YYYY-MM-DD)"
    },
    "endDate": {
      "type": "string",
      "format": "date",
      "description": "Дата окончания действия договора (ISO 8601, YYYY-MM-DD)"
    },
    "tariffId": {
      "type": "integer",
      "minimum": 1,
      "description": "Идентификатор тарифа, применяемого к договору"
    },
    "vehicleIds": {
      "type": "array",
      "items": {
        "type": "integer",
        "minimum": 1
      },
      "minItems": 1,
      "uniqueItems": true,
      "description": "Список идентификаторов ТС, на которые распространяется договор"
    },
    "parkingPlaceIds": {
      "type": "array",
      "items": {
        "type": "integer",
        "minimum": 1
      },
      "minItems": 1,
      "uniqueItems": true,
      "description": "Список идентификаторов ПМ, закрепляемых по договору"
    }
  },
  "additionalProperties": false
}
```

## Инварианты и ограничения

- Все пять полей обязательны; дополнительные поля запрещены (`additionalProperties: false`).
- `startDate` и `endDate` — календарные даты ISO 8601 (`YYYY-MM-DD`) без времени; границы действия договора трактуются в рабочем поясе платформы `+03:00` (Europe/Moscow). Проверка `format: date` включается валидатором с поддержкой форматов (`ajv` + `ajv-formats`).
- Соотношение `endDate > startDate` не выражается средствами JSON Schema — проверяется бизнес-логикой `Сервиса Договоров` до создания `[договор]`.
- `tariffId` и элементы списков — положительные целые числа: суррогатные ключи `BIGINT` таблиц `tariffs`, `vehicles`, `parking_places` ([нормализованная ER-модель](../database/erd/erd-normalized-er-model.md)). Имена полей следуют camelCase-конвенции REST-контрактов платформы (UC-10.6, UC-12.1); в БД им соответствуют snake_case-колонки.
- `vehicleIds` и `parkingPlaceIds` — непустые списки без дубликатов (`minItems: 1`, `uniqueItems: true`).
- Равенство длин `vehicleIds` и `parkingPlaceIds` контрактом не требуется — правила закрепления ТС за машиноместами остаются на стороне бизнес-логики.
- Принадлежность ТС клиенту, доступность машиномест на запрошенный срок и отсутствие договора-дубликата (расширение `3а` UC-8.2) проверяются сервером после структурной валидации.
