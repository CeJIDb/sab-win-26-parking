# Demo 5 — Финальное демо: итог всего проекта

Финальное демо объединяет результаты всех пяти этапов работы команды Five Whys: от исследования AS-IS и постановки цели до архитектуры, функционального проектирования и интеграций. Пять докладчиков, 50 слайдов, критерий готовности MVP.

## Повестка

**Этап 1. Исследование бизнеса (AS-IS)** — Demo 1

- Контекст объекта: открытый паркинг в Санкт-Петербурге, 600 мест, 24/7, конкурирующая бесплатная парковка рядом
- Event Storming AS-IS — цепочка событий от въезда до выезда, выявление ручных шагов и разрывов учета
- BPMN-процессы: въезд/выезд, идентификация клиента, подписание договора, оплата
- Четыре ключевые проблемы: КПП (P1), пропускная способность (P2), отсутствие онлайн-пути (P3), ЮЛ и аналитика (P4)
- UML Class — доменная модель AS-IS; State Machine — жизненный цикл договора

**Этап 2. Концептуальное проектирование решения** — Demo 2

- Цель: 80% взаимодействий клиента с парковкой — онлайн
- Impact Map: цель → изменения в поведении акторов → поставки
- Opportunity Canvas: проблемы, идеи решений, ограничения, метрики успеха
- User Story Map: пять рабочих областей, граница MVP (четыре из пяти)

**Этап 3. Функциональное проектирование решения** — Demo 3

- Event Storming To-Be: целевой поток событий, сравнение с AS-IS
- Контекстная диаграмма: граница системы, 11 внешних систем, ключевые интеграции
- Концептуальная модель: разделение Бронирования и Парковочной сессии как единый язык команды
- Use Case: диаграмма, реестр, пример описанного UC, CRUDL-анализ
- Ключевой сценарий: автоматическая идентификация на въезде (СКУД → платформа → шлагбаум)
- Навигационная карта и кликабельные прототипы личного кабинета клиента
- Функциональные и нефункциональные требования (производительность, надежность, доступность, ИБ)

**Этап 4. Техническое проектирование — архитектура** — Demo 4

- Анализ угроз методом «галстук-бабочка»: несанкционированный доступ, барьеры, план реагирования
- Event Storming To-Be с выделенными доменными контекстами; доменная декомпозиция по DDD: Core / Supporting / Generic
- Выбор архитектуры: модульный монолит — обоснование через нагрузку (3–4 RPS), бюджет, сроки, отсутствие DevOps
- C4-диаграммы: контекст (5 категорий акторов), контейнеры (4 контейнера + PostgreSQL), компоненты
- Нормализованная ER-модель, выбор СУБД

**Этап 5. Техническое проектирование — интеграции** — Demo 5

- Data Flow Diagram (DFD L1): потоки данных между подсистемами и внешними сторонами
- UML Sequence Diagram: сценарий онлайн-оплаты краткосрочной аренды (UC-10-2)
- Маппинг полей и JSON-контракты интеграционных сообщений
- REST API: метод проверки права доступа на въезде
- Реестры ошибок (оплата и SSO): код, тип, причина, автоматизация
- Требования к журналированию событий: системные, безопасности, финансовые, операционные
- Асинхронные процедуры: выбор Outbox-паттерна вместо Kafka и RabbitMQ
- Итог: DoD — «Excel больше не нужен»

## Артефакты-источники

**Этап 1 — AS-IS**

- [Event Storming AS-IS](../../artifacts/as-is/event-storming-as-is.md) — карта доменных событий текущего состояния; основа для выявления узких мест и формулировки проблем.
- [BPMN-процессы AS-IS](../../artifacts/as-is/bpmn-parking-exit.md) — формализованные процессы въезда/выезда, идентификации клиента, подписания договора и оплаты.
- [UML Class — доменная модель AS-IS](../../artifacts/as-is/uml-class-domain-as-is.md) — структура сущностей и связей предметной области до проектирования решения.
- [UML State — договор с физическим лицом](../../artifacts/as-is/uml-state-contract-with-individual.md) — машина состояний договора; показывает жизненный цикл ключевой сущности.

**Этап 2 — Концептуальное проектирование**

- [Impact Map](../../artifacts/impact-map.md) — связывает цель проекта с акторами, воздействиями и поставками.
- [Opportunity Canvas](../../artifacts/opportunity-canvas.md) — фиксирует проблемную ситуацию, идеи решений и метрики ценности.
- [User Story Map](../../artifacts/user-story-map.md) — описывает ключевые пользовательские сценарии и состав MVP.

**Этап 3 — Функциональное проектирование**

- [Контекстная диаграмма](../../artifacts/context-diagram.md) — фиксирует границы системы, внешних акторов и ключевые потоки данных.
- [Реестр Use Case](../../artifacts/use-case/use-case-registry.md) — полный список сценариев с приоритетами и связями с требованиями.
- [Концептуальная модель с атрибутами](../../artifacts/conceptual-model-with-attributes.md) — словарь ключевых сущностей домена с атрибутами.
- [Навигационная карта](../../artifacts/navigation-map.md) — схема переходов между экранами пользовательского интерфейса.

**Этап 4 — Архитектура**

- [Анализ угроз: галстук-бабочка](../../artifacts/infosec/bow-tie-unauthorized-access-to-system-and-data.md) — моделирует угрозу несанкционированного доступа с барьерами на обеих сторонах события.
- [ES TO-BE с выделенными контекстами](../../architecture/ddd/es-tobe-sd-contexts.md) — определяет границы bounded contexts; основа для C4-декомпозиции.
- [C4-диаграммы](../../architecture/c4/c4-diagrams.md) — система на уровнях контекста, контейнеров и компонентов.
- [Нормализованная ER-модель](../../architecture/database/erd/erd-normalized-er-model.md) — схема базы данных в нормальной форме с разбивкой по доменам.
