## Предусловия

- Клиент ЮЛ авторизован в ЛК.
- В профиле клиента заполнены данные организации (UC-2.13 «Добавить данные организации»).
- В профиле клиента заполнены банковские реквизиты организации.
- В профиле клиента есть хотя бы одно ТС.
- Клиент подключен к одному из операторов ЭДО, поддерживаемых платформой (или есть роуминг с тем оператором, где работает Владелец).
- У Владельца есть аккаунт и действующая КЭП в том же операторе ЭДО (или совместимом через роуминг) для подписания договоров со стороны платформы.
- Существует опубликованный шаблон договора долгосрочной аренды для ЮЛ.
- Доступны для бронирования ПМ в нужном секторе на нужный срок.

## Триггер

Клиент ЮЛ в ЛК переходит в раздел «Создать договор».

## Постусловие

- Атрибут `статусЖизненногоЦикла` созданного договора имеет значение «Ожидает активации».
- Текущая попытка подписания по маршруту «ЭДО: клиент, затем владелец» завершена со статусом «Подписан».
- В текущей попытке подписания сохранены ссылка на финальный документ с двумя ЭП, даты подписания клиентом и владельцем, а также дата завершения попытки.
- На указанные клиентом ПМ созданы бронирования на весь срок договора.
- Клиент получил уведомление об успешном подписании договора и доступности документа в ЛК.
- Управляющий получил уведомление о новом подписанном договоре.

Проверка условий активации и переход договора в статус «Активен» не входят в сценарий создания договора. Правила этого перехода определены в разделе [«Активация договора» функциональной модели](../uml-state-contract-to-be.md#активация-договора).

## Основной поток

1. Клиент в форме «Создать договор» указывает параметры аренды:
   - `датаНачала`;
   - `датаОкончания`;
   - тариф;
   - ТС;
   - ПМ.
2. Система рассчитывает стоимость по выбранному клиентом тарифу и отображает условия договора (сумма, период, ПМ, ТС).
3. Клиент подтверждает «Заключить договор» → «Да».
4. Система создает `[договор]` со следующими атрибутами:
   - `идентификатор` — автоген;
   - `клиентИд` — ссылка на клиента из сессии;
   - `шаблонДоговораИд` — ссылка на опубликованный шаблон долгосрочной аренды для ЮЛ;
   - `номерДоговора` — автоген по правилу нумерации;
   - `датаНачала`, `датаОкончания` — из формы;
   - `статусЖизненногоЦикла` = «Ожидает активации».
5. Система создает первую попытку подписания:
   - `маршрутПодписания` = «ЭДО: клиент, затем владелец»;
   - `статусПодписания` = «Черновик»;
   - `ссылкаНаДокумент` = `null`.
6. Система формирует документ договора по шаблону договора с подстановкой реквизитов ЮЛ из профиля клиента и параметров из формы.
7. Система передает документ в ЭДО с маршрутом согласования: Клиент → Владелец.
8. Система получает от ЭДО подтверждение приема документа и сохраняет `кодОператораЭДО` и `идентификаторДокументаЭДО` в текущей попытке.
9. Система присваивает текущей попытке статус «Ожидает подписи клиента».
10. Система отправляет клиенту уведомление «договор отправлен на подпись в ЭДО».
11. Система получает от ЭДО событие «документ подписан клиентом».
12. Система обновляет текущую попытку:
    - `статусПодписания` = «Ожидает подписи владельца»;
    - `датаПодписанияКлиентом` = момент события из ЭДО.
13. Система получает от ЭДО документ, подписанный обеими сторонами (с двумя ЭП), и проверяет обе подписи.
14. Система сохраняет финальный документ в файловом хранилище.
15. Система обновляет текущую попытку:
    - `статусПодписания` = «Подписан»;
    - `датаПодписанияВладельцем` = момент получения финального документа;
    - `ссылкаНаДокумент` = ссылка на сохраненный документ;
    - `датаЗавершения` = момент завершения попытки.
16. Система создает бронирования на указанные клиентом ПМ на весь срок договора. Созданные бронирования сами по себе не являются основанием для доступа.
17. Система отправляет клиенту уведомление об успешном подписании договора и доступности документа в ЛК.
18. Система отправляет управляющему уведомление о новом подписанном договоре.
19. Система завершает выполнение сценария.

## Расширение

**3а. У клиента уже есть договор с тем же шаблоном и пересекающимся составом машиномест за пересекающийся период**

3а1. Система определяет существующий `[договор]` по бизнес-ключу:
   - тот же `клиентИд`;
   - тот же `шаблонДоговораИд`;
   - пересекающийся состав ПМ;
   - пересекающийся период `датаНачала`–`датаОкончания`;
   - `статусЖизненногоЦикла` не принимает значения «Отменен», «Срок действия истек» или «Расторгнут».

3а2. Система возвращает клиенту существующий договор с его `статусЖизненногоЦикла` и состоянием текущей попытки подписания.

3а3. Система завершает выполнение сценария.

**8а. Подтверждение приема от ЭДО не получено**

8а1. Система фиксирует отсутствие подтверждения приема по таймауту.
8а2. Текущая попытка сохраняет статус «Черновик»; повторная техническая отправка использует тот же ключ идемпотентности.
8а3. Система отправляет клиенту уведомление об ошибке отправки документа в ЭДО.
8а4. Система завершает выполнение сценария.

**11а. Из ЭДО получено событие отказа клиента от подписания**

11а1. Система присваивает текущей попытке статус «Отклонен клиентом» и сохраняет причину события.
11а2. Система отправляет клиенту уведомление об отказе от подписания.
11а3. Система завершает выполнение сценария.

**11б. Событие подписания клиентом не получено в течение 7 календарных дней**

11б1. Система фиксирует таймаут ожидания подписи клиента.
11б2. Система присваивает текущей попытке статус «Срок подписания истек»; статус жизненного цикла «Срок действия истек» не используется для таймаута подписания.
11б3. Система отправляет клиенту уведомление об истечении срока подписания.
11б4. Система завершает выполнение сценария.

**13а. Из ЭДО получено событие отказа Владельца от подписания**

13а1. Система присваивает текущей попытке статус «Отклонен владельцем» и сохраняет причину события.
13а2. Система отправляет клиенту уведомление об отказе со стороны парковки.
13а3. Система завершает выполнение сценария.

**13б. Финальный документ не получен в течение 7 дней**

13б1. Система фиксирует таймаут ожидания финального документа с двумя ЭП.
13б2. Система присваивает текущей попытке статус «Срок подписания истек»; статус жизненного цикла «Срок действия истек» не используется для таймаута подписания.
13б3. Система отправляет клиенту уведомление об истечении срока подписания со стороны парковки.
13б4. Система завершает выполнение сценария.

После перехода в статус «Отклонен клиентом», «Отклонен владельцем» или «Срок подписания истек» повторное оформление создает новую попытку подписания. Если в течение 7 календарных дней новая попытка не создана, система переводит договор из статуса «Ожидает активации» в статус «Отменен».

## Требования для UC-8.2 → интеграции

- `INT-012` — исходящий документ и входящие статусы документооборота ЭДО.
- `INT-014` — подтверждение приема, события подписания и отказа, финальный документ и таймаут подписания.
- `INT-015` — уведомления о ходе и результате подписания.

Все входящие события сопоставляются с текущей попыткой по паре `кодОператораЭДО + идентификаторДокументаЭДО`. Дубликат или событие старой попытки фиксируется во входящих событиях договора и не повторяет переход.
