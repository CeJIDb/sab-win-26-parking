# UML State Machine TO-BE: договор

Этот артефакт фиксирует таблицы состояний и переходов, по которым можно построить UML State Machine в PlantUML. Диаграмма намеренно не добавлена: таблицы являются редактируемым источником для ее последующей ручной сборки.

Модель разделяет два независимых автомата:

- попытку подписания документа;
- жизненный цикл договора.

## Статус и границы

Таблицы являются целевой TO-BE-моделью для плана разделения статусов договора. Они задают допустимые переходы, но не заменяют детальные use case и интеграционные контракты.

Подтвержденные сценарии с ЮЛ — договор через ЭДО по UC-8.2 и регистрация подписанного оригинала в админке по UC-8.8. Маршрут ФЛ взят из действующего UC-8.1 и нужен для проверки универсальности модели.

Исторический StateChart договора с ФЛ остается AS-IS-источником и не изменяется.

## Почему два автомата

| Ось            | Объект состояния                        | На какой вопрос отвечает                                                     | Пример независимого изменения                      |
| -------------- | --------------------------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------- |
| Подписание     | Конкретная попытка подписания документа | На каком этапе находится получение обязательных подписей?                    | Клиент подписал документ, но владелец еще нет      |
| Жизненный цикл | Договор                                 | Дает ли договор право пользоваться парковкой и чем завершилось его действие? | Подписанный договор ожидает даты начала или оплаты |

Терминальный результат попытки подписания не переписывается. Повторная отправка исправленного документа создает новую попытку. Договор при этом остается тем же агрегатом и продолжает собственный жизненный цикл.

## Маршруты подписания

| Код маршрута             | Сценарий               | Подпись клиента            | Подпись владельца             | Канал                                              | Статус проработки                                         |
| ------------------------ | ---------------------- | -------------------------- | ----------------------------- | -------------------------------------------------- | --------------------------------------------------------- |
| `CLIENT_SMS_ACCEPTANCE`  | Договор с ФЛ по UC-8.1 | Акцепт оферты кодом из СМС | Не требуется в текущем UC-8.1 | ЛК + СМС                                           | Предварительный: UC-8.1 еще требует отдельной детализации |
| `EDO_CLIENT_THEN_OWNER`  | Договор с ЮЛ по UC-8.2 | КЭП клиента ЮЛ             | Обязательна во всех случаях   | ЭДО                                                | Подтвержденный маршрут текущего скоупа                    |
| `MANUAL_SIGNED_ORIGINAL` | Договор с ЮЛ по UC-8.8 | Обязательна                | Обязательна                   | Подписанный оригинал + ручная регистрация; без ЭДО | Подтвержденный маршрут текущего скоупа                    |

Правило `owner_signature_required` выводится из маршрута, а не задается оператором вручную:

| Маршрут                  | `owner_signature_required` |
| ------------------------ | -------------------------- |
| `CLIENT_SMS_ACCEPTANCE`  | `false`                    |
| `EDO_CLIENT_THEN_OWNER`  | `true`                     |
| `MANUAL_SIGNED_ORIGINAL` | `true`                     |

Таким образом, переход «клиент подписал, подпись владельца не нужна» существует только для маршрута ФЛ `CLIENT_SMS_ACCEPTANCE`. Для любого договора с ЮЛ этот переход запрещен.

## Автомат попытки подписания

### Состояния

| Состояние                   | Тип                       | Смысл                                                                       |
| --------------------------- | ------------------------- | --------------------------------------------------------------------------- |
| `DRAFT`                     | Начальное, нетерминальное | Документ формируется или исправляется до отправки                           |
| `UNDER_REVIEW`              | Нетерминальное            | Документ проходит внутреннее согласование, если оно предусмотрено маршрутом |
| `AWAITING_CLIENT_SIGNATURE` | Нетерминальное            | Документ принят каналом подписания и ожидает действия клиента               |
| `AWAITING_OWNER_SIGNATURE`  | Нетерминальное            | Клиент подписал документ, ожидается обязательная подпись владельца          |
| `SIGNED`                    | Терминальное              | Получены и проверены все подписи, обязательные для маршрута                 |
| `REJECTED_BY_CLIENT`        | Терминальное              | Клиент отказался подписывать документ                                       |
| `REJECTED_BY_OWNER`         | Терминальное              | Владелец отказался подписывать документ                                     |
| `SIGNING_EXPIRED`           | Терминальное              | Истек срок ожидания подписи или финального документа                        |
| `CANCELLED`                 | Терминальное              | Оформление отменено до получения всех обязательных подписей                 |

### Повторное оформление

Повторное оформление после `REJECTED_BY_CLIENT`, `REJECTED_BY_OWNER`, `SIGNING_EXPIRED` или `CANCELLED` не является переходом назад в `DRAFT`.

| Условие                                                                        | Действие                                                        |
| ------------------------------------------------------------------------------ | --------------------------------------------------------------- |
| Повторяется техническая отправка того же документа                             | Использовать ту же попытку и тот же ключ идемпотентности        |
| Изменилось содержимое документа                                                | Создать новую попытку с новым `attempt_no` и `document_version` |
| Предыдущая попытка терминальна                                                 | Создать новую попытку; старую не изменять                       |
| В течение 7 календарных дней после неуспешной попытки новая попытка не создана | Закрыть договор переходом `PENDING_ACTIVATION → CANCELLED`      |

### Данные попытки подписания

Внешние идентификаторы принадлежат попытке, а не договору. Минимальный состав `contract_signing_attempts`:

| Атрибут                    | Назначение                                                                   |
| -------------------------- | ---------------------------------------------------------------------------- |
| `id`                       | Идентификатор попытки                                                        |
| `contract_id`              | Договор, для которого выполняется подписание                                 |
| `attempt_no`               | Последовательный номер попытки внутри договора                               |
| `signing_route`            | Один из маршрутов подписания                                                 |
| `signing_status`           | Текущее состояние попытки                                                    |
| `document_version`         | Версия подписываемого содержимого                                            |
| `edo_provider_code`        | Код оператора ЭДО; `NULL` для маршрутов без ЭДО                              |
| `edo_document_id`          | Идентификатор документа у оператора ЭДО; `NULL` для маршрутов без ЭДО        |
| `outbound_idempotency_key` | Ключ идемпотентной отправки документа                                        |
| `document_file_ref`        | Ссылка на финальный или проверяемый документ                                 |
| `client_signed_at`         | Юридически значимый момент подписи или акцепта клиентом                      |
| `owner_signed_at`          | Юридически значимый момент подписи владельцем                                |
| `manual_verified_at`       | Момент проверки оригинала сотрудником; не подменяет неизвестную дату подписи |
| `signature_deadline_at`    | Срок ожидания подписания или финального документа                            |
| `version`                  | Версия для optimistic locking                                                |
| `created_at`               | Момент создания попытки                                                      |
| `updated_at`               | Момент последнего изменения попытки                                          |
| `completed_at`             | Момент перехода в терминальное состояние                                     |

Обязательные ограничения:

- `UNIQUE (contract_id, attempt_no)`;
- частичный `UNIQUE (edo_provider_code, edo_document_id)` для ненулевой пары;
- уникальность `outbound_idempotency_key`;
- неизменяемость пары `edo_provider_code + edo_document_id` после ее фиксации;
- `contracts.current_signing_attempt_id` может ссылаться только на попытку того же договора.

## Автомат жизненного цикла

### Состояния

| Состояние            | Тип                       | Смысл                                                                                      |
| -------------------- | ------------------------- | ------------------------------------------------------------------------------------------ |
| `PENDING_ACTIVATION` | Начальное, нетерминальное | Договор создан, но еще не дает право доступа: ожидается подписание, дата начала или оплата |
| `ACTIVE`             | Нетерминальное            | Все условия активации выполнены, договор дает основание для бронирования и доступа         |
| `SUSPENDED`          | Нетерминальное            | Действие временно приостановлено; место сохраняется, доступ запрещен                       |
| `CANCELLED`          | Терминальное              | Договор не вступил в действие и закрыт до первой активации                                 |
| `EXPIRED`            | Терминальное              | Ранее активированный договор завершился по сроку                                           |
| `TERMINATED`         | Терминальное              | Ранее активированный договор досрочно расторгнут                                           |

### Данные договора

В `contracts` остаются атрибуты жизненного цикла и технические поля изменения записи:

| Атрибут                      | Назначение                                               |
| ---------------------------- | -------------------------------------------------------- |
| `lifecycle_status`           | Текущее состояние жизненного цикла договора              |
| `current_signing_attempt_id` | Текущая попытка подписания договора                      |
| `lifecycle_version`          | Версия для optimistic locking переходов жизненного цикла |
| `activated_at`               | Момент первой активации договора                         |
| `archived_at`                | Момент архивирования после терминального состояния       |
| `created_at`                 | Момент создания договора                                 |
| `updated_at`                 | Момент последнего изменения записи договора              |

## Активация договора

`Contract Service` является единственным владельцем `lifecycle_status`. События ЭДО, оплаты и календаря не записывают `ACTIVE` напрямую, а запускают команду `EvaluateContractActivation`.

Проверка выполняется после:

- перехода текущей попытки в `SIGNED`;
- подтверждения полной оплаты;
- наступления `start_date`;
- снятия блокировки или приостановки;
- восстановления после сбоя обработки события.

Инварианты активации:

- период договора трактуется в часовом поясе `Europe/Moscow` как `[start_date 00:00; end_date + 1 day 00:00)`;
- полная оплата после `start_date`, но до окончания периода активирует договор с момента подтверждения оплаты, без ретроактивного доступа;
- отсутствие или частичность оплаты остается состоянием счета, платежа или задолженности, а не договора;
- договор без успешной попытки подписания не может стать `ACTIVE`;
- `archived_at` не является состоянием и заполняется только после терминального состояния жизненного цикла.

## Идемпотентность и порядок событий

Для входящих событий ЭДО нужна таблица `contract_inbox_events` или эквивалентный inbox-механизм.

| Ситуация                                                                   | Правило обработки                                                                                                             |
| -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Повторно получено то же событие                                            | Дедупликация по оператору и идентификатору события; состояние не меняется второй раз                                          |
| Событие относится к неизвестной паре `edo_provider_code + edo_document_id` | Не менять договор; поместить событие на разбор или сверку polling                                                             |
| Событие относится к старой попытке                                         | Сохранить факт приема, но не менять текущую попытку и договор                                                                 |
| События пришли не по порядку                                               | Разрешать только допустимый переход; финальный документ с двумя ЭП может восстановить пропущенный промежуточный шаг по `S-07` |
| Событие пытается изменить терминальную попытку                             | Не менять состояние; зафиксировать конфликт                                                                                   |
| Два обработчика конкурируют                                                | Использовать `version` и compare-and-set; проигравший обработчик перечитывает состояние                                       |

Изменение состояния, запись истории и фиксация обработанного inbox-события выполняются в одной транзакции.

## Аудит переходов

История подписания привязана к попытке, история жизненного цикла — к договору. Обе истории append-only.

| Поле              | Назначение                                                               |
| ----------------- | ------------------------------------------------------------------------ |
| `sequence_no`     | Порядковый номер перехода внутри попытки или договора                    |
| `transition_id`   | Идентификатор правила `S-*` или `L-*`                                    |
| `old_status`      | Исходное состояние; `NULL` только для начальной записи                   |
| `new_status`      | Целевое состояние                                                        |
| `actor_type`      | `CLIENT`, `OWNER`, `EMPLOYEE`, `SYSTEM`, `EDO`                           |
| `actor_ref`       | Идентификатор актора, если применимо                                     |
| `source_type`     | Команда, событие ЭДО, платежное событие, планировщик или ручная операция |
| `source_event_id` | Идентификатор исходного события для трассировки и дедупликации           |
| `reason_code`     | Машиночитаемая причина перехода                                          |
| `reason_text`     | Комментарий оператора или описание исключения                            |
| `occurred_at`     | Когда бизнес-событие произошло во внешнем источнике                      |
| `recorded_at`     | Когда платформа записала переход                                         |

Для каждой истории обязательны непрерывная последовательность, уникальность `sequence_no`, запрет `UPDATE` и `DELETE` для прикладной роли и атомарность с обновлением текущего состояния.

## Влияние на бронирование и доступ

| Жизненный статус     | Место и бронирование                                                               | Решение доступа                                                         |
| -------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `PENDING_ACTIVATION` | Резерв допустим по правилам оформления, но не является активным основанием доступа | `deny`                                                                  |
| `ACTIVE`             | Связанные бронирования действуют                                                   | Договор может быть основанием `allow`, если остальные проверки пройдены |
| `SUSPENDED`          | Место и связи сохраняются                                                          | `deny`                                                                  |
| `CANCELLED`          | Будущие бронирования закрываются, резерв освобождается                             | `deny`                                                                  |
| `EXPIRED`            | Будущие бронирования закрываются, место освобождается                              | `deny`                                                                  |
| `TERMINATED`         | Будущие бронирования закрываются, место освобождается                              | `deny`                                                                  |

Read-модель Access Control должна учитывать только `lifecycle_status = ACTIVE` и `archived_at IS NULL`. Статус попытки подписания сам по себе не дает право доступа.

## Маппинг use case

| Use case                | Маршрут                  | Ключевые переходы                                             | Примечание                                                                        |
| ----------------------- | ------------------------ | ------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| UC-8.1, ФЛ              | `CLIENT_SMS_ACCEPTANCE`  | `S-01 → S-04 → S-06`, затем `L-02` после оплаты и даты начала | Единственный текущий маршрут без подписи владельца; требует отдельной детализации |
| UC-8.2, ЮЛ через ЭДО    | `EDO_CLIENT_THEN_OWNER`  | `S-01 → S-04 → S-05 → S-09`, затем `L-02`                     | Подпись владельца обязательна для всех договоров с ЮЛ                             |
| UC-8.8, ЮЛ в админке    | `MANUAL_SIGNED_ORIGINAL` | `S-01 → S-14`, затем `L-02`                                   | Подписанный оригинал регистрируется без ЭДО                                       |
| UC-10.10, онлайн-оплата | Не меняет маршрут        | Успешная полная оплата запускает проверку `L-02`              | Платеж не записывает `ACTIVE` напрямую и не обходит остальные guards              |

## Правила построения PlantUML

При переносе таблиц в PlantUML:

1. Построить две отдельные диаграммы, а не один общий граф.
2. Использовать идентификаторы `S-*` и `L-*` в подписях переходов для обратной трассировки к таблицам.
3. Записывать переход как `event [guard] / effect`, не прятать guard в примечании.
4. Выделить терминальные состояния и запретить обратные стрелки из них.
5. Показать создание новой попытки отдельной заметкой или связью между экземплярами, а не стрелкой терминального состояния в `DRAFT`.
6. Для `S-06` явно написать `route = CLIENT_SMS_ACCEPTANCE`; без этого диаграмма ошибочно разрешит договору с ЮЛ завершиться без подписи владельца.
7. Для `S-07` указать, что это восстановление по финальному документу с двумя проверенными ЭП, а не обход подписи владельца.

## Отделение административного маршрута

UC-8.8 уже проработан как отдельный административный use case. Его нельзя объединять с клиентским UC-8.2, потому что сценарии различаются:

- первичный актор — управляющий или владелец, а не клиент ЮЛ;
- входом служит подписанный оригинал и ручное подтверждение, а не callback ЭДО;
- нужны отдельные права доступа, подтверждение наличия обеих подписей и аудит ручной проверки;
- дата подписи на оригинале и дата проверки сотрудником могут различаться;
- ошибки ввода, дубли, исправление реквизитов и отзыв ошибочной регистрации требуют собственных расширений;
- финансовые состояния из UC-8.8 должны быть перенесены в платежные сущности, не меняя основной административный поток.

Маршрут `MANUAL_SIGNED_ORIGINAL` подтвержден UC-8.8. Поля ЭДО для него не заполняются. Отдельно нужно согласовать только способ хранения доказательства: достаточно аудита подтверждения управляющего или требуется скан оригинала.
