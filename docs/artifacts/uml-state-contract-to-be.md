# UML State Machine TO-BE: договор

Имена атрибутов и статусов в этом функциональном артефакте приводятся на русском языке. Английские технические идентификаторы определяются в нормализованной ER-модели, интеграционных контрактах и DDL.

Этот артефакт фиксирует таблицы состояний и переходов, по которым можно построить UML State Machine в PlantUML. Диаграмма намеренно не добавлена: таблицы являются редактируемым источником для ее последующей ручной сборки.

Модель разделяет два независимых автомата:

- попытку подписания документа;
- жизненный цикл договора.

## Статус и границы

Таблицы являются целевой TO-BE-моделью для плана разделения статусов договора. Они задают допустимые переходы, но не заменяют детальные use case и интеграционные контракты.

Подтвержденные сценарии с ЮЛ — договор через ЭДО по UC-8.2 и регистрация подписанного оригинала в админке по UC-8.8. Маршрут ФЛ взят из действующего UC-8.1 и нужен для проверки универсальности модели.

Исторический StateChart договора с ФЛ остается AS-IS-источником и не изменяется.

## Почему два автомата

| Ось            | Объект состояния                        | На какой вопрос отвечает                                                     | Пример независимого изменения                      |
| -------------- | --------------------------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------- |
| Подписание     | Конкретная попытка подписания документа | На каком этапе находится получение обязательных подписей?                    | Клиент подписал документ, но владелец еще нет      |
| Жизненный цикл | Договор                                 | Дает ли договор право пользоваться парковкой и чем завершилось его действие? | Подписанный договор ожидает даты начала или оплаты |

Терминальный результат попытки подписания не переписывается. Повторная отправка исправленного документа создает новую попытку. Договор при этом остается тем же агрегатом и продолжает собственный жизненный цикл.

## Маршруты подписания

| Код маршрута             | Сценарий               | Подпись клиента            | Подпись владельца             | Канал                                              | Статус проработки                                         |
| ------------------------ | ---------------------- | -------------------------- | ----------------------------- | -------------------------------------------------- | --------------------------------------------------------- |
| `CLIENT_SMS_ACCEPTANCE`  | Договор с ФЛ по UC-8.1 | Акцепт оферты кодом из СМС | Не требуется в текущем UC-8.1 | ЛК + СМС                                           | Предварительный: UC-8.1 еще требует отдельной детализации |
| `EDO_CLIENT_THEN_OWNER`  | Договор с ЮЛ по UC-8.2 | КЭП клиента ЮЛ             | Обязательна во всех случаях   | ЭДО                                                | Подтвержденный маршрут текущего скоупа                    |
| `MANUAL_SIGNED_ORIGINAL` | Договор с ЮЛ по UC-8.8 | Обязательна                | Обязательна                   | Подписанный оригинал + ручная регистрация; без ЭДО | Подтвержденный маршрут текущего скоупа                    |

Правило `подписьВладельцаОбязательна` выводится из маршрута, а не задается оператором вручную:

| Маршрут                  | `подписьВладельцаОбязательна` |
| ------------------------ | ----------------------------- |
| `CLIENT_SMS_ACCEPTANCE`  | Нет                           |
| `EDO_CLIENT_THEN_OWNER`  | Да                            |
| `MANUAL_SIGNED_ORIGINAL` | Да                            |

Таким образом, переход «клиент подписал, подпись владельца не нужна» существует только для маршрута ФЛ `CLIENT_SMS_ACCEPTANCE`. Для любого договора с ЮЛ этот переход запрещен.

## Автомат попытки подписания

### Состояния

| Статус                      | Тип                       | Смысл                                                                       |
| --------------------------- | ------------------------- | --------------------------------------------------------------------------- |
| «Черновик»                  | Начальное, нетерминальное | Документ формируется или исправляется до отправки                           |
| «На согласовании»           | Нетерминальное            | Документ проходит внутреннее согласование, если оно предусмотрено маршрутом |
| «Ожидает подписи клиента»   | Нетерминальное            | Документ принят каналом подписания и ожидает действия клиента               |
| «Ожидает подписи владельца» | Нетерминальное            | Клиент подписал документ, ожидается обязательная подпись владельца          |
| «Подписан»                  | Терминальное              | Получены и проверены все подписи, обязательные для маршрута                 |
| «Отклонен клиентом»         | Терминальное              | Клиент отказался подписывать документ                                       |
| «Отклонен владельцем»       | Терминальное              | Владелец отказался подписывать документ                                     |
| «Срок подписания истек»     | Терминальное              | Истек срок ожидания подписи или финального документа                        |
| «Отменен»                   | Терминальное              | Оформление отменено до получения всех обязательных подписей                 |

### Повторное оформление

Повторное оформление после перехода в статус «Отклонен клиентом», «Отклонен владельцем», «Срок подписания истек» или «Отменен» не является возвратом в статус «Черновик».

| Условие                                                                        | Действие                                                          |
| ------------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| Повторяется техническая отправка того же документа                             | Использовать ту же попытку и тот же ключ идемпотентности          |
| Изменилось содержимое документа                                                | Создать новую попытку с новыми `номерПопытки` и `версияДокумента` |
| Предыдущая попытка терминальна                                                 | Создать новую попытку; старую не изменять                         |
| В течение 7 календарных дней после неуспешной попытки новая попытка не создана | Закрыть договор переходом «Ожидает активации» → «Отменен»         |

### Данные попытки подписания

Внешние идентификаторы принадлежат попытке, а не договору. Минимальный состав сущности «Попытка подписания договора»:

| Атрибут                        | Назначение                                                                    |
| ------------------------------ | ----------------------------------------------------------------------------- |
| `идентификатор`                | Идентификатор попытки                                                         |
| `договорИд`                    | Договор, для которого выполняется подписание                                  |
| `номерПопытки`                 | Последовательный номер попытки внутри договора                                |
| `маршрутПодписания`            | Один из маршрутов подписания                                                  |
| `статусПодписания`             | Текущее состояние попытки                                                     |
| `версияДокумента`              | Версия подписываемого содержимого                                             |
| `кодОператораЭДО`              | Код оператора ЭДО; не заполняется для маршрутов без ЭДО                       |
| `идентификаторДокументаЭДО`    | Идентификатор документа у оператора ЭДО; не заполняется для маршрутов без ЭДО |
| `ключИсходящейИдемпотентности` | Ключ идемпотентной отправки документа                                         |
| `ссылкаНаДокумент`             | Ссылка на финальный или проверяемый документ                                  |
| `датаПодписанияКлиентом`       | Юридически значимый момент подписи или акцепта клиентом                       |
| `датаПодписанияВладельцем`     | Юридически значимый момент подписи владельцем                                 |
| `датаПроверкиОригинала`        | Момент проверки оригинала сотрудником; не подменяет неизвестную дату подписи  |
| `срокПодписания`               | Срок ожидания подписания или финального документа                             |
| `версия`                       | Версия для защиты изменений от гонок                                          |
| `датаСоздания`                 | Момент создания попытки                                                       |
| `датаИзменения`                | Момент последнего изменения попытки                                           |
| `датаЗавершения`               | Момент перехода в терминальное состояние                                      |

Обязательные ограничения:

- пара `договорИд + номерПопытки` уникальна;
- пара `кодОператораЭДО + идентификаторДокументаЭДО` уникальна, когда оба атрибута заполнены;
- `ключИсходящейИдемпотентности` уникален;
- пара `кодОператораЭДО + идентификаторДокументаЭДО` неизменяема после ее фиксации;
- `текущаяПопыткаПодписанияИд` может ссылаться только на попытку того же договора.

## Автомат жизненного цикла

### Состояния

| Статус                | Тип                       | Смысл                                                                                      |
| --------------------- | ------------------------- | ------------------------------------------------------------------------------------------ |
| «Ожидает активации»   | Начальное, нетерминальное | Договор создан, но еще не дает право доступа: ожидается подписание, дата начала или оплата |
| «Активен»             | Нетерминальное            | Все условия активации выполнены, договор дает основание для бронирования и доступа         |
| «Приостановлен»       | Нетерминальное            | Действие временно приостановлено; место сохраняется, доступ запрещен                       |
| «Отменен»             | Терминальное              | Договор не вступил в действие и закрыт до первой активации                                 |
| «Срок действия истек» | Терминальное              | Ранее активированный договор завершился по сроку                                           |
| «Расторгнут»          | Терминальное              | Ранее активированный договор досрочно расторгнут                                           |

### Данные договора

В договоре остаются атрибуты жизненного цикла и аудита изменения записи:

| Атрибут                      | Назначение                                         |
| ---------------------------- | -------------------------------------------------- |
| `статусЖизненногоЦикла`      | Текущее состояние жизненного цикла договора        |
| `текущаяПопыткаПодписанияИд` | Текущая попытка подписания договора                |
| `версияЖизненногоЦикла`      | Версия для защиты переходов от гонок               |
| `датаАктивации`              | Момент первой активации договора                   |
| `датаРасторжения`            | Юридически значимый момент досрочного расторжения  |
| `датаАрхивирования`          | Момент архивирования после терминального состояния |
| `датаСоздания`               | Момент создания договора                           |
| `датаИзменения`              | Момент последнего изменения записи договора        |

| `L-09` | «Приостановлен»     | Клиент расторг договор                                 | Клиент является стороной договора; указан `кодПричины`                                                          | Клиент                                        | «Расторгнут»          | Заполнить `датаРасторжения`; закрыть будущие бронирования; записать инициатора и основание                   |
| `L-10` | «Активен»           | Парковка расторгла договор                             | Владелец или сотрудник уполномочен; заполнены `инициаторИд` и `кодПричины`                                      | Владелец или уполномоченный сотрудник         | «Расторгнут»          | Заполнить `датаРасторжения`; запретить доступ; закрыть будущие бронирования; записать инициатора и основание |
| `L-11` | «Приостановлен»     | Парковка расторгла договор                             | Владелец или сотрудник уполномочен; заполнены `инициаторИд` и `кодПричины`                                      | Владелец или уполномоченный сотрудник         | «Расторгнут»          | Заполнить `датаРасторжения`; закрыть будущие бронирования; записать инициатора и основание                   |

Переход из любого из статусов «Отменен», «Срок действия истек» или «Расторгнут» запрещен. Если отношения с клиентом возобновляются после терминального статуса, создается новый договор.

## Активация договора

`Contract Service` является единственным владельцем атрибута `статусЖизненногоЦикла`. События ЭДО, оплаты и календаря не записывают «Активен» напрямую, а запускают команду `EvaluateContractActivation`.

Проверка выполняется после:

- получения текущей попыткой статуса «Подписан»;
- подтверждения полной оплаты;
- наступления `датаНачала`;
- снятия блокировки или приостановки;
- восстановления после сбоя обработки события.

Инварианты активации:

- период договора трактуется в часовом поясе `Europe/Moscow` как `[датаНачала 00:00; датаОкончания + 1 день 00:00)`;
- полная оплата после `датаНачала`, но до окончания периода активирует договор с момента подтверждения оплаты, без ретроактивного доступа;
- отсутствие или частичность оплаты остается состоянием счета, платежа или задолженности, а не договора;
- договор без успешной попытки подписания не может получить статус «Активен»;
- `датаАрхивирования` не является состоянием и заполняется только после терминального состояния жизненного цикла.

## Идемпотентность и порядок событий

Для входящих событий ЭДО нужна сущность «Входящее событие договора» или эквивалентный механизм дедупликации.

| Ситуация                                                                           | Правило обработки                                                                                                             |
| ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Повторно получено то же событие                                                    | Дедупликация по оператору и идентификатору события; состояние не меняется второй раз                                          |
| Событие относится к неизвестной паре `кодОператораЭДО + идентификаторДокументаЭДО` | Не менять договор; поместить событие на разбор или сверку                                                                     |
| Событие относится к старой попытке                                                 | Сохранить факт приема, но не менять текущую попытку и договор                                                                 |
| События пришли не по порядку                                                       | Разрешать только допустимый переход; финальный документ с двумя ЭП может восстановить пропущенный промежуточный шаг по `S-07` |
| Событие пытается изменить терминальную попытку                                     | Не менять состояние; зафиксировать конфликт                                                                                   |
| Два обработчика конкурируют                                                        | Использовать `версия` и сравнение версий; проигравший обработчик перечитывает состояние                                       |

Изменение состояния, запись истории и фиксация обработанного inbox-события выполняются в одной транзакции.

## Аудит переходов

История статусов подписания привязана к попытке, история жизненного цикла — к договору. Обе истории доступны только для добавления новых записей.

| Поле                    | Назначение                                                               |
| ----------------------- | ------------------------------------------------------------------------ |
| `номерПерехода`         | Порядковый номер перехода внутри попытки или договора                    |
| `идентификаторПерехода` | Идентификатор правила `S-*` или `L-*`                                    |
| `исходныйСтатус`        | Исходное состояние; не заполняется только для начальной записи           |
| `новыйСтатус`           | Целевое состояние                                                        |
| `типИнициатора`         | `CLIENT`, `OWNER`, `EMPLOYEE`, `SYSTEM`, `EDO`                           |
| `инициаторИд`           | Идентификатор инициатора, если применимо                                 |
| `типИсточника`          | Команда, событие ЭДО, платежное событие, планировщик или ручная операция |
| `событиеИсточникИд`     | Идентификатор исходного события для трассировки и дедупликации           |
| `кодПричины`            | Машиночитаемая причина перехода                                          |
| `текстПричины`          | Комментарий оператора или описание исключения                            |
| `датаСобытия`           | Когда бизнес-событие произошло во внешнем источнике                      |
| `датаЗаписи`            | Когда платформа записала переход                                         |

Для каждой истории обязательны непрерывная последовательность, уникальность `номерПерехода`, запрет изменения и удаления записей прикладной ролью и атомарность с обновлением текущего состояния.

## Влияние на бронирование и доступ

| Жизненный статус      | Место и бронирование                                                               | Решение доступа                                                         |
| --------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| «Ожидает активации»   | Резерв допустим по правилам оформления, но не является активным основанием доступа | `deny`                                                                  |
| «Активен»             | Связанные бронирования действуют                                                   | Договор может быть основанием `allow`, если остальные проверки пройдены |
| «Приостановлен»       | Место и связи сохраняются                                                          | `deny`                                                                  |
| «Отменен»             | Будущие бронирования закрываются, резерв освобождается                             | `deny`                                                                  |
| «Срок действия истек» | Будущие бронирования закрываются, место освобождается                              | `deny`                                                                  |
| «Расторгнут»          | Будущие бронирования закрываются, место освобождается                              | `deny`                                                                  |

Read-модель Access Control должна учитывать только значение «Активен» атрибута `статусЖизненногоЦикла` и незаполненную `датаАрхивирования`. Статус попытки подписания сам по себе не дает право доступа.

## Правила построения PlantUML

При переносе таблиц в PlantUML:

1. Построить две отдельные диаграммы, а не один общий граф.
2. Использовать идентификаторы `S-*` и `L-*` в подписях переходов для обратной трассировки к таблицам.
3. Записывать переход как `event [guard] / effect`, не прятать guard в примечании.
4. Выделить терминальные состояния и запретить обратные стрелки из них.
5. Показать создание новой попытки отдельной заметкой или связью между экземплярами, а не стрелкой из терминального статуса в статус «Черновик».
6. Для `S-06` явно написать `route = CLIENT_SMS_ACCEPTANCE`; без этого диаграмма ошибочно разрешит договору с ЮЛ завершиться без подписи владельца.
7. Для `S-07` указать, что это восстановление по финальному документу с двумя проверенными ЭП, а не обход подписи владельца.

## Отделение административного маршрута

UC-8.8 уже проработан как отдельный административный use case. Его нельзя объединять с клиентским UC-8.2, потому что сценарии различаются:

- первичный актор — управляющий или владелец, а не клиент ЮЛ;
- входом служит подписанный оригинал и ручное подтверждение, а не callback ЭДО;
- нужны отдельные права доступа, подтверждение наличия обеих подписей и аудит ручной проверки;
- дата подписи на оригинале и дата проверки сотрудником могут различаться;
- ошибки ввода, дубли, исправление реквизитов и отзыв ошибочной регистрации требуют собственных расширений;
- финансовые состояния из UC-8.8 должны быть перенесены в платежные сущности, не меняя основной административный поток.

Маршрут `MANUAL_SIGNED_ORIGINAL` подтвержден UC-8.8. Поля ЭДО для него не заполняются. Отдельно нужно согласовать только способ хранения доказательства: достаточно аудита подтверждения управляющего или требуется скан оригинала.
