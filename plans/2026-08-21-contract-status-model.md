# План: единая модель состояний договора

**Дата:** 2026-08-21  
**Статус:** согласованная модель, реализация не начата  
**Ветка:** `docs/contract-status-model`  
**Задача:** разделить статус подписания и статус действия договора, синхронизировать связанные TO-BE-артефакты и оба физических DDL без смешения с финансовыми состояниями.

## Контекст

Текущая модель использует один `contract_status_enum` сразу для подготовки документа, подписания, действия договора, завершения срока и архивирования. При этом связанные use case также записывают в статус договора финансовые состояния: ожидание оплаты, частичную оплату и отмену оплаты. Из-за этого одинаковые слова имеют разный смысл, таймаут подписания конфликтует с окончанием срока действия, а DDL отстает от ERD по составу enum и атрибутов.

Пользователь 2026-08-21 согласовал разделение модели на две независимые оси, отдельный `archived_at` и перенос финансовых состояний в `invoices`, `payments` и `debts`. Это согласование также является явным разрешением на последующую правку [интеграционных требований](../docs/specs/integration/integration-requirements.md) в рамках данного плана. Устаревшие требования не удаляются: их формулировки уточняются с сохранением идентификаторов и трассировки.

План описывает одно изменение: единую модель состояний договора от концептуального уровня до физического DDL. Развертывание учебной БД, задания по SQL и общая стратегия межконтекстных связей выполняются по отдельным планам.

## Зачем именно так

Подписание документа и действие договора меняются по разным причинам. Подписание может завершиться отказом или таймаутом, а уже подписанный договор может ожидать даты начала или оплаты, действовать, быть временно приостановлен, завершиться по сроку или быть досрочно расторгнут. Одно поле не позволяет сохранить оба факта без потери смысла.

Архивирование также не заменяет юридически значимое состояние: после переноса записи в архив должно оставаться видно, был договор подписан, истек по сроку или был расторгнут. Поэтому архив хранится как временная отметка, а не значение enum.

Истории двух осей разделяются физически. Это сохраняет типобезопасность enum, исключает строки с взаимоисключающими nullable-полями и позволяет независимо анализировать процесс подписания и жизненный цикл действия договора.

## Целевая модель

### Статус подписания

Поле: `signing_status`, тип: `contract_signing_status_enum`.

| Значение                    | Смысл                                           |
| --------------------------- | ----------------------------------------------- |
| `DRAFT`                     | Документ формируется или сохранен как черновик  |
| `UNDER_REVIEW`              | Внутреннее согласование до отправки на подпись  |
| `AWAITING_CLIENT_SIGNATURE` | Документ отправлен, ожидается подпись клиента   |
| `AWAITING_OWNER_SIGNATURE`  | Клиент подписал, ожидается подпись владельца    |
| `SIGNED`                    | Получены все подписи, обязательные для маршрута |
| `REJECTED_BY_CLIENT`        | Клиент отказался от подписания                  |
| `REJECTED_BY_OWNER`         | Владелец отказался от подписания                |
| `SIGNING_EXPIRED`           | Истек срок подписания на одном из этапов        |
| `CANCELLED`                 | Оформление отменено до завершения подписания    |

`SIGNED`, `REJECTED_BY_CLIENT`, `REJECTED_BY_OWNER`, `SIGNING_EXPIRED` и `CANCELLED` являются терминальными состояниями конкретного маршрута подписания. Повторное оформление создает новый маршрут или новую версию документа, а не переписывает исторический результат без аудита.

### Статус действия

Поле: `lifecycle_status`, тип: `contract_lifecycle_status_enum`.

| Значение             | Смысл                                                                                   |
| -------------------- | --------------------------------------------------------------------------------------- |
| `PENDING_ACTIVATION` | Договор еще не дает право доступа: ожидается подпись, дата начала или условие активации |
| `ACTIVE`             | Договор действует и может быть основанием для связанных бронирований и доступа          |
| `SUSPENDED`          | Действие временно приостановлено с возможностью восстановления                          |
| `EXPIRED`            | Завершился срок действия ранее активированного договора                                 |
| `TERMINATED`         | Ранее действовавший договор досрочно расторгнут                                         |

`EXPIRED` используется только для окончания срока действия. Таймаут подписи называется `SIGNING_EXPIRED` и относится только к `signing_status`.

### Атрибуты договора

В `contracts` должны быть согласованы следующие атрибуты:

| Атрибут             | Тип PostgreSQL                            | Правило                                                                              |
| ------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------ |
| `signing_status`    | `contract_signing_status_enum NOT NULL`   | Начальное значение `DRAFT`                                                           |
| `lifecycle_status`  | `contract_lifecycle_status_enum NOT NULL` | Начальное значение `PENDING_ACTIVATION`                                              |
| `document_file_ref` | `VARCHAR(512)`                            | Ссылка или идентификатор документа, но не бинарное содержимое                        |
| `client_signed_at`  | `TIMESTAMPTZ`                             | Момент подписи или акцепта клиентом                                                  |
| `owner_signed_at`   | `TIMESTAMPTZ`                             | Момент подписи владельцем; nullable для маршрута, где подпись владельца не требуется |
| `archived_at`       | `TIMESTAMPTZ`                             | Момент архивирования; не меняет значения двух статусов                               |

Старое поле `status` и тип `contract_status_enum` удаляются из целевой bootstrap-схемы после перевода всех ссылок.

### История состояний

Одна `contract_status_history` заменяется двумя append-only таблицами:

- `contract_signing_status_history` с `old_status` и `new_status` типа `contract_signing_status_enum`;
- `contract_lifecycle_status_history` с `old_status` и `new_status` типа `contract_lifecycle_status_enum`.

Обе таблицы содержат `id`, `contract_id`, `changed_by_employee_id`, `reason` и `changed_at`. Первая запись по каждой оси допускает `old_status = NULL`; последующие записи образуют непрерывную цепочку. Изменение текущего состояния договора и добавление записи истории выполняются атомарно. Для системных и интеграционных переходов `changed_by_employee_id` может быть `NULL`, а источник фиксируется в `reason` до отдельного решения о структурированном поле источника.

### Инварианты

- Любое состояние действия, кроме `PENDING_ACTIVATION`, допустимо только при `signing_status = SIGNED`.
- `ACTIVE` не означает оплату: условие активации может проверять счет и платеж, но результат оплаты хранится в модуле Payment.
- `SIGNED` означает получение всех подписей, обязательных для выбранного маршрута договора.
- При `signing_status = SIGNED` поле `client_signed_at` заполнено; необходимость `owner_signed_at` определяется маршрутом и типом договора.
- `document_file_ref` указывает на актуальный итоговый документ после завершения подписания, если документ существует в файловом хранилище или ЭДО.
- `archived_at` не очищает и не заменяет статусы, даты подписания и историю переходов.
- `end_date`, если задана, не меньше `start_date`; `EXPIRED` обозначает завершение срока действия, а не просрочку оплаты или подписи.
- Финансовые формулировки `ожидает оплаты`, `ожидает доплаты`, `частично оплачен`, `оплата отменена` и `просрочена оплата` не являются значениями статуса договора.

## Маппинг use case

### UC-8.1, договор с ФЛ

- При создании: `DRAFT` + `PENDING_ACTIVATION`.
- После подтвержденного акцепта оферты по СМС: `SIGNED`, заполнен `client_signed_at`; `owner_signed_at` не требуется для этого маршрута.
- До выполнения условия активации договор остается `PENDING_ACTIVATION`.
- Ошибка, отмена или отсутствие оплаты меняют счет, платеж или задолженность, но не `signing_status` договора.
- После выполнения условий активации: `lifecycle_status = ACTIVE`.

### UC-8.2, договор с ЮЛ через ЭДО

- При создании: `DRAFT` + `PENDING_ACTIVATION`.
- После успешной передачи в ЭДО: `AWAITING_CLIENT_SIGNATURE`.
- После подписи клиента: `AWAITING_OWNER_SIGNATURE`, заполнен `client_signed_at`.
- После получения финального документа с двумя ЭП: `SIGNED`, заполнены `owner_signed_at` и `document_file_ref`.
- `ACTIVE` устанавливается только при выполнении условий активации; будущая дата начала сохраняет `PENDING_ACTIVATION`.
- Отказ клиента, отказ владельца и таймаут записываются соответственно как `REJECTED_BY_CLIENT`, `REJECTED_BY_OWNER` и `SIGNING_EXPIRED`; они не подменяются `EXPIRED`.

### UC-8.8, договор с ЮЛ в админке

- Черновик: `DRAFT` + `PENDING_ACTIVATION`.
- Внутреннее согласование при его наличии: `UNDER_REVIEW`.
- Подтвержденный подписанный оригинал переводит маршрут в `SIGNED`; даты подписей и `document_file_ref` заполняются по доступным подтвержденным данным.
- Частичная, отмененная и просроченная оплата отражаются в `invoices`, `payments` и `debts`; договор остается `PENDING_ACTIVATION`, пока условие активации не выполнено.
- Полная оплата сама по себе не активирует договор раньше `start_date` и других обязательных условий.

## Scope

Входит:

- инвентаризация актуальных TO-BE-документов по статусам, истории, датам подписания и архивированию договора;
- обновление [концептуальной модели](../docs/artifacts/conceptual-model-with-attributes.md);
- обновление [нормализованной ERD](../docs/architecture/database/erd/erd-normalized-er-model.md), включая Mermaid, таблицы атрибутов, сводки и текстовые описания;
- обновление многосхемного DDL `sql/database/chartdb-postgresql-erd-normalized.sql`;
- обновление плоского DDL `sql/database/chartdb-postgresql-erd-normalized-public.sql` для ChartDB;
- синхронизация UC-8.1, UC-8.2 и UC-8.8 с двумя осями и финансовыми сущностями;
- уточнение INT-012, INT-014 и INT-015 в `docs/specs/integration/integration-requirements.md` без удаления требований и без молчаливой смены их идентификаторов;
- синхронизация действующих TO-BE-ссылок и перечней таблиц, найденных при аудите, включая `docs/architecture/integration/is-interaction-regulation.md`, `docs/artifacts/dfd-l1.md`, `docs/artifacts/es-to-be/es-tobe-bp-booking-and-contract.md`, `docs/artifacts/user-story-map.md` и `docs/process/mvp-definition-of-done.md`;
- обновление журнала трассировки и создание ретро после завершения реализации.

Не входит:

- изменение исторических AS-IS-артефактов, протоколов интервью, закрытых планов и ретро;
- изменение импортированного `docs/architecture/database/erd/data-dictionary.md`, который не является каноническим источником;
- переработка UI и backend-кода;
- проектирование общей политики межконтекстных FK и Application Service;
- развертывание или наполнение учебной SQL-БД;
- миграция существующей production-БД и backfill реальных данных;
- пересмотр статусов счетов, платежей и задолженностей, кроме устранения их ошибочного использования как статусов договора.

Если аудит найдет еще один актуальный TO-BE-документ с нормативным описанием статуса договора, он включается в это изменение и в строку трассировки. Простые упоминания слова «договор» без определения состояния не требуют правки.

## Порядок синхронизации

1. Зафиксировать полный список нормативных упоминаний и классифицировать каждый файл как канонический TO-BE, производный TO-BE или исторический источник.
2. Обновить концептуальную модель и описать две оси, атрибуты, смысл значений и базовые инварианты.
3. Синхронизировать UC-8.1, UC-8.2 и UC-8.8 с утвержденным маппингом без финансовых псевдостатусов договора.
4. Уточнить интеграционные требования и регламент: события ЭДО меняют `signing_status`, финальный документ заполняет даты и ссылку, архивирование заполняет `archived_at`.
5. Обновить ERD целиком: диаграмму, сущность `contracts`, обе истории, сводные таблицы, связи и текстовые разделы.
6. Привести оба DDL к ERD и проверить их на пустых базах.
7. Обновить производные TO-BE-документы и ссылки на старую `contract_status_history`.
8. Провести поиск остаточных противоречий, обновить трассировку и выполнить проверки проекта.

## Изменения интеграционного контракта

В требованиях и регламенте фиксируется однозначный маппинг:

| Событие или ответ ЭДО               | Изменение договора                                                           |
| ----------------------------------- | ---------------------------------------------------------------------------- |
| Документ принят и отправлен клиенту | `signing_status = AWAITING_CLIENT_SIGNATURE`                                 |
| Документ подписан клиентом          | `signing_status = AWAITING_OWNER_SIGNATURE`, заполнить `client_signed_at`    |
| Получен финальный документ          | `signing_status = SIGNED`, заполнить `owner_signed_at` и `document_file_ref` |
| Клиент отказался                    | `signing_status = REJECTED_BY_CLIENT`                                        |
| Владелец отказался                  | `signing_status = REJECTED_BY_OWNER`                                         |
| Истек срок подписи                  | `signing_status = SIGNING_EXPIRED`                                           |
| Документ передан в архив            | заполнить `archived_at`, не менять два статуса                               |

Название уведомления о таймауте должно явно говорить об истечении срока подписания и не использовать неоднозначное «договор просрочен». Активация договора описывается отдельным переходом `lifecycle_status`, а не побочным эффектом любого события финальной подписи.

## Физическая модель и обратная совместимость

Оба DDL являются bootstrap-скриптами для пустой БД, поэтому в них сразу фиксируется целевая структура без временного сохранения старого `contract_status_enum`. Порядок определения объектов:

1. `contract_signing_status_enum` и `contract_lifecycle_status_enum`;
2. таблица `contracts` с двумя статусами и согласованными атрибутами;
3. `contract_signing_status_history`;
4. `contract_lifecycle_status_history`;
5. индексы и ссылки на новые таблицы.

В многосхемном DDL обе истории и `contracts` остаются в схеме `contract`; `contract_id` имеет физический FK внутри контекста. Поле `changed_by_employee_id` сохраняет действующую политику межконтекстной связи. В плоском DDL связи материализуются для визуализации по тем же правилам, что и остальные cross-context связи этого файла.

Отдельная миграция старых данных не создается в этом плане. Если появится непустая БД, требующая обновления на месте, для нее нужен отдельный migration-план с таблицей маппинга старого `status` в две оси и правилами обработки неоднозначных значений.

## Проверка

### Семантическая сверка

- Все девять значений `contract_signing_status_enum` одинаковы в концептуальной модели, ERD и обоих DDL.
- Все пять значений `contract_lifecycle_status_enum` одинаковы в концептуальной модели, ERD и обоих DDL.
- `EXPIRED` нигде не обозначает таймаут подписания или просрочку оплаты.
- Финансовые состояния не записываются в поля договора.
- UC, INT и регламент интеграций используют один и тот же маппинг событий ЭДО.
- Все актуальные ссылки на `contract_status_history` заменены двумя таблицами истории.
- Исторические источники, оставленные без изменения, явно исключены из нормативной сверки.

### Проверка DDL

Каждый DDL исполняется отдельно в чистой временной PostgreSQL БД с `ON_ERROR_STOP`. Проверки каталога подтверждают:

- наличие двух новых enum и точный порядок их значений;
- отсутствие `contract_status_enum` и `contracts.status`;
- наличие `signing_status`, `lifecycle_status`, `document_file_ref`, `client_signed_at`, `owner_signed_at`, `archived_at`;
- наличие двух таблиц истории с правильными типами `old_status` и `new_status`;
- отсутствие `contract_status_history`;
- наличие внутриконтекстного FK от каждой истории к `contracts`;
- успешный rollback или удаление только специально созданных временных БД после проверки.

Если локальная PostgreSQL недоступна, отсутствие исполнения DDL фиксируется как незакрытый критерий, а не заменяется только визуальным ревью.

## Определение «готово»

- [ ] Полный аудит нормативных TO-BE-упоминаний договора сохранен в рабочем описании изменения или PR.
- [ ] Концептуальная модель содержит две оси, точные enum, атрибуты и инварианты.
- [ ] UC-8.1, UC-8.2 и UC-8.8 используют утвержденный маппинг и не превращают оплату в статус договора.
- [ ] INT-012, INT-014 и INT-015 однозначно сопоставляют события ЭДО с `signing_status`, датами, файлом и `archived_at`.
- [ ] Интеграционный регламент не смешивает таймаут подписания с окончанием действия договора.
- [ ] ERD обновлена во всех представлениях и больше не содержит единый `contract_status_enum`.
- [ ] Многосхемный и плоский DDL содержат одинаковую контрактную модель с учетом различий в cross-context FK.
- [ ] Оба DDL успешно выполнены в отдельных чистых временных БД и проверены запросами к системному каталогу.

## Риски и зависимости

- `UNDER_REVIEW` применим только при реальном внутреннем согласовании; его нельзя автоматически вставлять во все маршруты.
- Для ФЛ и ЮЛ различается обязательность подписи владельца, поэтому общий `CHECK` на `owner_signed_at IS NOT NULL` для любого `SIGNED` будет ошибочным без отдельного признака маршрута.
- Договор может быть подписан, но еще не активен из-за будущей даты начала или другого условия; UC и уведомления не должны считать эти события синонимами.
- Старый `EXPIRED` неоднозначен. Bootstrap-DDL можно заменить напрямую, но миграция непустых данных потребует ручной классификации на `SIGNING_EXPIRED`, lifecycle `EXPIRED` или финансовую просрочку.
- Плоский DDL нужен ChartDB, а многосхемный DDL отражает архитектуру. Их различия по FK сохраняются, но enum, колонки и имена таблиц истории должны совпадать.
- Изображения и импортированные материалы нельзя автоматически считать источником истины. Производный визуальный asset обновляется только вместе с редактируемым исходником и по документированному процессу.
- В integration requirements уже используются групповые повторяющиеся идентификаторы `INT-014` и `INT-015`. Их перенумерация не входит в эту задачу и не должна выполняться попутно.
