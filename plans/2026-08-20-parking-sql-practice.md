# План: SQL-практика на реальной ERD парковки

**Дата:** 2026-08-20

**Статус:** черновик для совместного ревью

**Ветка:** `feature/sql-practice`
**Задача:** безопасно развернуть на внешнем PostgreSQL воспроизводимую учебную БД по актуальной ERD парковки и подготовить каталог заданий без готовых SQL-решений.

## Контекст

Основы SQL пройдены. Следующий шаг учебного плана — закрепить навык на предметной области парковки, используя существующую ERD проекта вместо отдельной упрощенной модели.

PostgreSQL уже работает в Docker на внешнем сервере. Локальный агент подключается к серверу по SSH и передает SQL-файлы через стандартный ввод в `docker exec -i ... psql`. Порт PostgreSQL не публикуется в интернет, а файлы репозитория не копируются в контейнер.

Практика подготавливается в таком порядке:

1. Проверить готовность согласованного канонического DDL как входа в работу.
2. Согласовать границы первой итерации и матрицу из 15 заданий.
3. Определить детерминированные профили синтетических данных.
4. Создать безопасные сценарии создания, наполнения, проверки и сброса учебной БД.
5. Через SSH и `docker exec` создать изолированную БД на внешнем PostgreSQL.
6. Загрузить структуру и данные, выполнить автоматические проверки.
7. Создать каталог заданий, проверочные метаданные и отдельные пустые SQL-файлы.

Самостоятельное выполнение заданий и ревью пользовательских запросов являются отдельным процессом и не входят в этот план или его Definition of Done.

## Зачем именно так

Цель подготовки — не получить еще один готовый набор SQL, а создать воспроизводимую учебную среду, в которой бизнес-вопрос можно перевести в модель данных, запрос и объективно проверяемый результат.

Полная ERD остается основой структуры и связей. Наполнение развивается через два детерминированных профиля: базовый корректный набор и контролируемые аномалии для задач по качеству данных. Это сохраняет реальную модель, но не смешивает корректные данные с учебными нарушениями без явной маркировки.

Готовые SQL-решения заранее не создаются. Проверяемость обеспечивается метаданными результата: ожидаемыми именами колонок, количеством строк и контрольной суммой канонически сериализованного результата с явно заданной сортировкой. Эти метаданные не раскрывают способ построения запроса.

## Цель

Подготовить воспроизводимый учебный контур, в котором:

- отдельная PostgreSQL БД безопасно создается на внешнем сервере через SSH и `docker exec`;
- структура соответствует согласованной физической модели модульного монолита;
- синтетические данные повторяемо загружаются и проверяются;
- опубликованы 15 заданий без SQL-решений и отдельные пустые файлы для запросов;
- для каждого задания существует объективный, не раскрывающий решение критерий проверки.

## Источники и их приоритет

Источники используются в следующем порядке:

1. `sql/database/postgresql-bootstrap.sql` — единственный канонический исполняемый DDL для пустой PostgreSQL после завершения архитектурных планов-предпосылок.
2. `docs/architecture/database/erd/erd-normalized-er-model.md` — семантика сущностей, атрибутов, связей и бизнес-инвариантов.
3. `docs/artifacts/conceptual-model-with-attributes.md`, UC и `docs/specs/integration/integration-requirements.md` — бизнес-смысл жизненных циклов и интеграций.
4. `sql/database/chartdb-postgresql-erd-normalized.sql` — производный многосхемный visual-only экспорт для ChartDB, не источник для развертывания.
5. `sql/database/chartdb-postgresql-erd-normalized-public.sql` — производный плоский visual-only экспорт для ChartDB, не источник для развертывания.
6. `docs/architecture/database/erd/data-dictionary.md` — вспомогательный импортированный материал, не канонический источник.
7. [Бесплатный курс Hexlet «Основы SQL»](https://ru.hexlet.io/programs/sql-basics-free) — жесткая граница допустимых SQL-конструкций первой итерации.
8. Практико-ориентированный план развития SA в соседнем репозитории `systems-analyst-db` — дополнительный источник учебных результатов; перед формированием каталога фиксируются путь и commit SHA, а его содержание не расширяет границу курса Hexlet.

Если источники расходятся, развертывание блокируется до согласования. Нельзя молча исправлять DDL только в `sql/practice/` и создавать параллельную модель. Сначала должны быть синхронизированы канонический `postgresql-bootstrap.sql`, ERD и производные ChartDB-экспорты.

## Архитектурные предпосылки

Исправление статусов договора и согласование правил целостности модульного монолита вынесены в отдельные планы:

- [единая модель состояний договора](2026-08-21-contract-status-model.md);
- [целостность данных модульного монолита](2026-08-21-modular-monolith-data-integrity.md).

Они не выполняются в рамках этого плана. Развертывание начинается только после полного завершения обоих планов, создания `sql/database/postgresql-bootstrap.sql` и его успешной структурной проверки. В учебном контуре без backend файл `verify-data.sql` дополнительно проверяет логические ссылки и прикладные инварианты после загрузки данных.

Планы выполняются последовательно: сначала единая модель состояний договора, затем целостность данных модульного монолита и только после этого развертывание SQL-практики. Второй архитектурный план выполняет финальную сверку ERD и DDL уже после изменения договорной модели.

## Scope

Входит:

- read-only аудит версии PostgreSQL, контейнера, текущих БД и доступных ресурсов;
- проверка готовности утвержденной версии канонического `postgresql-bootstrap.sql` до первой записи;
- подключение к внешнему серверу по SSH с проверкой host key;
- выполнение `psql` внутри существующего PostgreSQL-контейнера через `docker exec -i`;
- создание отдельной БД `parking_sql_practice` и выделенных ролей владельца и ученика;
- воспроизводимое создание структуры на основе канонического `postgresql-bootstrap.sql`;
- детерминированные профили `base` и `quality` с синтетическими данными;
- автоматические проверки схемы, данных и логических межмодульных ссылок;
- каталог ровно из 15 заданий без SQL-решений;
- отдельный пустой SQL-файл и проверочные метаданные для каждого задания;
- документация создания, загрузки, сброса и проверки учебной БД;
- трассировка реализованных артефактов и ретро после завершения плана.

Не входит:

- изменение `docs/specs/`, ERD, архитектурных решений или канонического DDL;
- production-миграции и использование рабочей БД;
- публикация PostgreSQL-порта в интернет;
- хранение SSH-ключей, паролей и заполненного `.env` в репозитории;
- реализация backend, UI или Application Service;
- написание решений в пользовательских SQL-файлах;
- самостоятельное выполнение заданий пользователем;
- ревью, исправление или оценка пользовательских запросов.

## Границы первой итерации

Первая итерация содержит ровно 15 read-only заданий в пределах программы Hexlet:

| Группа                                         | Количество |
| ---------------------------------------------- | ---------- |
| Проекция колонок и псевдонимы                  | 2          |
| `WHERE`, сравнения, даты и `NULL`              | 3          |
| `LIKE`, `ILIKE` и `SIMILAR TO`                 | 2          |
| `AND`, `OR`, `BETWEEN` и `IN`                  | 2          |
| `ORDER BY`, `NULLS FIRST/LAST`, `LIMIT/OFFSET` | 2          |
| `DISTINCT` и `DISTINCT ON`                     | 1          |
| Агрегаты, `GROUP BY` и `HAVING`                | 3          |

В первой итерации запрещены `JOIN`, подзапросы, `CTE`, оконные функции, `EXPLAIN` и задания на индексы. Изученные в курсе DDL, DML и транзакции откладываются: роль ученика остается read-only, а общий эталонный набор данных не должен изменяться во время решения задач.

Бизнес-вопросы выбираются из направлений загрузки парковки, бронирований, договоров, платежей, доступа и качества данных, но каждое задание решается по одной таблице. Новое направление добавляется только заменой существующего задания, а не расширением первой итерации.

## Формат каталога заданий

Для каждой задачи фиксируются:

| Поле                   | Содержание                                                        |
| ---------------------- | ----------------------------------------------------------------- |
| ID                     | Стабильный номер задания                                          |
| Бизнес-вопрос          | Что нужно узнать или проверить                                    |
| Аналитическая ценность | Какое решение поддерживает результат                              |
| Контекст ERD           | Какая таблица и какие атрибуты участвуют                          |
| Проверяемый навык      | Одна или несколько конструкций из утвержденной матрицы            |
| Профиль данных         | `base` или `quality`                                              |
| Требования к данным    | Какие состояния и пограничные случаи нужны                        |
| Форма результата       | Ожидаемые имена колонок, порядок сортировки и уровень детализации |
| Критерий проверки      | Количество строк и SHA-256 канонического CSV-результата           |

После утверждения каталога для каждого задания создается отдельный пустой файл вида `001-occupancy-by-sector.sql`. Файл содержит только номер, формулировку задачи, ожидаемую форму результата и место для пользовательского запроса.

## Детерминированные данные

Каждый профиль данных имеет манифест со следующими полями:

- версия набора и commit SHA схемы;
- фиксированный `as_of` с часовым поясом `Europe/Moscow`;
- точное количество строк по таблицам;
- стабильные диапазоны идентификаторов;
- перечень покрываемых статусов и сценариев;
- фиксированный seed генератора, если используется генерация;
- ожидаемые результаты `verify-data.sql`;
- для `quality` — точный перечень намеренно внесенных нарушений.

Базовый профиль содержит только корректные состояния и как минимум по одному примеру каждого применимого статуса. Профиль `quality` накладывает контролируемые аномалии поверх базового набора.

## Подключение и выполнение через SSH и Docker

Единственный поддерживаемый путь записи:

```text
локальный SQL-файл
  → stdin команды ssh
  → docker exec -i <postgres-container>
  → psql -X -v ON_ERROR_STOP=1 --single-transaction
  → parking_sql_practice
```

Файл остается в локальном репозитории и передается в контейнер потоком. Временная копия DDL на сервере или внутри контейнера не создается.

В `.env.example` фиксируются только имена переменных без значений:

- `PARKING_SQL_SSH_HOST`;
- `PARKING_SQL_SSH_PORT`;
- `PARKING_SQL_SSH_USER`;
- `PARKING_SQL_SSH_KEY_PATH`;
- `PARKING_SQL_PG_CONTAINER`;
- `PARKING_SQL_PG_ADMIN_USER`;
- `PARKING_SQL_DATABASE` со строго допустимым значением `parking_sql_practice`;
- `PARKING_SQL_OWNER_ROLE`;
- `PARKING_SQL_STUDENT_ROLE`.

Пароль PostgreSQL не передается в аргументах команд и не выводится в лог. Используется локальная аутентификация, уже настроенная внутри контейнера, либо секреты контейнера без их извлечения агентом.

При первом SSH-подключении пользователь сверяет fingerprint host key по независимому каналу. Отключать `StrictHostKeyChecking` запрещено.

## Предохранители и восстановление

До любой записи сценарий обязан проверить:

- SSH host key и имя удаленного хоста;
- точное имя PostgreSQL-контейнера;
- `SHOW server_version`, `SHOW TimeZone` и доступность требуемых расширений;
- что целевая БД называется строго `parking_sql_practice`;
- что роль ученика не имеет прав создания и удаления БД или изменения учебных данных;
- что существующая БД либо отсутствует, либо содержит служебный маркер этого проекта и ожидаемую версию набора данных.

Сброс разрешен только при одновременном выполнении двух условий:

1. имя БД равно `parking_sql_practice`;
2. в БД существует маркер `project_slug = 'sab-win-26-parking-sql-practice'`.

При несовпадении хотя бы одной проверки сценарий завершается без изменений. Нельзя принимать произвольное имя БД для обхода защиты.

Все данные синтетические, поэтому восстановление выполняется полным пересозданием БД из версионированных DDL и seed-файлов. Готовность сброса подтверждается циклом `create → load → verify → reset → create → load → verify` с одинаковыми контрольными результатами.

## Предлагаемая структура будущих файлов

```text
sql/practice/
├── readme.md
├── .env.example
├── setup/
│   ├── create-database.sh
│   ├── load-schema.sh
│   ├── load-seed.sh
│   ├── reset-database.sh
│   ├── verify-schema.sql
│   ├── verify-data.sql
│   ├── seed-base.sql
│   ├── seed-quality.sql
│   └── dataset-manifest.md
├── tasks/
│   ├── query-catalog.md
│   └── expected-results.json
└── queries/
    ├── 001-<task-name>.sql
    ├── 002-<task-name>.sql
    └── ...
```

Канонический DDL не копируется в `sql/practice/`. `load-schema.sh` передает `sql/database/postgresql-bootstrap.sql` по SSH в `docker exec -i ... psql`. Создание самой БД выполняется отдельно, поскольку `CREATE DATABASE` нельзя включить в ту же транзакцию, что и создание таблиц.

## Риски и зависимости

- Текущие ChartDB-экспорты отстают от согласованной модели договора и не должны использоваться для развертывания; SQL-практика ожидает завершенный `postgresql-bootstrap.sql`.
- Межконтекстные логические ссылки не закреплены физическими `FOREIGN KEY`; для учебного контура их проверяет `verify-data.sql`.
- Сценарии `UC-8.1` и `UC-8.8` смешивают статусы договора и оплаты; их синхронизация выполняется по отдельному плану-предпосылке до развертывания.
- DDL неидемпотентен, поэтому повторяемость обеспечивается пересозданием строго выделенной БД, а не повторным запуском поверх частично созданной схемы.
- Отказ от `JOIN` в первой итерации ограничивает каждое задание одной таблицей; межмодульные вопросы откладываются до следующего учебного уровня.
- Проверочные контрольные суммы требуют канонического порядка строк и фиксированного формата CSV, иначе одинаковые результаты дадут разные хеши.
