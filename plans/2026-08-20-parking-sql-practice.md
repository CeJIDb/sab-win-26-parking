# План: SQL-практика на реальной ERD парковки

**Дата:** 2026-08-20  
**Статус:** черновик для совместного ревью  
**Ветка:** `feature/sql-practice`  
**Задача:** подготовить учебную PostgreSQL БД на реальной ERD парковки и организовать практику бизнес- и системно-аналитических SQL-запросов без готовых решений.

## Контекст

Основы SQL пройдены. Следующий шаг учебного плана — закрепить навык на предметной области парковки, используя существующую ERD проекта вместо отдельной упрощенной модели.

PostgreSQL уже работает в Docker на внешнем сервере. Доступ к серверу возможен по SSH. Параметры подключения будут переданы позже через локальный `.env` в согласованном формате. На этапе планирования подключаться к серверу и создавать конфигурационные файлы не нужно.

Практика строится в таком порядке:

1. Совместно сформулировать полезные бизнес- и системно-аналитические вопросы.
2. Определить, какие данные нужны для получения содержательных ответов.
3. Подготовить учебную БД и синтетическое наполнение.
4. Создать каталог заданий и отдельные пустые SQL-файлы.
5. Пользователь самостоятельно пишет запросы.
6. Агент проводит ревью только после явной просьбы пользователя.

## Зачем именно так

Цель практики — не получить еще один готовый набор SQL, а научиться переводить бизнес-вопрос в модель данных, запрос и проверяемый результат.

Полная ERD остается источником структуры и связей. Наполнение можно развивать поэтапно: сначала добавить данные, необходимые для согласованного набора задач, затем расширять домены вместе со сложностью запросов. Это позволяет не генерировать данные, которые пока не участвуют в обучении, и при этом не подменять реальную модель упрощенной схемой.

Готовые решения заранее не создаются. Пустые SQL-файлы принадлежат пользователю: агент не заполняет и не переписывает их без отдельной просьбы.

## Цель

Создать воспроизводимый учебный контур, в котором пользователь может подключиться к PostgreSQL, изучить реальную ERD парковки, самостоятельно решить согласованные задачи и получить ревью запросов с точки зрения SQL, бизнеса и системного анализа.

## Источники истины

- `docs/architecture/database/erd/erd-normalized-er-model.md` — каноническая ERD;
- `docs/architecture/database/erd/data-dictionary.md` — словарь данных;
- `sql/database/chartdb-postgresql-erd-normalized.sql` — многосхемный PostgreSQL DDL;
- `sql/database/chartdb-postgresql-erd-normalized-public.sql` — плоский DDL для визуализации;
- `docs/architecture/ddd/ddd-bounded-contexts.md` — границы доменных контекстов;
- практико-ориентированный план развития SA в соседнем репозитории `systems-analyst-db` — учебные результаты по SQL.

Если ЭДО меняет ERD, статусы договора или DDL, перед развертыванием БД ветка должна получить актуальные изменения из `main` после завершения и слияния ЭДО. Формировать каталог запросов можно до этого.

## Принципы практики

- Использовать реальную ERD целиком, не создавать параллельную упрощенную модель.
- Начинать с бизнес-вопроса, а не с SQL-конструкции.
- Для каждой задачи фиксировать аналитическую ценность и ожидаемую форму результата.
- Наполнять домены данными по потребностям согласованных задач.
- Использовать только синтетические данные без реальных персональных и платежных сведений.
- Не хранить секреты и параметры реального подключения в Git.
- Не публиковать готовые решения до самостоятельной попытки пользователя.
- Проводить ревью запросов только по явной просьбе пользователя.
- Не изменять пользовательский SQL во время ревью без разрешения; сначала давать замечания и варианты улучшения.

## Scope

Входит:

- аудит пригодности текущего DDL для запуска в PostgreSQL;
- безопасное подключение к PostgreSQL на внешнем сервере через SSH;
- отдельная учебная БД или другой изолированный контур, согласованный до развертывания;
- воспроизводимое создание структуры на основе канонической ERD;
- синтетическое наполнение, поддерживающее согласованные бизнес-сценарии;
- каталог задач без SQL-решений;
- отдельный пустой SQL-файл для каждой задачи;
- самостоятельное выполнение запросов пользователем;
- ревью по запросу пользователя;
- документация запуска, сброса и проверки данных;
- трассировка изменений и ретро после завершения плана.

Не входит:

- изменение `docs/specs/` без отдельного разрешения;
- изменение ERD только ради упрощения учебных запросов;
- production-миграции и использование рабочей БД;
- хранение SSH-ключей, паролей и заполненного `.env` в репозитории;
- реализация backend или UI;
- автоматическая генерация решений за пользователя;
- ревью или исправление пользовательских запросов без его просьбы.

## Сначала определить полезные вопросы

До создания данных и SQL-файлов нужно совместно выбрать задачи из нескольких аналитических направлений:

- загрузка парковки, занятость мест и использование секторов;
- спрос по времени, длительность сессий и оборачиваемость мест;
- воронка бронирований, отмены и неявки;
- начисления, оплаты, возвраты и задолженность;
- клиенты, автомобили, договоры и тарифы;
- въезды, выезды, решения СКУД и ручные проверки;
- уведомления, ошибки доставки и обращения клиентов;
- качество данных, нарушенные инварианты и логические междоменные связи;
- сверка операционных данных между бронированием, сессией, счетом и платежом.

Окончательный перечень не фиксируется этим планом заранее. Он создается в диалоге и утверждается пользователем до проектирования наполнения.

## Формат будущего каталога задач

Для каждой задачи нужно зафиксировать:

| Поле                   | Содержание                                              |
| ---------------------- | ------------------------------------------------------- |
| ID                     | Стабильный номер задания                                |
| Бизнес-вопрос          | Что нужно узнать или проверить                          |
| Аналитическая ценность | Какое решение поддерживает результат                    |
| Контекст ERD           | Какие сущности и связи участвуют                        |
| Проверяемый навык      | Например, `JOIN`, агрегация, `CTE`, окно или `EXPLAIN`  |
| Требования к данным    | Какие состояния и пограничные случаи нужны              |
| Форма результата       | Ожидаемые колонки и уровень детализации без SQL-решения |
| Критерий проверки      | Как понять, что запрос отвечает на вопрос               |

После утверждения каталога для каждого задания создается отдельный пустой файл с именем вида `001-occupancy-by-sector.sql`. Файл содержит только номер, формулировку задачи и место для пользовательского запроса.

## Безопасно подключиться к внешнему серверу

Перед созданием `.env.example` нужно определить фактический способ доступа к PostgreSQL:

- SSH-туннель к порту PostgreSQL; или
- выполнение `psql` внутри контейнера через SSH и `docker exec`.

Предпочтителен SSH-туннель или доступ к `psql` внутри контейнера без публикации PostgreSQL в интернет.

После выбора способа подключения согласовать имена переменных. Возможный состав:

- адрес, порт и пользователь SSH;
- путь к локальному приватному SSH-ключу;
- имя контейнера PostgreSQL, если используется `docker exec`;
- внутренний адрес и порт PostgreSQL, если используется туннель;
- имя отдельной учебной БД;
- пользователь БД, пароль и режим SSL.

В репозитории может появиться только `.env.example` с пустыми значениями. Заполненный `.env` создает пользователь локально после проверки, что он исключен из Git. Значения секретов нельзя выводить в логи, документацию, ответы агента или команды с раскрытием аргументов.

До первой операции записи нужно подтвердить:

- выбран правильный сервер и контейнер;
- целевая БД предназначена только для учебы;
- существующие учебные данные можно заменить или есть отдельная новая БД;
- понятен способ восстановления после ошибки;
- разрушительные команды ограничены точным именем учебной БД или схемы.

## Предлагаемая структура будущих файлов

Структура является предметом отдельного ревью до создания:

```text
sql/practice/
├── readme.md
├── env.example
├── setup/
│   ├── create-schema.sql
│   ├── seed-data.sql
│   └── verify-data.sql
├── tasks/
│   └── query-catalog.md
└── queries/
    ├── 001-<task-name>.sql
    ├── 002-<task-name>.sql
    └── ...
```

Канонический DDL не копируется в `sql/practice/`: учебный контур должен подключать файл из `sql/database/` или документировать контролируемое преобразование, если исходный экспорт нельзя выполнить напрямую.

## Правила ревью пользовательских запросов

Для каждого переданного на ревью файла проверять:

1. Отвечает ли запрос на исходный бизнес-вопрос.
2. Верно ли выбраны сущности, связи и уровень детализации.
3. Не теряются ли строки из-за типа `JOIN` или условий с `NULL`.
4. Корректны ли агрегации, временные границы и денежные единицы.
5. Обрабатываются ли пограничные случаи из задания.
6. Читается ли запрос без устного пояснения автора.
7. Нужен ли анализ плана выполнения и индекс на текущем объеме данных.

Результат ревью сначала оформляется замечаниями. Исправленный SQL агент пишет только после отдельной просьбы пользователя.

## Риски и зависимости

- DDL предназначался в том числе для ChartDB и может потребовать проверки перед исполнением в PostgreSQL.
- Междоменные логические ссылки не всегда закреплены физическими `FOREIGN KEY`; их нужно учитывать в данных и контрольных запросах.
- Изменения ЭДО могут обновить договорный домен, поэтому финальное развертывание зависит от актуализации ветки от `main`.
- Внешний сервер требует особенно точного разделения read-only аудита и операций записи.
- Слишком большой набор задач снизит ценность самостоятельной практики; первая итерация должна быть ограничена после совместного обсуждения.
- Синтетические данные должны быть достаточно разнообразными, но объяснимыми и воспроизводимыми.

## Правила коммитов

- План хранится в ветке `feature/sql-practice`.
- Реализация начинается только после совместного ревью и утверждения плана.
- Изменения группируются по фазам и областям репозитория.
- Файлы добавляются в staging поштучно.
- Коммит и push выполняются только по явной просьбе пользователя.
