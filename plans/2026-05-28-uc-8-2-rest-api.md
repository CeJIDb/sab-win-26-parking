# Подплан Фазы 5: UC-8.2 — JSON-пример + JSON Schema (POST /api/contracts)

**Дата**: 2026-05-28
**Родительский план**: [2026-05-02-uc-8-2-edo-integration.md](2026-05-02-uc-8-2-edo-integration.md)
**Задача**: спроектировать внутренний REST-метод `POST /api/contracts` (PWA Клиента ЮЛ → Сервис Договоров) и закрепить его двумя артефактами:

- [payload-uc-8-2-create-contract.md](../docs/architecture/integration/payload-uc-8-2-create-contract.md) — каноничные примеры request body, success-response, 200-response для расширения `3а` и трех error-response (400, 422, 502).
- [schema-uc-8-2-create-contract.md](../docs/architecture/integration/schema-uc-8-2-create-contract.md) — формальная JSON Schema (draft 2020-12) с `$defs` под `ContractCreateRequest`, `ContractResponse`, `ProblemResponse`.

## Зачем именно так

Пятый deliverable из 9 в наборе UC-8.2. Опирается на UC-8.2 шаги 1–9 (синхронная часть, до возврата контроля клиенту), Sequence Фазы 4 (раскрытие участников «Клиент ЮЛ → Система») и [INT-014 / INT-015](../docs/specs/integration/integration-requirements.md). Дает «как именно клиентское приложение шлет форму и что получает в ответ» — то, что в UC описано на уровне бизнес-шагов, а в Sequence свернуто в `POST /api/contracts` одной стрелкой.

Стиль и оформление воспроизводят [payload-uc-10-2-payment.md](../docs/architecture/integration/payload-uc-10-2-payment.md) и [schema-uc-10-2-payment.md](../docs/architecture/integration/schema-uc-10-2-payment.md) — уже принятый в проекте образец JSON-артефактов: разделы «Назначение», «Контекст применения», блок примеров, семантика полей, связанные документы. Отличия: у UC-10.2 описан только response (ответ от платежного сервиса), а UC-8.2 — это пара request + response, поэтому payload расширяется секциями для request body и для каждого кода ответа.

REST-канон (нативный HTTP-код + body без обертки) вместо `{result, error}` envelope из UC-10.2 — сознательное расхождение. Обоснование зафиксировано ниже в таблице решений.

## Решения, зафиксированные перед стартом

Согласовано в чате 2026-05-28 (по ответам пользователя на 4 уточняющих вопроса перед стартом фазы) и развернуто в подплане:

| #   | Вопрос                                                                                                         | Решение                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| --- | -------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Sync-граница метода `POST /api/contracts`                                                                      | Возврат **после шага 9 UC**: внутри обработки запроса синхронно выполняются шаги 4–9 (создать черновик, подтянуть реквизиты ЮЛ, сформировать документ, отправить в ЭДО, получить `идДокументаЭДО` — шаг 7, перевести статус в `AWAITING_CLIENT_SIGNATURE` — шаг 8, опубликовать outbox-событие для уведомления — шаг 9). Ответ `201 Created` отдается с уже актуальным статусом `AWAITING_CLIENT_SIGNATURE` и заполненным `edoDocumentId`. Совпадает с Sequence Фазы 4 (`Система` делает шаги 1–9 цельным блоком до возврата контроля «Клиенту ЮЛ»). Альтернатива «вернуть `DRAFT` сразу, дальше polling» — отклонена: расходится с Sequence, требует второго endpoint'а GET (в scope Фазы 5 не входит). **Ограничения sync-границы (зафиксировать в payload-артефакте раздел «Контекст применения»):** sync-вызов внутри обработки уходит во внешнюю систему ЭДО (СБИС / Диадок) — типовая латентность 1–5 секунд, верхняя граница до 30 секунд. Серверный таймаут на вызов ЭДО — 30 секунд (после чего срабатывает расширение 7а). UI клиента должен показывать индикатор ожидания, при истечении пользовательского таймаута — опираться на async-уведомление (см. решение #17). Sync-ответ `201` не означает финального заключения договора — только успешную передачу в ЭДО и переход в `AWAITING_CLIENT_SIGNATURE`.                           |
| 2   | Envelope ответа                                                                                                | **Чистый REST**: HTTP-код несет семантику результата, body содержит ContractResponse (на 2xx) или ProblemResponse (на 4xx/5xx) **без внешней обертки** `{result, error}`. Рекомендация автора подплана с обоснованием: (a) метод `POST /api/contracts` — это внутренний контракт клиентского UI с собственным API, а не проксирование внешнего платежного провайдера (как UC-10.2-1 с ЮKassa, для которой envelope обоснован), (b) согласуется с уже принятым в проекте OpenAPI-образцом [UC-10.6](../docs/architecture/integration/openapi-uc-10-6-receipt.md) и упростит Фазу 8 (Swagger). Envelope `{result, error}` остается паттерном для адаптеров внешних провайдеров                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 3   | Объем endpoint'ов в Фазе 5                                                                                     | Только `POST /api/contracts`. `GET /api/contracts/{id}` (получение текущего состояния договора, нужный для опционального polling клиентским UI во время ожидания подписи) — опционально добавляется в Фазе 7 (Postman) и/или Фазе 8 (OpenAPI), если по ходу появится необходимость. Фокус Фазы 5 — request body и пять ответов одного endpoint'а                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| 4   | Структура файлов                                                                                               | Два файла (как в UC-10.2): один `payload-*` с примерами, один `schema-*` со схемами. Внутри `schema-*` — единая JSON Schema с `$defs.ContractCreateRequest`, `$defs.ContractResponse`, `$defs.ProblemResponse`. **Корневая часть схемы — пустой `object` без `required`/`properties`**: она ничего не валидирует сама по себе и служит контейнером для трех именованных подсхем, которые в Фазе 8 переиспользуются через `$ref` из OpenAPI yaml. Валидация конкретного примера на шаге 5.7 — через временные wrapper-схемы вида `{"$ref": "uc-8-2-create-contract.json#/$defs/<Имя>"}`, по одной на каждую сущность. **Альтернатива «корневой `oneOf` по трем `$defs`» — отклонена**: поля `ContractCreateRequest` и `ContractResponse` пересекаются (`tariffId`, `startDate`, `endDate`, `vehicleIds`, `parkingPlaceIds`), валидный пример Request будет матчить и Response (если опциональные поля Response не указаны как required) — это ломает семантику `oneOf` (matches-more-than-one или false-negative). Альтернатива «4 отдельных файла (payload-request, payload-response, schema-request, schema-response)» — тоже отклонена: больше cross-link и нагрузки на индекс при отсутствии пользы                                                                                                                                             |
| 5   | Источник `clientId` в запросе                                                                                  | `clientId` **не передается** в request body — резолвится сервером из контекста аутентифицированной сессии клиента. Конкретный механизм аутентификации PWA Клиента ЮЛ (Bearer-токен, cookie-сессия, иное) **за scope этого подплана** — фиксируется отдельным ADR по модели авторизации (в реестре ADR на 2026-05-28 такого ADR нет, требуется завести). На уровне Фазы 5 артефакты описывают только структуру payload и НЕ декларируют конкретный auth-механизм; в payload-артефакте раздел «Контекст применения» формулируется нейтрально: «`clientId` определяется сервером из контекста сессии». Аналогично UC-10.6, где идентификация клиента также вынесена из тела запроса                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| 6   | Поля request body                                                                                              | По UC-8.2 шаг 1: `startDate` (string, date), `endDate` (string, date), `tariffId` (integer), `vehicleIds` (array of integer, minItems=1), `parkingPlaceIds` (array of integer, minItems=1). Без `clientId` (см. #5). **`templateId` не передается клиентом** — определяется сервером. **Явное допущение Фазы 5**: на момент написания артефакта в системе ровно один опубликованный шаблон договора для долгосрочной аренды ЮЛ. UC-8.2 предусловие «существует опубликованный шаблон» формально означает «хотя бы один», то есть допущение «ровно один» — сужение, принятое автором подплана для упрощения payload. Допущение фиксируется отдельным абзацем в payload-артефакте (раздел «Семантика полей» → подзаголовок «Открытые вопросы»). **Открытый вопрос вынесен в Фазу 8 (OpenAPI) и Фазу 9 (регламент v2)**: если в продакшен-конфигурации шаблонов окажется больше одного — поле `templateId` придется добавить в `ContractCreateRequest` и в `ContractCreate*.xsd`; в этом случае Фаза 5 будет пересмотрена пост-фактум, запись в журнале трассировки                                                                                                                                                                                                                                                                                   |
| 7   | Поля response body (success)                                                                                   | `contractId` (integer), `contractNumber` (string, формат правила нумерации), `status` (enum из `contract_status_enum`), `startDate`/`endDate` (string, date), `tariffId` (integer), `vehicleIds`/`parkingPlaceIds` (arrays of integer), `amount` (number, рассчитан по тарифу), `currency` (string, ISO 4217), `edoDocumentId` (string, идДокументаЭДО из шага 7 UC), `createdAt` (string, date-time, ISO 8601 UTC), опц. `alreadyExists` (boolean, true только для ответа на расширение 3а)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 8   | Расширение **3а** (существующий договор по бизнес-ключу)                                                       | Ответ `200 OK` с тем же `ContractResponse` + поле `alreadyExists: true`. Мотивация: UC шаг 3а2 говорит «возвращает клиенту существующий с его текущим статусом» — это **штатный успех**, не конфликт. `409 Conflict` отклонен: семантика 409 — «состояние ресурса противоречит запросу», а здесь сервер сознательно возвращает уже существующий ресурс. Текущий статус возвращенного договора может быть любым нефинальным (`DRAFT`, `AWAITING_CLIENT_SIGNATURE`, `AWAITING_OWNER_SIGNATURE`, `ACTIVE`)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| 9   | Покрываемые HTTP-коды ошибок                                                                                   | `400 Bad Request` — невалидный JSON или нарушение типов / форматов (например, `startDate` не дата, `vehicleIds` пустой). `401 Unauthorized` — нет / просрочена / невалидна аутентификация клиента (упоминается коротко, без отдельного примера body — стандарт; конкретный механизм аутентификации — за scope, см. #5). `403 Forbidden` — клиент аутентифицирован, но не имеет роли «Клиент ЮЛ» (например, частник без активного профиля организации пытается создать договор долгосрочной аренды). Упоминается коротко, без отдельного примера body — стандарт. **Семантика 401 vs 403 разделена согласно RFC 7235 / RFC 7231: 401 = нет credentials, 403 = credentials есть, но прав не хватает.** `422 Unprocessable Entity` — бизнес-валидация: не выполнены предусловия UC-8.2 (нет реквизитов организации в профиле клиента, нет ТС, выбранные ПМ недоступны / пересекаются с другим действующим договором). `502 Bad Gateway` — расширение **7а** UC (ЭДО не подтвердил прием в течение настроенного серверного таймаута 30 с, см. #1). Без `404`/`5xx` иных: метод POST не имеет ресурсного пути со специфическими 404, прочие 5xx — общесистемные и не специфичны для UC-8.2. **Итого 7 кодов**: 200, 201, 400, 401, 403, 422, 502. Из них с body-примером в Фазе 5 покрыты 5 (200, 201, 400, 422, 502); 401 и 403 — упоминанием без body |
| 10  | Тело ошибки                                                                                                    | Унифицированный `ProblemResponse`: `error_id` (integer — HTTP-код или внутренний код), `text_error` (string — человекочитаемое сообщение), опц. `details` (object — дополнительные поля: для 422 это `field` с указанием нарушенного предусловия, например `field: "client.organization.bankRequisites"` или `field: "parkingPlaces.intersection"`; для 502 — `field: "edo.timeout"`). Имена полей `error_id` / `text_error` — для консистентности с уже существующим UC-10.2-1 (там тот же контракт ошибки)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 11  | Спецификация JSON Schema                                                                                       | Draft 2020-12 (`https://json-schema.org/draft/2020-12/schema`), как в `schema-uc-10-6-receipt.md` — актуализировано 2026-06-10, исходно был выбран 2019-09 по образцу `schema-uc-10-2-payment.md`. Включаются `$id`, `title`, `description`, `required`, `properties` с `examples` для каждой подсхемы. `additionalProperties: false` на верхнем уровне `ContractCreateRequest` и `ContractResponse` — для строгости контракта                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| 12  | Стиль именования JSON-полей                                                                                    | camelCase, как в UC-10.2 (`paymentId`, `transactionId`). Соответствие русским атрибутам UC-8.2 фиксируется в разделе «Семантика полей» payload-артефакта: `идентификатор` → `contractId`, `номерДоговора` → `contractNumber`, `датаНачала` → `startDate`, `статус` → `status` и т.д. БД-колонки (`client_signed_at`, `owner_signed_at` из ERD) в этот контракт **не попадают** — они актуализируются только после webhook'ов от ЭДО (шаги 10/12 UC), т.е. после возврата `201 Created` клиенту                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| 13  | Enum `status` в response                                                                                       | Все 11 значений `contract_status_enum` из [ERD `contracts`](../docs/architecture/database/erd/erd-normalized-er-model.md): `DRAFT`, `UNDER_REVIEW`, `AWAITING_CLIENT_SIGNATURE`, `AWAITING_OWNER_SIGNATURE`, `ACTIVE`, `SUSPENDED`, `REJECTED_BY_CLIENT`, `REJECTED_BY_OWNER`, `EXPIRED`, `TERMINATED`, `ARCHIVED`. На штатном success-пути POST возвращает `AWAITING_CLIENT_SIGNATURE`; ответ на расширение 3а — любой нефинальный статус (`DRAFT`, `UNDER_REVIEW`, `AWAITING_CLIENT_SIGNATURE`, `AWAITING_OWNER_SIGNATURE`, `ACTIVE`, `SUSPENDED`). Финальные статусы (`REJECTED_BY_CLIENT`, `REJECTED_BY_OWNER`, `EXPIRED`, `TERMINATED`, `ARCHIVED`) в ответ на `POST` приходить не должны — расширение 3а ищет «нефинальный» по бизнес-ключу. Документируем полный enum — клиент должен уметь распарсить любое валидное значение                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| 14  | Валидация артефактов                                                                                           | Прогон через `ajv-cli@5` с плагином `ajv-formats` (нужен явно, иначе `format: date` / `format: date-time` ajv не валидирует, проверка фальшиво «зеленая»). Поскольку `ajv-cli validate -s <schema> -d <data>` валидирует payload против **корневой** схемы, а у нас root — пустой контейнер (см. решение #4), валидация идет через три временные wrapper-схемы (по одной на `$defs.<Имя>`), которые подцепляют основную схему через `-r`. Команда (для request-примера): `npx -y -p ajv-cli@5 -p ajv-formats ajv --spec=draft2020 -c ajv-formats validate -s /tmp/wrapper-create-request.json -r /tmp/schema.json -d /tmp/example-request.json`. По одному прогону на каждый из 6 примеров. Если ajv по какой-то причине недоступен — fallback **локально** через [json-schema.org/tools](https://json-schema.org/tools) (CLI-варианты на Python / Go). Онлайн-валидаторы (`jsonschemavalidator.net` и т.п.) **запрещены** для этих артефактов: в примерах фигурируют шаблоны банковских реквизитов организации (UC-8.2 предусловие) — выгрузка таких payload во внешний сервис нарушает практику работы с PII. Сами `.json`-файлы в репозиторий не коммитим — примеры остаются в markdown как fenced blocks, на время прогона выгружаем в `/tmp/` и удаляем по завершении шага                                                                    |
| 15  | Запись `CHG-*` в журнал трассировки                                                                            | **Не делается** в этом подплане. Мастер-план собирает одну общую запись в Фазе 10 на весь набор 9 артефактов UC-8.2                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| 16  | Связь с [is-interaction-regulation.md](../docs/architecture/integration/is-interaction-regulation.md) (Блок 3) | В Фазе 5 регламент **не правится**. Колонка «Полезная нагрузка» в строках INT-014 относится к XML-формату ЭДО (Фаза 6), а не к JSON внутреннего REST. Внутренний REST на уровне регламента не фигурирует (Блок 3 описывает только внешние интеграции). Согласовано с решением Фазы 3 «Внутренние модульные связи в регламент не выносятся»                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| 17  | Каналы ошибки в расширении 7а (HTTP vs async-уведомление)                                                      | UC-8.2 шаг 7а описывает **два** канала: HTTP-ответ серверу sync-запроса (см. решение #9 — `502 Bad Gateway` с `ProblemResponse`) и async-уведомление клиенту по INT-015 (UC шаг 7а2). Эти каналы **не дублируют друг друга, а покрывают разные сценарии**: (a) sync `502` — основной канал, фронт PWA показывает ошибку немедленно при получении ответа; (b) async-уведомление через INT-015 — fallback на случай, когда sync-ответ не доставлен клиенту (фронт уже закрыл вкладку, сеть оборвалась после отправки запроса, mobile-агент в фоне). Чтобы не было двойной нотификации, реализация на стороне сервера: async-уведомление по UC шаг 7а2 публикуется в outbox **всегда**, но `Notification Service` дедуплицирует по `(contractId, событие)` — если фронт уже подтвердил получение sync-ответа (опционально, не в scope подплана), async-канал гасится. На уровне Фазы 5 это уточнение фиксируется в payload-артефакте отдельным абзацем под примером `502`. В UC-8.2 правки не вносим (шаг 7а2 формулирует логику корректно, конфликта нет)                                                                                                                                                                                                                                                                                            |

- `payload-*` содержит шесть блоков примеров: request body, response 201 (success), response 200 (расширение 3а — alreadyExists), response 400 (validation), response 422 (business — нарушение предусловий UC), response 502 (расширение 7а — ЭДО недоступен).

- Раздел «Связанные документы» обоих артефактов ссылается на UC-8.2, INT-014/015, Sequence Фазы 4, ERD (источник `contract_status_enum`), родительский план UC-8.2 и взаимно друг на друга. В payload — дополнительно ссылка на образец UC-10.2.

### schema-uc-8-2-create-contract.md

По образцу [schema-uc-10-2-payment.md](../docs/architecture/integration/schema-uc-10-2-payment.md):

1. **Заголовок** `# JSON Schema — UC-8.2 POST /api/contracts`.
2. **Оглавление**.
3. **Назначение** — задать формальный контракт, служить опорой для автоматической валидации, фиксировать допустимые значения статусов и обязательные поля.
4. **Контекст применения** — ссылка на payload-артефакт за примерами, спецификация draft 2020-12, область — пара request body + три варианта response body.
5. **JSON Schema** — fenced `json` блок с полной схемой:
   - `$schema` = `https://json-schema.org/draft/2020-12/schema`,
   - `$id` = `https://parking.example.com/schemas/uc-8-2-create-contract.json`,
   - `title`, `description`,
   - `$defs.ContractCreateRequest` (object, additionalProperties=false, required = все 5 полей),
   - `$defs.ContractResponse` (object, additionalProperties=false, required = 11 полей кроме `alreadyExists`),
   - `$defs.ProblemResponse` (object, additionalProperties=false на верхнем уровне; для `details` — вложенный object с `additionalProperties=true`; required = `error_id`, `text_error`),
   - **корневая часть схемы** — `type: object` без `required` и `properties` (контейнер для `$defs`, ничего не валидирует). Валидация конкретного примера делается через временную wrapper-схему `{"$ref": "uc-8-2-create-contract.json#/$defs/<Имя>"}` (см. шаг 5.7). Top-level `oneOf` сознательно не используется — обоснование в решении #4.
6. **Инварианты и ограничения** — буллиты:
   - `startDate` < `endDate`;
   - `vehicleIds` и `parkingPlaceIds` непустые;
   - `status` — одно из 11 значений `contract_status_enum`;
   - `alreadyExists: true` допустим только в `ContractResponse`;
   - `edoDocumentId` обязательный на success-пути 201 (нефинальный статус, ЭДО уже подтвердил прием).
7. **Связанные документы** — payload, Sequence, UC-8.2, INT-014, ERD (источник enum статусов), мастер-план, индекс integration/. OpenAPI Фазы 8 упоминается **текстом без ссылки** (файл еще не создан); ссылка появится в Фазе 8.

## Содержательные правила (общие для обоих артефактов)

- **Имена JSON-полей** — camelCase, фиксированный набор (см. #6 и #7 в таблице решений). Соответствие русским атрибутам UC-8.2 — в разделе «Семантика полей» payload-артефакта.
- **Даты** — `string` с `format: date` (ISO 8601 YYYY-MM-DD) для бизнес-дат `startDate`/`endDate`; `string` с `format: date-time` (ISO 8601 UTC, `Z`-суффикс) для `createdAt`. Часовой пояс ответа — UTC.
- **Денежные значения** — `amount: number` (не строка). Валюта отдельным полем `currency: string` с примером `"RUB"`. Согласовано с UC-10.2.
- **Идентификаторы** — `integer` для внутренних (`contractId`, `tariffId`, `vehicleIds[]`, `parkingPlaceIds[]`); `string` для внешних (`edoDocumentId` — это идентификатор от ЭДО, формат зависит от оператора).
- **Текст без буквы «ё»** — «черновик» вместо «чёрновик» (тут нет), «передаваемая», «семантика», «получает», «передает». Проверяется через `grep -nE 'ё|Ё'` перед коммитом.
- **Стиль fenced blocks** — `json` (lowercase), отступ 2 пробела, перенос строки в конце блока.
