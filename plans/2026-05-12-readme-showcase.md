# План: README-витрина

**Дата**: 2026-05-12
**Задача**: Переписать корневой `README.md` как витрину портфолио (hero + проблема→решение→цель + 6 highlights с TODO-местами под превью + команда как рабочий контекст + навигация по аудиториям + стек + краткий EN-summary), перенести narrative-разделы из root README в `docs/process/project-journey.md` и новый `docs/project-overview.md`, оставить `docs/readme.md` чистым оглавлением. Подплан 1 из roadmap `plans/2026-05-12-portfolio-roadmap.md`.

## Стартовое состояние и предусловия

- Ветка `docs/portfolio-roadmap` (создана в roadmap-сессии). Отдельная ветка под подплан не создается.
- В git-status на момент старта может быть `M plans/2026-05-12-portfolio-roadmap.md` и/или `?? plans/2026-05-12-simplify-scripts-package-json.md` — это правки из общей roadmap-сессии и созданный файл подплана 8. Они **не относятся к работе подплана 1** и должны быть закоммичены отдельно (через `npm run commit:atomic`) или `git stash`-нуты до старта фазы 2, чтобы не путаться в diff'е.
- Перед стартом убедиться: `git diff --name-only` показывает либо чистое дерево, либо только файлы, которые пользователь намеренно оставил вне этого подплана.
- Если в ходе работы появится дополнительный modified-файл из параллельного чата — пауза, разбор, и только потом продолжение.
- **Порядок выполнения roadmap (7 → 8 → 1 → ...) формально требует, чтобы подплан 8 был закрыт с зеленым GitHub Actions до старта подплана 1.** В этой сессии пользователь явно стартует подплан 1 раньше — это осознанное решение (см. раздел «Известные риски», пункт 1). Подплан 1 не трогает скрипты, husky-хуки и CI-конфиги, поэтому работа на одной ветке возможна; но риск конфликта в `package.json` и в текстовых файлах docs/ есть, и он зафиксирован.

## Зачем именно так

Текущий root `README.md` (189 строк) написан как описание учебного проекта: подробный «о проекте», команда, структура каталогов, история этапов. Это работает для участников курса, но не работает как витрина портфолио для RU HR/рекрутера и RU SA-интервьюера: нет первого впечатления (hero), нет цепочки проблема→решение→цель, нет визуальных хайлайтов артефактов системного анализа, нет краткой EN-аннотации.

Целевая аудитория после переписывания — внешний читатель за 30 секунд должен понять: (a) что это за проект, (b) какие 6 ключевых артефактов системного анализа здесь сделаны, (c) куда смотреть дальше в зависимости от роли (HR, SA-интервьюер, участник команды). Репозиторий позиционируется как личное портфолио владельца, поэтому повествование ведется от первого лица; команда из 5 человек упоминается как рабочий контекст (без отдельной секции «личный вклад»).

Альтернативы:

- **«Оставить все как есть + дописать сверху hero»** — отброшено: README удлинится до 250+ строк, дубль с разделами «о проекте» и «как развивался», hero потеряется в шуме.
- **«Полностью перенести narrative в docs/, root README — только hero + ссылки»** — отброшено: внешнему читателю придется кликать сразу же, чтобы понять о чем проект; витрина без содержания.
- **«Полноценный README.en.md с переключателем языка»** — отброшено: это подплан 6. В подплане 1 EN — только короткий inline-блок (~10–15 строк) в конце root README, чтобы зацепить англоязычного читателя без дублирования всей версии.

Merge-стратегия пересекающихся разделов выбрана как **вариант A** из roadmap (см. raidmap, пункт 9 «Известных рисков»):

- **«С чего начать»** (root README, раздел `## С чего начать`) и **«С чего начать»** (`docs/readme.md`, раздел `## С чего начать`) — оставить только в `docs/readme.md` как canonical; из root README дать одну ссылку «Маршрут знакомства» на якорь в `docs/readme.md`.
- **«Как развивался проект»** (root README, раздел `## Как развивался проект`) — перенести в `docs/process/project-journey.md` (он уже о развитии проекта), из root README оставить 1–2 предложения и ссылку. **Запрет: при переносе narrative подплан 1 НЕ добавляет упоминаний AI-инструментов по имени (cursor, claude, codex и т.п.).** Допустимо «с помощью AI-агента», «с помощью LLM-инструмента». Этот запрет защищает результат подплана 7 от реинжекта (см. roadmap, пункт 11 «Известных рисков»).
- **«Основные предметные области»** (root README, раздел `## Основные предметные области`) и **«Технологии репозитория»** (root README, раздел `## Технологии репозитория`) — перенести в новый `docs/project-overview.md`. `docs/readme.md` остается чистым оглавлением документации, narrative туда не подмешивается.

Превью-картинки для 6 highlights в подплане 1 пока **не вставляются** — вместо этого в каждой карточке стоит видимая TODO-метка вида `<!-- TODO: cover 1200×630 — подплан 2 -->`, плюс пустая строка для будущего `![](path)`. Подплан 2 заменит TODO-метки на реальные `![](path)`. Это решение позволяет закрыть подплан 1 независимо от подплана 2 и не блокировать друг друга.

## Цель

1. Корневой `README.md` переписан как витрина портфолио со следующей структурой:
   - Hero (1–3 строки: что это, для кого).
   - Проблема → Решение → Цель (короткий блок, 5–8 строк или маркеры; формулировка цели — verbatim из Impact Map, см. фаза 4.3).
   - **6 highlights** — карточки артефактов из roadmap (AS-IS Event Storming, Контекстная диаграмма, DDD bounded contexts, C4, DFD L1, Sequence UC-10.2), каждая с TL;DR-сноской, TODO-меткой под cover и ссылкой на основной файл.
   - Команда как рабочий контекст (5 человек, без отдельной секции «личный вклад»).
   - Навигация по аудиториям: HR / SA-интервьюер / участник команды — короткие маршруты входа.
   - Стек (краткий список технологий репозитория).
   - Wireframe (краткая ссылка на демо и инструкция пересборки — сохранить).
   - EN-summary inline (~10–15 строк).
2. `docs/process/project-journey.md` дополнен (или его существующий раздел расширен) narrative из бывшего раздела `## Как развивался проект` root README. Из root README раздел сокращен до 1–2 предложений + ссылка. **Без упоминаний AI-инструментов по имени.**
3. Создан новый файл `docs/project-overview.md` с разделами «Основные предметные области» и «Технологии репозитория». Из root README эти разделы удалены, в root README — короткая ссылка на overview (или пункт стека ссылается на overview).
4. Из root README удален отдельный раздел «С чего начать» (раздел `## С чего начать` в текущем root README); вместо него — короткое упоминание «Маршрут знакомства» со ссылкой на `docs/readme.md#с-чего-начать` (текущий якорь в `docs/readme.md` сохраняется, заголовок там не меняется).
5. Все ссылки внутри обновленного root README рабочие — проверено через `npm run lint:md-links`.
6. `npm run ci:check` — зеленый локально. После push ветки (push делает пользователь) — GitHub Actions `policy-checks`, `quality-gates`, `commitlint` зеленые.
7. Ретро написано в `docs/process/retro/2026-05-12-readme-showcase.md`.

## Scope

**Входит:**

- Полная переработка root `README.md` под структуру витрины (см. «Цель», пункт 1).
- Перенос narrative «Как развивался проект» в `docs/process/project-journey.md`.
- Создание `docs/project-overview.md` и перенос туда «Основные предметные области» + «Технологии репозитория».
- Удаление из root README раздела «С чего начать» с заменой на короткую ссылку.
- Точечные правки в `docs/readme.md` только если потребуется добавить/уточнить якорь «С чего начать», на который ссылается обновленный root README. Содержимое `docs/readme.md` по существу не меняется.
- Точечные правки в `docs/process/project-journey.md` для интеграции перенесенного narrative — не переписывание файла целиком.
- Краткий EN-summary (~10–15 строк) в конце root README.
- TODO-метки под cover в 6 карточках highlights — без реальных картинок (это подплан 2).
- Smoke-проверки: `npm run lint:md`, `npm run lint:md-links`, `npm run lint:md:fix` (или `lint:md:custom` если подплан 8 уже закрыт), `npm run ci:check`.
- Прогон GitHub Actions после push (push делает пользователь).

**Не входит:**

- Полноценный `README.en.md` с переключателем языка — это подплан 6.
- Реальные cover-картинки и `![](path)` для highlights — это подплан 2.
- TL;DR-карточки **внутри самих файлов highlights** (`docs/artifacts/as-is/event-storming-as-is.md` и т.д.) — это подплан 3. В root README в каждой карточке highlight будет своя короткая TL;DR-сноска (1–2 строки), но это **не та же самая** TL;DR, что появится в шапках файлов highlights в подплане 3.
- Demo Days как мини-кейсы — это подплан 5.
- Бейджи (badges) Shields.io, OG-image, переименование Netlify-сабдомена — это подплан 4.
- Журнал трассировки `docs/process/traceability-matrix-log.md` — подплан 1 не меняет требования, артефакты системного анализа или архитектуру (только narrative и навигацию). Журнал не обновляется. Это явно фиксируется в «Итоге».
- Правка `docs/specs/` — этот каталог не трогаем (правило CLAUDE.md).
- Изменения в `ui/`, `sql/`, `scripts/` — этот подплан про текст витрины.

## Известные риски и принятые решения

1. **Запуск подплана 1 до закрытия подплана 8.** Roadmap явно фиксирует порядок 7 → 8 → 1, причем подплан 8 закрывается **только после зеленого GitHub Actions** на ветке `docs/portfolio-roadmap` (см. roadmap, пункт 4 «Известных рисков»). Митигация: подплан 1 не трогает `package.json`, `scripts/`, husky-хуки, CI-конфиги, поэтому пересечения с подпланом 8 минимальны. **Возможный конфликт** — если подплан 8 переименовывает `lint:md:legacy` → `lint:md:custom`, и в подплане 1 в smoke-проверках указано имя скрипта. Принципиальное решение: подпланы 1 и 8 могут идти параллельно, но работа каждого подплана не должна затрагивать файлы другого (1 трогает root README + docs/process/project-journey.md + docs/project-overview.md, 8 трогает scripts/ + package.json + .husky/ + .github/workflows/). Митигация — тройная: (a) явный запрет в «Зачем именно так» и «Цели»; (b) baseline-grep в фазе 1 шаг 4; (c) повторный grep после фазы 3 (шаг 3.3) и фазы 4 (шаг 4.11).
