# План: целостность данных модульного монолита

**Дата**: 2026-08-21
**Задача**: синхронизировать архитектурные артефакты и физическую модель PostgreSQL с едиными правилами владения данными, межмодульных ссылок, чтения и транзакционной целостности модульного монолита.

## Зачем именно так

Проект уже выбрал модульный монолит в ADR-003 и одну PostgreSQL БД, но решение не доведено до единого исполняемого контракта. DDD, C4, DFD, ERD и DDL по-разному отвечают на вопросы:

- какой модуль владеет таблицей и имеет право записи;
- где заканчивается внутримодульная связь и начинается межконтекстная;
- кто проверяет логическую ссылку без физического `FOREIGN KEY`;
- когда допустим SQL view, а когда нужен публичный интерфейс модуля, snapshot или асинхронная проекция;
- где начинается и заканчивается ACID-транзакция сквозного use case;
- какие исключения из схемной изоляции допустимы.

Из-за этого текущая документация формально декларирует границы, но не позволяет однозначно проверить их в DDL и правах БД. Отдельный ADR по целостности нужен как нормативное продолжение ADR-003: ADR-003 отвечает за стиль развертывания, новый ADR отвечает за владение данными и способы сохранения целостности внутри этого стиля.

Этот план выполняется после [плана единой модели состояний договора](2026-08-21-contract-status-model.md). Оба плана меняют ERD и DDL, поэтому параллельное выполнение запрещено: аудит и исправления целостности должны опираться на уже обновленную договорную модель и завершать общую сверку физических артефактов.

## Согласованное целевое решение

1. Основной процесс использует одну PostgreSQL БД.
2. Каждый модуль, владеющий состоянием, получает собственную PostgreSQL-схему. Вспомогательная security- или technical-схема допустима только как документированное исключение с одним владельцем.
3. Модуль является единственным владельцем записи в свои таблицы. Другой модуль не получает `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE` или право обходить публичный интерфейс владельца.
4. Внутри одного модуля целостность максимально обеспечивается PostgreSQL: `FOREIGN KEY`, `CHECK`, `UNIQUE`, `NOT NULL`, exclusion constraints и подходящие индексы.
5. Между bounded contexts ссылка по умолчанию хранится как логический ID без физического `FOREIGN KEY`. Она индексируется, проверяется через публичный интерфейс владельца и обслуживается явной lifecycle-политикой.
6. Сквозной use case координирует `Application Service`: открывает одну ACID-транзакцию, вызывает публичные интерфейсы модулей и фиксирует связанные изменения. Он не владеет доменными правилами и таблицами.
7. Межмодульное чтение выполняется одним из трех способов:
   - синхронный public read contract: provider-owned read-only SQL view, если нужен актуальный снимок в той же БД;
   - immutable snapshot в агрегате-потребителе, если нужно сохранить исторически значимые входные данные;
   - проекция или materialized view, если допустима eventual consistency и чтение не участвует в критическом решении.
8. Consumer-owned view может компоновать только публичные views поставщиков. Он не должен напрямую зависеть от их базовых таблиц.
9. Физический межконтекстный `FOREIGN KEY` допустим только как зарегистрированное исключение. Для него фиксируются инвариант, причина отказа от логической ссылки, владелец, политика удаления, связность миграций и план выделения модуля.
10. Межконтекстные объекты не удаляются физически, пока на них могут существовать логические ссылки. По умолчанию применяются статус, архивирование или tombstone; проверка сирот выполняется отдельной сверкой.

## Целевая карта хранения

Начальная карта для синхронизации артефактов:

| Модуль         | Основная схема | Владеет состоянием                                                                       |
| -------------- | -------------- | ---------------------------------------------------------------------------------------- |
| `Access`       | `access`       | решения допуска, причины, ручные override, append-only аудит                             |
| `Booking`      | `booking`      | бронирования и история статусов                                                          |
| `Session`      | `session`      | парковочные сессии и фактические данные въезда/выезда                                    |
| `Tariff`       | `tariff`       | тарифы, версии, ставки и применимость                                                    |
| `Calculation`  | `calculation`  | воспроизводимые расчетные snapshots, если они сохраняются                                |
| `Payment`      | `payment`      | счета, платежи, чеки, возвраты и долги                                                   |
| `Contract`     | `contract`     | договоры, шаблоны и история состояний                                                    |
| `Customer`     | `client`       | клиенты, организации, ТС, согласия, настройки и льготные категории                       |
| `Facility`     | `facility`     | парковки, секторы, ПМ, КПП и технические статусы                                         |
| `Notification` | `notification` | уведомления, шаблоны и состояние доставки                                                |
| `Support`      | `support`      | обращения и их жизненный цикл                                                            |
| `Employee`     | `employee`     | сотрудники, роли и служебные профили                                                     |
| `Analytics`    | `report`       | производные read-модели и аналитические витрины, но не операционный аудит других модулей |

Уточнения к карте:

- `facility.access_points` остается мастер-справочником КПП у `Facility`; `Access` хранит логический `access_point_id` в своем аудите.
- `access_logs` переносится из `report` в `access`; `Analytics` получает данные через проекцию или read-only контракт.
- `benefit_categories` переносится из бесхозной `shared` в `client`; `Tariff` использует логический ID категории.
- общая `shared.outbox_events` не считается доменной моделью `Notification`. Предпочтительный вариант для MVP: outbox-таблица в схеме каждого модуля-производителя и единый read contract для worker. Альтернатива в виде общей technical-схемы допускается только если ADR явно задаст владельца, ограниченный интерфейс вставки и отсутствие произвольной общей записи.
- `auth` остается инфраструктурной security-схемой, а `pii` - security-схемой персональных данных. Для каждой таблицы этих схем в матрице владения указывается единственный модуль-владелец; они не становятся самостоятельными bounded contexts.
- `SkudAdapter`, `DisplayAdapter` и `Notification Worker` не получают собственные доменные таблицы. Локальный журнал адаптера из ADR-003 не входит в основную PostgreSQL БД.

## Выявленные расхождения

### ADR и DDD

1. [ADR-003](../docs/architecture/adr/adr-003-modular-monolith.md) оставляет стратегию схемной изоляции в `Next steps`, хотя ERD и DDL уже реализуют частичный вариант. Нет нормативного правила для FK, логических ID, удаления и сверки сирот.
2. ADR-003 перечисляет раннюю 12-модульную декомпозицию, а [DDD bounded contexts](../docs/architecture/ddd/ddd-bounded-contexts.md) содержит 15 контекстов и отдельно выделяет `Calculation`, `SkudAdapter` и `DisplayAdapter`.
3. DDD запрещает прямой доступ к таблицам другого контекста, но не формулирует исключение для read-only views из ADR-005 и ADR-006. Одновременно локальная проекция ГРЗ для `Access` описана концептуально, но отсутствует в физической модели.
4. ADR-005 и ADR-006 называют views контрактом чтения, но не определяют единообразно владельца view, его схему, grants, совместимость версий и запрет доступа consumer к базовым таблицам.
5. ADR-002 фиксирует критический инвариант `Session -> Booking`, но не связывает его с политикой логического ID, запретом hard delete и транзакционной ответственностью `Application Service`.

### C4 и DFD

6. [C4 L3](../docs/architecture/c4/c4-diagrams.md) показывает 20 сервисов, не сопоставляет их однозначно с 15 bounded contexts и описывает PostgreSQL как общий R/W для всех компонентов. Это допускает произвольную запись в чужие схемы.
7. C4 не показывает `Application Service` как слой координации use case, поэтому прямые стрелки между компонентами выглядят как разрешение обходить транзакционную рамку.
8. [DFD L1](../docs/artifacts/dfd-l1.md) повторяет старую группировку: `Billing` и `Payment` делят финансовые таблицы, `Client Profile` и `Fleet` делят клиентскую модель, а `Identity` обозначен как домен. Это расходится с актуальной DDD-картой.
9. DFD назначает `access_points` модулю `Access`, хотя DDD относит КПП к `Facility`; `access_logs` назначен `Access`, но DDL хранит его в `report`.
10. Потоки `Access -> Session`, `Session -> Booking`, `Session -> Facility` и другие команды не отделены от оркестрации через `Application Service` и не показывают общую ACID-границу там, где она обязательна.

### ERD и SQL

11. [Многосхемный DDL](../sql/database/chartdb-postgresql-erd-normalized.sql) содержит два незарегистрированных межконтекстных физических FK:
    - `contract.contracts.client_id -> client.clients.id`;
    - `tariff.tariffs.benefit_category_id -> shared.benefit_categories.id`.
12. Внутримодульная связь `facility.zone_type_vehicle_types.vehicle_type_id -> facility.vehicle_types.id` оставлена без FK, несмотря на согласованное правило физических ограничений внутри модуля.
13. В DDL отсутствуют схема `access`, схема `calculation`, заявленные `v_access_*`, `v_booking_inventory`, роли и grants. Политика чтения из ADR-005/006 не исполняется физически.
14. `shared.outbox_events` противоречит формулировке ADR-003 о записи outbox в схеме модуля-производителя и создает общую таблицу с несколькими писателями.
15. `report.access_logs` смешивает операционный журнал `Access` с производной аналитикой `Analytics`.
16. ERD местами делегирует `Application Service` проверки, которые принадлежат PostgreSQL внутри одного модуля. Например, `payments -> invoices` уже является локальным FK, а единственность активного долга может обеспечиваться partial unique index вместо конструкции `SELECT` перед `INSERT`.
17. [Плоский DDL](../sql/database/chartdb-postgresql-erd-normalized-public.sql) намеренно материализует все связи как FK для ChartDB. Это допустимо только как визуальный экспорт; он не должен называться источником физической политики или использоваться для развертывания.
18. В концептуальной модели термин `внешний ключ` используется как бизнес-ссылка. Нужна явная оговорка: концептуальная связь не требует физического PostgreSQL FK через границу контекста.

### Сценарии и требования

19. UC-12.4, UC-12.8 и UC-12.9 описывают последовательные изменения `Session`, `Booking` и `Facility`, но не называют `Application Service`, публичные команды модулей и общую транзакционную границу.
20. `fr-parking-session.md` относит оплату и чеки к контексту `Booking`, тогда как DDD и ERD отдают финансовую модель модулю `Payment`.
21. Требования и UC используют доменные ссылки, но не обязаны фиксировать физический FK. Нужно убрать только архитектурные противоречия, не менять согласованное бизнес-поведение.

## Scope

Входит:

- новый ADR о стратегии владения данными и целостности модульного монолита;
- синхронизация ADR-002/003/005/006 и индекса ADR;
- единая матрица `bounded context -> module -> schema -> tables -> write owner -> read contracts`;
- синхронизация DDD, C4 L2/L3, DFD L1 и их редактируемых/растровых источников;
- синхронизация концептуальной модели, ERD, многосхемного DDL и плоского визуального DDL;
- инвентаризация всех физических FK и логических ID с классификацией по владельцу контекста;
- физические внутримодульные ограничения и индексы;
- удаление незарегистрированных межконтекстных FK или оформление обоснованного исключения;
- реализация публичных read-only views, ролей и grants для ADR-005/006;
- выбор и фиксация физического outbox-варианта, согласованного с ADR-003;
- точечная синхронизация связанных UC и `docs/specs/` при обнаруженном архитектурном противоречии;
- проверки сирот логических ссылок, прав записи и структуры схем;
- обновление журнала трассировки, индексов документов и ретро.

Не входит:

- изменение бизнес-статусов договора: оно выполняется по отдельному плану;
- реализация backend-кода, репозиториев или самого `Application Service`;
- переход к микросервисам, отдельным БД или распределенным транзакциям;
- добавление Kafka/RabbitMQ в MVP вместо выбранного ADR-003 Outbox;
- изменение пользовательских сценариев или бизнес-требований, не вызванное архитектурным противоречием;
- миграция production-данных и развертывание на рабочем сервере;
- использование плоского ChartDB DDL как production/bootstrap DDL.

## Правила проектирования

### Классификация связей

Для каждого поля вида `*_id` заполняется реестр:

| Поле                    | Владелец source | Владелец target | Тип связи                         | Механизм                   | Индекс | Lifecycle                 | Проверка                       |
| ----------------------- | --------------- | --------------- | --------------------------------- | -------------------------- | ------ | ------------------------- | ------------------------------ |
| `<schema.table.column>` | `<module>`      | `<module>`      | внутри модуля / между контекстами | FK / logical ID / snapshot | да/нет | restrict/status/tombstone | constraint/test/reconciliation |

Классификация идет по владельцам модели, а не только по именам PostgreSQL-схем. Security-схема может принадлежать модулю, но это должно быть явно отражено в матрице.

### Ответственность `Application Service`

`Application Service` обязан:

- открыть транзакцию на границе одного use case;
- вызвать публичные команды и запросы участвующих модулей;
- передать только IDs, value objects и immutable snapshots;
- откатить все локальные изменения при ошибке до commit;
- записать outbox-события в той же транзакции, что и бизнес-изменения.

`Application Service` не должен:

- выполнять SQL к таблицам модулей напрямую;
- дублировать доменные правила переходов состояний;
- заменять локальные `CHECK`, `UNIQUE` или FK проверкой `SELECT` перед записью;
- гарантировать межконтекстную ссылочную целостность при hard delete без отдельной lifecycle-политики.

### Контракты чтения

| Потребность                              | Механизм                                       | Согласованность                    | Владелец                        |
| ---------------------------------------- | ---------------------------------------------- | ---------------------------------- | ------------------------------- |
| Решение allow/deny на КПП                | provider-owned views + составной view `Access` | актуальный снимок одной транзакции | поставщики семантики + `Access` |
| Подбор ПМ на интервал                    | `facility.v_booking_inventory`                 | актуальный снимок одной транзакции | `Facility`                      |
| Историческая цена, ГРЗ, параметры тарифа | immutable snapshot                             | состояние на момент операции       | агрегат-потребитель             |
| Отчеты и аналитика                       | проекции/materialized views/read replica       | eventual consistency               | `Analytics`                     |
| Операционный экран активных сессий       | public operational view                        | актуальное состояние               | `Session`                       |

Приложение-потребитель получает `SELECT` только на публичный view. Прямые grants на базовые таблицы поставщика запрещены. Breaking change read contract выполняется через expand-contract и совместимый период миграции.

### Реестр исключений для физических межконтекстных FK

По умолчанию реестр пуст. Каждое исключение содержит:

- source и target;
- критический инвариант;
- почему `Application Service` и lifecycle-политика недостаточны;
- кто владеет миграцией обеих сторон;
- `ON DELETE`/`ON UPDATE` политику;
- влияние на тесты и развертывание;
- способ замены FK при выделении модуля;
- ссылку на ADR и дату пересмотра.

Наличие общей PostgreSQL само по себе не является достаточным основанием для исключения.

## Определение «готово»

- [ ] ADR-009 принят и однозначно определяет границы модулей, физические ограничения, логические ID, чтение, транзакции и исключения.

- [ ] В многосхемном DDL нет незарегистрированных межконтекстных FK.

## Риски и меры

| Риск                                                              | Мера                                                                                            |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Логический ID становится сиротой после удаления master-записи     | запрет hard delete, статус/tombstone, reconciliation query и тест lifecycle                     |
| `Application Service` превращается в слой бизнес-логики           | доменные правила остаются в модулях; orchestration tests проверяют только порядок и атомарность |
| View скрывает прямую связанность со схемой поставщика             | provider-owned contract, grants только на view, expand-contract и consumer regression tests     |
| Модульный монолит остается модульным только на диаграмме          | роли БД, запрет write grants, структурные SQL-проверки и CI-контроль                            |
| Shared-схема становится обходом владения                          | удалить бесхозные объекты или дать каждому technical object одного владельца и узкий интерфейс  |
| Flat DDL случайно используют для развертывания                    | явный баннер visual-only, ссылки на канонический многосхемный DDL и проверка setup-скриптов     |
| Одновременная синхронизация многих артефактов породит новый дрейф | единая матрица владения, атомарные фазы, traceability и финальная двусторонняя сверка           |
