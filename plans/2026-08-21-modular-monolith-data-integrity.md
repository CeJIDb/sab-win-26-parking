# План: целостность данных модульного монолита

**Дата**: 2026-08-21
**Задача**: синхронизировать архитектурные артефакты и эталонную учебную модель PostgreSQL с едиными правилами владения данными, межмодульных ссылок, чтения и локальной транзакционной целостности модульного монолита.

## Зачем именно так

Проект уже выбрал модульный монолит в ADR-003 и одну PostgreSQL БД, но решение не доведено до единого исполняемого контракта. DDD, C4, DFD, ERD и DDL по-разному отвечают на вопросы:

- какой модуль владеет таблицей и имеет право записи;
- где заканчивается внутримодульная связь и начинается межконтекстная;
- кто проверяет логическую ссылку без физического `FOREIGN KEY`;
- когда допустим SQL view, а когда нужен публичный интерфейс модуля, snapshot или асинхронная проекция;
- где начинается и заканчивается ACID-транзакция сквозного use case;
- какие исключения из схемной изоляции допустимы.

Из-за этого текущая документация формально декларирует границы, но не позволяет однозначно проверить их в DDL и структурных проверках. Отдельный ADR по целостности нужен как нормативное продолжение ADR-003: ADR-003 отвечает за стиль развертывания, новый ADR отвечает за владение данными и способы сохранения целостности внутри этого стиля.

Этот план выполняется после [плана единой модели состояний договора](2026-08-21-contract-status-model.md). Оба плана меняют ERD и DDL, поэтому параллельное выполнение запрещено: аудит и исправления целостности должны опираться на уже обновленную договорную модель и завершать общую сверку физических артефактов.

Целевой DDL не является production-схемой. Он должен отражать бизнес-сущности, связи и архитектуру учебного проекта, исполняться на пустой PostgreSQL и служить входом для [плана SQL-практики](2026-08-20-parking-sql-practice.md). Production-миграции, конкурентные writers, эксплуатационная отказоустойчивость и runtime-реализация backend в нем не моделируются.

## Предусловия запуска

- План [единой модели состояний договора](2026-08-21-contract-status-model.md) завершен: все фазы `[x]`, итог актуализирован, ретро создано, а его изменения присутствуют в рабочей ветке этого плана. Его ERD и ChartDB-экспорты принимаются как семантическая входная модель, но не как финальный канонический DDL для SQL-практики.
- Пользователь в ревью 2026-08-21 явно разрешил точечные изменения перечисленных в этом плане файлов `docs/specs/` для устранения архитектурных противоречий без изменения бизнес-смысла и идентификаторов требований.
- Если хотя бы одно предусловие не выполнено, Фаза 0 остается незавершенной и работа с ERD, DDL и `docs/specs/` не начинается.

## Согласованное целевое решение

1. Основной процесс использует одну PostgreSQL БД. Эталонный bootstrap предназначен для пустой БД с синтетическими данными и SQL-практики, а не для production-развертывания.
2. Каждый модуль, владеющий состоянием, получает собственную PostgreSQL-схему. Вспомогательная security- или technical-схема допустима только как документированное исключение с одним логическим владельцем.
3. Модуль является единственным логическим владельцем записи в свои таблицы. Внутри одного процесса эта граница обеспечивается публичными интерфейсами, размещением репозиториев, ревью и статическим анализом зависимостей, а не отдельной runtime-ролью PostgreSQL на каждый модуль.
4. Целостность максимально обеспечивается понятными средствами PostgreSQL: `FOREIGN KEY`, `CHECK`, `UNIQUE`, `NOT NULL` и подходящими индексами. Стабильный межконтекстный FK допустим, если он защищает жесткий инвариант существования в общей учебной БД; каждый такой FK регистрируется вместе с lifecycle-политикой.
5. Логический ID без физического FK используется для внешних, полиморфных, исторических или намеренно слабо связанных ссылок. Он индексируется, получает явную lifecycle-политику и проверяется через `verify-data.sql` в будущем учебном контуре.
6. Сквозной локальный use case координирует `Application Service`: открывает одну ACID-транзакцию, вызывает публичные интерфейсы модулей и фиксирует связанные изменения вместе с outbox-событием. Сетевые вызовы к платежному провайдеру, ЭДО, СКУД и каналам уведомлений выполняются только после commit и не входят в PostgreSQL-транзакцию.
7. Межмодульное чтение выполняется одним из трех способов:
   - синхронный public read contract: provider-owned read-only SQL view, если нужен актуальный снимок в той же БД;
   - immutable snapshot в агрегате-потребителе, если нужно сохранить исторически значимые входные данные;
   - проекция или materialized view, если допустима eventual consistency и чтение не участвует в критическом решении.
8. Consumer-owned view может компоновать только публичные views поставщиков. Он не должен напрямую зависеть от их базовых таблиц на уровне архитектурного контракта.
9. Жесткий инвариант `Session -> Booking` обеспечивается зарегистрированным межсхемным FK `"session".parking_sessions.booking_id -> booking.bookings.id` с `ON UPDATE RESTRICT` и `ON DELETE RESTRICT`. `UNIQUE (booking_id)` не добавляется: одна бронь может иметь несколько сессий.
10. Outbox моделируется одной простой технической таблицей `integration.outbox_events`, принадлежащей инфраструктурному слою основного процесса. Worker claim/lease, retry API, `SECURITY DEFINER` функции и конкурентная обработка не входят в учебную физическую модель.
11. Сложные межтабличные правила делятся на две группы: проверяемые `verify-data.sql` на детерминированных данных и документируемые для будущей боевой реализации. Блокировки, `SERIALIZABLE`, exclusion constraints и параллельные writers в текущем плане не реализуются.
12. Межконтекстные объекты не удаляются физически, пока на них могут существовать логические ссылки. По умолчанию применяются статус, архивирование или tombstone; проверка сирот выполняется отдельной сверкой.

## Целевая карта хранения

Начальная карта для синхронизации артефактов:

| Модуль         | Основная схема | Владеет состоянием                                                                       |
| -------------- | -------------- | ---------------------------------------------------------------------------------------- |
| `Access`       | `access`       | решения допуска, причины, ручные override, append-only аудит                             |
| `Booking`      | `booking`      | бронирования и история статусов                                                          |
| `Session`      | `session`      | парковочные сессии и фактические данные въезда/выезда                                    |
| `Tariff`       | `tariff`       | тарифы, версии, ставки и применимость                                                    |
| `Calculation`  | `calculation`  | воспроизводимые расчетные snapshots, если они сохраняются                                |
| `Payment`      | `payment`      | счета, платежи, чеки, возвраты и долги                                                   |
| `Contract`     | `contract`     | договоры, шаблоны и история состояний                                                    |
| `Customer`     | `client`       | клиенты, организации, ТС, согласия, настройки и льготные категории                       |
| `Facility`     | `facility`     | парковки, секторы, ПМ, КПП и технические статусы                                         |
| `Notification` | `notification` | уведомления, шаблоны и состояние доставки                                                |
| `Support`      | `support`      | обращения и их жизненный цикл                                                            |
| `Employee`     | `employee`     | сотрудники, роли и служебные профили                                                     |
| `Analytics`    | `report`       | производные read-модели и аналитические витрины, но не операционный аудит других модулей |

Уточнения к карте:

- `facility.access_points` остается мастер-справочником КПП у `Facility`; `Access` хранит логический `access_point_id` в своем аудите.
- `access_logs` переносится из `report` в `access`; `Analytics` получает данные через проекцию или read-only контракт.
- `benefit_categories` переносится из бесхозной `shared` в `client`; `Tariff` использует логический ID категории.
- бесхозная `shared.outbox_events` заменяется простой `integration.outbox_events`. Это техническая таблица инфраструктурного слоя основного процесса, а не доменная модель `Notification`; operational API для claim/lease/retry в учебный DDL не входит.
- `auth` остается инфраструктурной security-схемой, а `pii` - security-схемой персональных данных. Для каждой таблицы этих схем в матрице владения указывается единственный модуль-владелец; они не становятся самостоятельными bounded contexts.
- `SkudAdapter`, `DisplayAdapter` и `Notification Worker` не получают собственные доменные таблицы. Локальный журнал адаптера из ADR-003 не входит в основную PostgreSQL БД.
- Отдельные runtime-роли внутренних модулей не создаются. Роли владельца учебной БД и read-only ученика относятся к последующему плану SQL-практики; ADR фиксирует логическое владение таблицами и реальные границы отдельно развернутых процессов.

## Выявленные расхождения

### ADR и DDD

1. [ADR-003](../docs/architecture/adr/adr-003-modular-monolith.md) оставляет стратегию схемной изоляции в `Next steps`, хотя ERD и DDL уже реализуют частичный вариант. Нет нормативного правила для FK, логических ID, удаления и сверки сирот.
2. ADR-003 перечисляет раннюю 12-модульную декомпозицию, а [DDD bounded contexts](../docs/architecture/ddd/ddd-bounded-contexts.md) содержит 15 контекстов и отдельно выделяет `Calculation`, `SkudAdapter` и `DisplayAdapter`.
3. DDD запрещает прямой доступ к таблицам другого контекста, но не формулирует исключение для read-only views из ADR-005 и ADR-006. Одновременно локальная проекция ГРЗ для `Access` описана концептуально, но отсутствует в физической модели.
4. ADR-005 и ADR-006 называют views контрактом чтения, но не определяют единообразно владельца view, его схему, совместимость версий и запрет прямой зависимости consumer от базовых таблиц.
5. ADR-002 фиксирует критический инвариант `Session -> Booking`, но не связывает его с политикой логического ID, запретом hard delete и транзакционной ответственностью `Application Service`.

### C4 и DFD

6. [C4 L3](../docs/architecture/c4/c4-diagrams.md) показывает 20 сервисов, не сопоставляет их однозначно с 15 bounded contexts и описывает PostgreSQL как общий R/W для всех компонентов. Это допускает произвольную запись в чужие схемы.
7. C4 не показывает `Application Service` как слой координации use case, поэтому прямые стрелки между компонентами выглядят как разрешение обходить транзакционную рамку.
8. [DFD L1](../docs/artifacts/dfd-l1.md) повторяет старую группировку: `Billing` и `Payment` делят финансовые таблицы, `Client Profile` и `Fleet` делят клиентскую модель, а `Identity` обозначен как домен. Это расходится с актуальной DDD-картой.
9. DFD назначает `access_points` модулю `Access`, хотя DDD относит КПП к `Facility`; `access_logs` назначен `Access`, но DDL хранит его в `report`.
10. Потоки `Access -> Session`, `Session -> Booking`, `Session -> Facility` и другие команды не отделены от оркестрации через `Application Service` и не показывают общую ACID-границу там, где она обязательна.

### ERD и SQL

11. [Многосхемный DDL](../sql/database/chartdb-postgresql-erd-normalized.sql) содержит два неклассифицированных межконтекстных физических FK:
    - `contract.contracts.client_id -> client.clients.id`;
    - `tariff.tariffs.benefit_category_id -> shared.benefit_categories.id`.
12. Внутримодульная связь `facility.zone_type_vehicle_types.vehicle_type_id -> facility.vehicle_types.id` оставлена без FK, несмотря на согласованное правило физических ограничений внутри модуля.
13. В DDL отсутствуют схема `access`, схема `calculation`, заявленные `v_access_*` и `v_booking_inventory`. Политика чтения из ADR-005/006 не отражена в эталонной физической модели.
14. `shared.outbox_events` не имеет явного технического владельца и смешивает понятие общей инфраструктуры с бесхозной shared-схемой.
15. `report.access_logs` смешивает операционный журнал `Access` с производной аналитикой `Analytics`.
16. ERD местами делегирует `Application Service` простые проверки, которые принадлежат PostgreSQL. Например, `payments -> invoices` уже является локальным FK, а допустимая форма счета обеспечивается обычным `CHECK`; сложные межтабличные правила при этом не нужно превращать в production-механизмы учебного DDL.
17. [Плоский DDL](../sql/database/chartdb-postgresql-erd-normalized-public.sql) намеренно материализует все связи как FK для ChartDB. Это допустимо только как визуальный экспорт; он не должен называться источником физической политики или использоваться для развертывания.
18. В концептуальной модели термин `внешний ключ` используется как бизнес-ссылка. Нужна явная оговорка: концептуальная связь не требует физического PostgreSQL FK через границу контекста.

### Сценарии и требования

19. UC-12.4, UC-12.8 и UC-12.9 описывают последовательные изменения `Session`, `Booking` и `Facility`, но не называют `Application Service`, публичные команды модулей, локальную транзакционную границу и выполнение внешней команды только после commit.
20. `fr-parking-session.md` относит оплату и чеки к контексту `Booking`, тогда как DDD и ERD отдают финансовую модель модулю `Payment`.
21. Требования и UC используют доменные ссылки, но не обязаны фиксировать физический FK. Нужно убрать только архитектурные противоречия, не менять согласованное бизнес-поведение.

## Scope

Входит:

- новый ADR о стратегии владения данными и целостности модульного монолита;
- синхронизация ADR-002/003/005/006 и индекса ADR;
- единая матрица `bounded context -> module -> schema -> tables -> write owner -> read contracts`;
- синхронизация DDD, C4 L2/L3, DFD L1 и их редактируемых/растровых источников;
- синхронизация концептуальной модели, ERD, многосхемного DDL и плоского визуального DDL;
- инвентаризация всех физических FK и логических ID с классификацией по владельцу контекста;
- физические ограничения и индексы для простых структурных и строковых инвариантов;
- регистрация стабильных межконтекстных FK, включая обязательный FK `Session -> Booking`, и обоснование оставшихся логических ID;
- реализация публичных read-only views для ADR-005/006 без отдельных runtime-ролей внутренних модулей;
- фиксация простой `integration.outbox_events` без operational claim/lease/retry API;
- разделение канонического исполняемого bootstrap DDL и двух visual-only экспортов ChartDB;
- точечная синхронизация связанных UC и `docs/specs/` при обнаруженном архитектурном противоречии;
- каталоговая SQL-проверка структуры схем, constraints, индексов, views и классификации ссылок;
- минимальный PostgreSQL smoke-check в CI: развертывание пустой схемы и запуск структурной проверки;
- обновление журнала трассировки, индексов документов и ретро.

Не входит:

- изменение бизнес-статусов договора: оно выполняется по отдельному плану;
- реализация backend-кода, репозиториев или самого `Application Service`;
- переход к микросервисам, отдельным БД или распределенным транзакциям;
- добавление Kafka/RabbitMQ в MVP вместо выбранного ADR-003 Outbox;
- production-миграции, backfill, zero-downtime deployment и rollback непустой рабочей БД;
- конкурентные writers, блокировки, `SERIALIZABLE`, exclusion constraints и retry-тесты;
- отдельные runtime-роли внутренних модулей, RLS, `SECURITY DEFINER` write API и применение `GRANT`/`REVOKE` для будущей backend-роли; append-only для историй остается документированным требованием production-реализации;
- worker claim/lease, operational retry, дедупликация и фактическая отправка событий outbox;
- роли владельца учебной БД, read-only ученика, seed-профили, задания и `verify-data.sql`: это scope [плана SQL-практики](2026-08-20-parking-sql-practice.md);
- machine-readable policy manifest, генераторы матриц и автоматический cross-artifact drift-check: это scope [отдельного плана автоматизации](2026-08-21-modular-integrity-policy-automation.md);
- изменение пользовательских сценариев или бизнес-требований, не вызванное архитектурным противоречием;
- использование плоского ChartDB DDL как production/bootstrap DDL.

## Правила проектирования

### Классификация связей

Для каждого поля вида `*_id` заполняется реестр:

| Поле                    | Владелец source | Владелец target | Тип связи                         | Механизм                               | Индекс | Lifecycle                 | Проверка                    |
| ----------------------- | --------------- | --------------- | --------------------------------- | -------------------------------------- | ------ | ------------------------- | --------------------------- |
| `<schema.table.column>` | `<module>`      | `<module>`      | внутри модуля / между контекстами | FK / logical ID / polymorphic/snapshot | да/нет | restrict/status/tombstone | constraint/verify-data/docs |

Классификация идет по владельцам модели, а не только по именам PostgreSQL-схем. Security-схема может принадлежать модулю, но это должно быть явно отражено в матрице.

### Уровни обеспечения инвариантов

1. **DDL constraints**: PK, устойчивые внутренние и межсхемные FK, `NOT NULL`, простые `CHECK`, `UNIQUE` и индексы. Они защищают структуру и правила одной строки.
2. **Проверки данных**: сложные межтабличные правила, полиморфные ссылки, согласованность текущего статуса с историей, пересечение броней и другие семантические аномалии проверяются будущим `verify-data.sql` на профилях `base` и `quality`.
3. **Архитектурная документация**: конкурентная запись, блокировки, уровни изоляции, retry и компенсации описываются как требования к возможной боевой реализации, но не исполняются учебным DDL.

Обычный межсхемный FK не нарушает write ownership: он не дает чужому модулю права записи, а только защищает существование target. Логический ID выбирается по семантике ссылки, а не автоматически из-за границы bounded context.

### Ответственность `Application Service`

`Application Service` обязан:

- открыть транзакцию на границе одного use case;
- вызвать публичные команды и запросы участвующих модулей;
- передать только IDs, value objects и immutable snapshots;
- откатить все локальные изменения при ошибке до commit;
- записать outbox-события в той же транзакции, что и бизнес-изменения.

`Application Service` не должен:

- выполнять SQL к таблицам модулей напрямую;
- дублировать доменные правила переходов состояний;
- заменять локальные `CHECK`, `UNIQUE` или FK проверкой `SELECT` перед записью;
- гарантировать межконтекстную ссылочную целостность при hard delete без отдельной lifecycle-политики;
- выполнять сетевой вызов к платежному провайдеру, ЭДО, СКУД или каналу уведомлений до commit локальной транзакции.

Runtime-реализация этих правил не входит в план. ADR, DDD, C4, DFD и UC должны одинаково отделять локальный commit от последующего внешнего эффекта.

### Контракты чтения

| Потребность                              | Механизм                                       | Согласованность                    | Владелец                        |
| ---------------------------------------- | ---------------------------------------------- | ---------------------------------- | ------------------------------- |
| Решение allow/deny на КПП                | provider-owned views + составной view `Access` | актуальный снимок одной транзакции | поставщики семантики + `Access` |
| Подбор ПМ на интервал                    | `facility.v_booking_inventory`                 | актуальный снимок одной транзакции | `Facility`                      |
| Историческая цена, ГРЗ, параметры тарифа | immutable snapshot                             | состояние на момент операции       | агрегат-потребитель             |
| Отчеты и аналитика                       | проекции/materialized views/read replica       | eventual consistency               | `Analytics`                     |
| Операционный экран активных сессий       | public operational view                        | актуальное состояние               | `Session`                       |

Потребляющий модуль использует только публичный view на уровне репозитория и архитектурного контракта. Отдельные PostgreSQL-роли внутренних модулей не создаются: основной процесс работает через общий runtime principal, а граница чтения контролируется кодом и структурными проверками. Breaking change read contract выполняется согласованно в едином deployment; production expand-contract остается рекомендацией, а не частью учебного bootstrap.

### Реестр физических межконтекстных FK

Каждый физический FK через границу контекста содержит:

- source и target;
- критический инвариант;
- почему жесткий инвариант существования полезнее слабо связанного logical ID;
- кто координирует согласованное изменение обеих сторон;
- `ON DELETE`/`ON UPDATE` политику;
- влияние на тесты и развертывание;
- способ замены FK при гипотетическом выделении модуля;
- ссылку на ADR и дату пересмотра.

Обязательная первая запись реестра: `"session".parking_sessions.booking_id -> booking.bookings.id`, `ON UPDATE RESTRICT`, `ON DELETE RESTRICT`, без `UNIQUE (booking_id)`. Остальные текущие и потенциальные межсхемные FK классифицируются по тому же правилу; их не нужно автоматически удалять ради будущей микросервисной декомпозиции, которая не входит в scope проекта.
