## Зачем именно так

Корневой `README.md` сейчас открывается заголовком и lead-параграфом — без визуальных маркеров статуса проекта. Для HR/SA-интервьюера это нормально, но не считывается «с первого взгляда»: учебный это проект или нет, проходят ли проверки, есть ли где посмотреть результат. 5 shields.io-бейджей (статус, CI, последний коммит, лицензия, демо) закрывают этот «скан-уровень» за одну строку.

OG-image (1200×630) решает другую задачу: при шеринге репо в Telegram, Slack, LinkedIn, x.com сейчас показывается дефолтная карточка GitHub (аватар + название). Кастомное превью с названием проекта и подзаголовком превращает ссылку в распознаваемую визитку портфолио. Загружается через GitHub Settings → Social Preview, файл-источник `docs/assets/social-preview.png` остаётся в репо как single source of truth.

Netlify-сабдомен `boisterous-heliotrope-94df12.netlify.app` — автоматически сгенерированное имя из 2 случайных слов. Для портфолио оно создаёт ощущение «не было времени переименовать». Переименование в осмысленный сабдомен (например, `mine-parking-sab-win-26`) делает ссылку в README цитируемой.

Альтернатива «отложить брендинг до EN-расширения (подплан 6)» отброшена пользователем: badges и Netlify — это поверхностный слой без блокеров и зависимостей от других подпланов, и без них витрина выглядит недоделанной даже после подплана 1.

Альтернатива «сгенерировать OG-image скриптом в репо (HTML→PNG через Playwright)» отброшена на входе сессии: даёт воспроизводимость, но добавляет код и зависимость от Playwright в CI ради одного PNG. Пользователь делает картинку вручную (Figma/Canva/Miro), кладёт готовый файл в `docs/assets/`.

Альтернатива «выделить Netlify-переименование в отдельный подплан» отброшена: фактическая работа в репо — обновить ссылку в 2 местах, остальное делает пользователь в UI Netlify. Отдельный подплан под это нерентабелен.

## Scope

**Входит:**

- Правка корневого `README.md`: вставка блока из 5 shields.io-бейджей и HTML-комментария про OG-image.
- Создание каталога `docs/assets/` с `readme.md`-описанием каталога и приём файла `social-preview.png` от пользователя (валидация размеров, формата, веса).
- Создание `docs/process/branding-checklist.md` — процедура переименования Netlify-сабдомена.
- Документирование в `branding-checklist.md` точного списка мест в репо, где после переименования сабдомена надо обновить ссылку (см. ниже «Список ссылок на Netlify в репо»).
- Обновление индекса `docs/process/readme.md` — добавление ссылки на `branding-checklist.md` в раздел «Содержание».
- Фактическая правка ссылок в репо после переименования (если пользователь успел переименовать сабдомен в рамках этой же сессии). Если не успел — фаза остаётся незакрытой, в `## Итог` фиксируется передача дальше.
- Фактическая верификация бейджей (открытие каждого raw-URL в браузере или `curl -I` с проверкой `200 OK` и непустого SVG-ответа) и OG-image (после загрузки в GitHub Settings — `metatags.io` или GitHub в инкогнито).
- Локальные прогоны `npm run lint:md`, `npm run lint:md-links`, `npm run ci:check`.
- Обновление ячейки подплана 4 в таблице roadmap [plans/2026-05-12-portfolio-roadmap.md](2026-05-12-portfolio-roadmap.md) и Фазы 8 — после написания ретро.
- Ретро `docs/process/retro/2026-05-13-portfolio-branding.md`.

**Не входит:**

- Генерация OG-image программно (Playwright/HTML→PNG, Figma API и т.п.) — пользователь готовит картинку вручную. Связанный со скриптогенерацией код в репо не появляется.
- Правка ссылок на Netlify в **исторических артефактах** — `docs/interviews/plans/interview-plan-7-2026-03-04-v01.md` и `docs/interviews/protocols/interview-protocol-7-2026-03-04-v01.md`. Это документы, привязанные к конкретной дате (2026-03-04); URL в них — то, что было на момент интервью. Подмена URL в исторических протоколах исказила бы факт. См. «Принятые решения» ниже.
- Создание GitHub Pages-альтернативы или ребалансировка между Netlify и Pages — Netlify остаётся, меняется только сабдомен.
- Подключение custom domain (sab-mine-parking.dev и т.п.) — только переименование автогенерированного `*.netlify.app`-сабдомена.
- Загрузка OG-image через GitHub Settings — это ручное действие пользователя; в подплане только фиксируем процедуру в `branding-checklist.md`. Сам факт того, что превью отображается, не проверяется в CI.
- Дополнительные бейджи (Conventional Commits, Prettier, markdownlint, Husky) — отброшены на входе, базовый набор зафиксирован.
- Брендинг wireframe (`ui/`) — favicon, footer, мета-теги в собранном HTML. Скоуп — README и репо-уровень.
- Журнал трассировки — подплан затрагивает только витринные тексты (`README.md`, `docs/process/branding-checklist.md`) и навигационные ссылки; требования, артефакты, архитектурные решения не меняются. Журнал не трогаем, факт зафиксируется в `## Итог`.

## Блок shields.io-бейджей в README

Место вставки — сразу после H1, **до** строки `Учебный проект курса …`. Между H1 и блоком бейджей — пустая строка; между блоком бейджей и lead-параграфом — пустая строка.

Все 5 бейджей идут в одной строке через пробел. URL'ы:

```markdown
![Status: учебный проект](https://img.shields.io/badge/status-%D1%83%D1%87%D0%B5%D0%B1%D0%BD%D1%8B%D0%B9%20%D0%BF%D1%80%D0%BE%D0%B5%D0%BA%D1%82-blue)
[![CI](https://github.com/CeJIDb/sab-win-26-parking/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/CeJIDb/sab-win-26-parking/actions/workflows/ci.yml)
![Last commit](https://img.shields.io/github/last-commit/CeJIDb/sab-win-26-parking)
[![License: ISC](https://img.shields.io/badge/license-ISC-green)](LICENSE)
[![Demo](https://img.shields.io/badge/demo-Netlify-success)](https://boisterous-heliotrope-94df12.netlify.app/)
```

Правила:

- **Порядок строго:** статус → CI → последний коммит → лицензия → демо. Слева направо: «что это», «исправно ли», «живой ли проект», «как использовать», «где посмотреть».
- **Статус** — статичный бейдж со значением «учебный проект». Кириллица в path сегменте shields.io должна быть URL-encoded (`%D1%83%D1%87%D0%B5%D0%B1%D0%BD%D1%8B%D0%B9` = «учебный», `%20` = пробел, `%D0%BF%D1%80%D0%BE%D0%B5%D0%BA%D1%82` = «проект») — иначе бейдж рендерится как «invalid». Русский текст для глаз — в alt атрибуте `Status: учебный проект`. Не «учебный проект курса …» — длинный текст разрывает строку.
- **CI** — динамический badge от GitHub Actions, ссылка на ветку `main`. На ветке `docs/portfolio-roadmap` бейдж покажет статус последнего прогона на `main` — это корректно, портфолио на витрине показывает «здоровье» основной ветки.
- **Last commit** — динамический shields.io от GitHub API; работает без токена.
- **License** — статичный, ссылка на `LICENSE` (файл в репо, лицензия ISC уже зафиксирована).
- **Demo** — ссылка на Netlify. **На момент создания плана URL `boisterous-heliotrope-94df12.netlify.app`** — после переименования сабдомена (если оно произойдёт в рамках этой же сессии или позже) ссылка обновляется в той же фазе, что и остальные Netlify-ссылки в репо.
- **Не использовать букву «е с точками»** — проверяется при сохранении.
- После сохранения README запустится `format-on-write.mjs` (Prettier) — визуально проверить, что блок бейджей остался одной логической строкой.
- **Не дублировать** ссылку «Репозиторий: CeJIDb/sab-win-26-parking» — она остаётся как есть после lead-параграфа.
- **Фактическая проверка рендера.** После вставки блока — для каждого из 5 бейджей открыть URL в браузере либо `curl -sI <url> | head -1`: должен быть `HTTP/... 200` и SVG-ответ. На бейдже статуса дополнительно проверить, что текст «учебный проект» отображается кириллицей, а не как `%D1%83%D1%87...` или «invalid».

## OG-image: `docs/assets/social-preview.png`

Каталог `docs/assets/` создаётся в рамках этого плана (сейчас не существует — `ls docs/assets/` возвращает ошибку «No such file or directory»). Вместе с каталогом создаётся `docs/assets/readme.md` — короткое описание назначения (хранилище бинарных ассетов витрины: OG-image и т.п.) и список текущих файлов. Это согласовано с паттерном репо: у `docs/specs/`, `docs/architecture/`, `docs/process/`, `docs/interviews/`, `docs/demo-days/` есть свой `readme.md`.

Требования к файлу:

- **Размер:** 1280×640 или больше, рекомендуется 1200×630 (GitHub Social Preview crop).
- **Формат:** PNG (опц. JPG, но PNG предпочтительнее ради чёткости текста).
- **Вес:** до 1 МБ (лимит GitHub для Social Preview). При весе > 1 МБ — пересохранить с меньшим качеством или уменьшить разрешение до 1200×630.
- **Содержание (рекомендация, не догма):** название проекта («Цифровая платформа парковки» / «Mine Parking — SA Portfolio»), краткий подзаголовок (одна строка), визуальный акцент (например, фрагмент C4-диаграммы или иконка парковки). Текст — читаемый, не мельче 32 px.

Агент **не генерирует** этот файл программно. Файл готовит пользователь вне репо (Figma/Canva/Miro/Photoshop) и кладёт в `docs/assets/social-preview.png`. После появления файла агент проверяет:

```bash
file docs/assets/social-preview.png         # PNG, 1200x630 (или близко)
ls -lh docs/assets/social-preview.png       # вес ≤ 1 МБ
```

После сохранения файла в README (после блока бейджей) добавляется HTML-комментарий:

```markdown
<!--
OG-image для Social Preview этого репозитория — docs/assets/social-preview.png.
Загружается через GitHub Settings → General → Social Preview (это ручное действие).
Процедура — docs/process/branding-checklist.md.
-->
```

Комментарий невидим в рендере, но виден тем, кто откроет raw README — это маркер, что превью обновлено и где лежит исходник.

## Процедура переименования Netlify-сабдомена

Создаётся файл `docs/process/branding-checklist.md` со следующей структурой (это содержимое файла, не часть плана):

```markdown
# Брендинг репозитория — чеклист

Регламент действий, связанных с внешним видом репозитория: OG-image и Netlify-сабдомен.

## OG-image (Social Preview)

1. Подготовить PNG 1200×630, ≤ 1 МБ. Сохранить как `docs/assets/social-preview.png`.
2. GitHub → репозиторий → Settings → General → Social preview → Edit → Upload an image → выбрать локальную копию `docs/assets/social-preview.png`.
3. Проверить рендер:
   - открыть `https://github.com/CeJIDb/sab-win-26-parking` в режиме инкогнито — карточка должна показываться в превью ссылки;
   - `https://metatags.io/?url=https%3A%2F%2Fgithub.com%2FCeJIDb%2Fsab-win-26-parking` — проверить тег `og:image` и предпросмотр для Twitter/Facebook/LinkedIn;
   - кэш мессенджеров (Telegram, Slack, x.com) обновляется не сразу — это нормально, не считать за провал.
4. При обновлении OG-image — заменить файл в `docs/assets/`, повторить шаг 2.

## Netlify-сабдомен

**Поведение старой ссылки.** После переименования сайта в Netlify старый адрес `boisterous-heliotrope-94df12.netlify.app` перестаёт обслуживать ваш сайт — обращения к нему возвращают 404. Точные сроки и условия повторного выделения старого имени Netlify не гарантирует, поэтому считайте старую ссылку «мертвой» с момента переименования. Практический вывод: правьте ссылки в репо в той же сессии, в которой меняете имя в UI.

Шаги:

1. Netlify → Sites → выбрать сайт → Site configuration → Domain management → Options → Edit site name.
2. Ввести новое имя (рекомендация: `mine-parking-sab-win-26` или похожее короткое осмысленное). Сохранить.
3. Проверить, что новый адрес `https://<new-name>.netlify.app/` открывается, wireframe рендерится.
4. Обновить ссылку в репо в четырёх местах:
   - `README.md` — блок бейджей, бейдж «Demo».
   - `README.md` — секция `## Навигация`, строка `Wireframe — демо`.
   - `README.md` — секция `## Wireframe-макет`, абзац «Задеплоенная версия UI доступна по ссылке».
   - `docs/process/project-journey.md` — абзац «Задеплоенная версия wireframe».
5. **Не трогать** документы-снимки, где URL фиксирует состояние на конкретную дату:
   - `docs/interviews/plans/interview-plan-7-2026-03-04-v01.md`, `docs/interviews/protocols/interview-protocol-7-2026-03-04-v01.md` — URL отражает реальность на 2026-03-04;
   - `plans/2026-05-12-readme-showcase.md` — план-снимок решений подплана 1 на 2026-05-12; URL зафиксирован в обосновании «решение зафиксировано» и менять его задним числом — искажать историю решений.
6. Прогнать `npm run lint:md-links` — должен быть зелёным.
```

## Принятые решения

Фиксация на входе сессии — чтобы не возвращаться к ним по ходу.

1. **OG-image готовит пользователь, не агент.** Альтернатива со скрипт-генерацией (HTML→PNG через Playwright) отброшена — даёт воспроизводимость, но добавляет код и CI-зависимость ради одного PNG. Если в будущем понадобится несколько превью под разные кампании — можно вернуться к этому решению.
2. **Базовый набор бейджей.** 5 бейджей зафиксированы (статус, CI, last-commit, license, demo); расширенный набор (Conventional Commits, Prettier, markdownlint, Husky) отброшен — у SA-портфолио аудитория не разработчики оснастки.
3. **Netlify-имя — на выбор пользователя в момент исполнения.** План не зашивает конкретный сабдомен, чтобы не плодить «решение в плане ради решения». В момент переименования пользователь сам выбирает имя из 1–3 вариантов; план только фиксирует процедуру и список мест в репо.
4. **Исторические протоколы интервью НЕ правятся.** `docs/interviews/plans/interview-plan-7-2026-03-04-v01.md` и `docs/interviews/protocols/interview-protocol-7-2026-03-04-v01.md` — это документы, привязанные к дате 2026-03-04. URL Netlify в них зафиксировал то, что было на момент интервью. Подмена URL исказила бы факт (читатель решит, что на 2026-03-04 уже был новый домен).
5. **Старый Netlify-сабдомен после переименования перестаёт обслуживать сайт.** После переименования старый URL возвращает 404; сроки и условия повторного выделения старого имени Netlify не гарантирует, поэтому считаем старую ссылку «мертвой» с момента смены имени. Практический вывод: в `branding-checklist.md` оба действия (переименование в UI и правка ссылок в репо) идут одним блоком, чтобы между ними не оставалось окна с битыми ссылками.
6. **CI-бейдж смотрит на `main`, не на текущую ветку.** Витрина показывает «здоровье» основной ветки, а не feature-ветки `docs/portfolio-roadmap`. Это сознательное решение — портфолио оценивается по `main`.
7. **`docs/assets/` создаётся с `readme.md` внутри.** Согласовано с паттерном репо: у всех соседних `docs/*` каталогов есть свой `readme.md` как точка входа. Бинарный каталог без описания особенно неприятен — `ls docs/assets/` ничего не объяснит читателю. README — это 10 строк (назначение + список текущих файлов + ссылка на `branding-checklist.md`), не overhead, а часть навигации.
8. **HTML-комментарий в README про OG-image — а не отдельный раздел.** Раздел «Social Preview» в видимой части README не нужен, информация — для будущего меня (или другого агента), который заглянет в исходник.
9. **Фаза 5 условная.** Если пользователь не переименует Netlify в этой сессии — это не блокирует закрытие плана. Фаза остаётся `[ ]`, в `## Итог` фиксируется «передано пользователю, фактическая правка ссылок — следующей сессией или вручную». Это компромисс: «готово» по плану — это «инфраструктура для бренда подготовлена», а не «всё видимое снаружи переименовано».
10. **Журнал трассировки не трогаем.** Все правки — витринные и навигационные; требования, артефакты, архитектурные решения не меняются.
